Behavioral Rules：Microsoft 用 AGENTS.md 让 Coding Agent 跨 Session 零复发

July 23, 2026

74 次暴露 0 复发：Microsoft 用 AGENTS.md 把人工评审变成 agent 的持久记忆

LLM coding agent 跨 session 重复同类错误是公认的痛点。人类评审者今天抓住了"HttpClient 不该被 dispose"，下一个 session agent 照犯不误——因为没有机制保留这个纠正。Microsoft 的 Aditya Aggarwal 和 Nahid Farhady Ghalaty 在 arXiv:2607.13091 提出了一个简洁到近乎朴素的闭环框架：每条被接受的人工评审评论 = 一条持久化行为规则。规则存入 version-controlled 的 instruction file（AGENTS.md），agent 每次启动都加载，形成棘轮效应——错误类别集合单调增长。

这不是 fine-tuning，不是 RAG，不是静态 prompt engineering。它是第四种路径：一个从评审结果到行为约束的自动反馈闭环。

核心机制：五步闭环 + 规则 Schema

框架的运作方式极其直观：

  1. Agent 生成/修改代码
  2. Agent 执行 self-review checklist（提交前自检）
  3. 人工评审提供反馈
  4. 被接受的评论编码为规则（添加到 instruction file）
  5. 更新后的 instruction file 在下次 session 加载

关键设计是规则不是自由文本，而是隐式遵循结构化 schema：

字段示例
Rule IDR17
CategoryArchitecture
Trigger OriginHuman PR reviewer
ScopeNew internal HttpClient registrations
ConstraintAdd client to AllowIPV4Internal SSRF policy
RationalePrevent runtime SSRF policy validation failures
Checklist MapSelf-review item #9
Traced ToPR review comment on missing SSRF allowlist entry

每条规则可溯源到具体评审事件，映射到 self-checklist 项，支持未来冲突检测和效果评分。Instruction file 分五节：行为规则、代码标准、自检清单、反模式、工作流规则。

硬数据：0% 复发率 + 评审焦点转移

在 35+ 微服务平台上部署 4 周、11 个 session 后，论文报告了令人注目的数字：

指标数值
行为规则5 → 18
代码标准3 → 15+
Self-review checklist0 → 15
追踪错误类别9
规则后 session 暴露74 次

Instr. file 大小~6,250 tokens（<5% of 128K）

9 个错误类别——从 HttpClient disposal 到 De Morgan 定律违反——在规则添加后累计暴露 74 次，零复发。这是一个观测性结果（非对照实验），但在 4 周窗口内的确显著。

更重要的是评审焦点的结构性转移。36 个 PR 评审的评论分布：

类别占比
架构/API设计/性能66%
认证/安全11%
查询正确性8%
机械正确性 + 风格仅 14%

低级错误被规则吸收后，评审者的注意力释放到设计层面。这正是"freed reviewers for higher-order concerns"的量化证据。

与 Reflexion/ExpeL/Voyager 的正交定位

论文最有价值的是系统对比部分。它不声称替代已有方法，而是明确了自己占据的正交维度：

关键差异：Reflexion 的记忆是情景级的——session 结束即丢弃，episode n 修复的错误在 n+1 会重新出现。本文的规则跨 session 边界持久化。ExpeL 从自主经验提取洞察，可能包含幻觉泛化——而本文的规则全部人工验证，因为错误规则会作为权威 context 放大错误而非纠正。SWE-bench 问"能解决这个 issue 吗？"，本文问"能避免已知错误类别吗？"——当前无基准测试衡量行为一致性随时间的变化。

规则特异性演化：从粗到细的自然精炼

一个有意思的发现：规则随时间从一般性向具体性演化。

Week 1460.60

特异性比率单调递增。早期规则粗粒度（"正确管理资源生命周期"），后期精炼为可操作约束（"IHttpClientFactory 创建的 HttpClient 不得被调用方 dispose"）。这暗示了一个实践原则：不要一开始就写精确规则，让它从使用中自然精炼。

对 Harness Engineering 的工程启示

1. Instruction file = harness 的持久化约束层

本文的 AGENTS.md 结构可直接映射为 harness 的 constraint layer。五节结构（行为规则、代码标准、自检清单、反模式、工作流规则）为 harness 设计提供了经过实战验证的模板。

2. 单调增长 + 特异性演化 = harness 持续改进的模式

规则不删除、只添加和精炼——这是 DevOps 持续改进原则在 agent 领域的映射。harness 的行为约束也应随时间累积，从粗粒度逐步精炼为具体可操作约束。

3. 缺失的基准 = agent verification 的空白

论文提出但未实现的行为一致性基准——规则语料 + 种子任务 + 时序评估 + 跨 session 边界——正好填补了当前 agent verification 领域的空白。现有基准测"当前能力"，没有一个测"纠正是否跨 session 存活"。

4. 三层记忆架构可复用

共享指令（全 agent）→ 个人规则（单开发者）→ session 记忆（单对话）的三层结构，为多 agent 系统提供了清晰的记忆分层模板。

局限与诚实标注

  • 无对照基线（论文自认）：0% 复发可能是规则效果，也可能是 Hawthorne 效应（被观察者改变行为）或任务分布变化。论文明确承认需要 A/B 对照实验，并列为未来工作。
  • 样本量小（论文自认）：11 session、36 PR、74 暴露——不足以做统计显著性声明，未报告 p 值。
  • 单语言/单团队（论文自认）：强类型语言 + 框架约定。弱类型语言或不同框架约定的代码库可能产生不同的评审评论分布和规则效果。
  • 增长饱和未测（论文自认）：~6,250 tokens 占 <5%，但未测试规则集饱和上下文窗口时的行为。层级化组织或摘要可能是必要的。
  • 规则冲突依赖人工检测（我的推断）：4 周仅遇到 1 例冲突。规模化后冲突频率上升，自动冲突检测将成为必需——论文提到了但未实现。
  • 评审质量依赖（论文自认）：规则质量取决于人工评审质量。错误规则会放大错误。噪声评审文化可能"毒化"规则集。

一句话

不改一个权重，用 version-controlled 的 AGENTS.md 把人工评审变成 agent 的持久记忆——74 次暴露 0 复发证明：闭环反馈的载体不需要比 Markdown 更复杂。
