CodeNib：预计算仓库多维视图，Agent token 消耗减少 50–87%

July 30, 2026

用 50–87% 更少的 token 找到同样的代码——不是靠更强的模型，而是预计算仓库的多维视图

Coding agent 每次接一个新 task，都要重新 grep、read、搜索依赖——即使同一个仓库的上一个 task 已经探索过完全相同的文件。UC San Diego 的 CodeNib 团队把这个看成 data-systems 问题：commit 是不可变的基础数据，chunks、embeddings、occurrences、relationships 都是可以预计算并复用的 derived views。一次构建，多 task 服用。

结果？在五个模型上，预注入 top-10 candidate + 一次性历史压缩的 context policy 用 50–87% 更少的 trajectory tokens 保持了与 grep/read 同等的代码定位精度。增量更新方面，vector reuse 在 90.3% 的 transition 上达到 25.4× 加速，graph repair 在 45.5% 的 transition 上达到 8.7× 加速。

核心思路：不 collapse 成一种索引

当前 coding agent 生态中，lexical search（BM25）、dense retrieval（embedding）、symbol navigation（LSP）、dependency graph 各自为政——不同的索引格式、不同的 runtime、不同的输出类型。CodeNib 的关键设计是 不把这些 collapse 成一个统一索引，而是让每种 view 独立存在，通过共享的 commit anchor 和 repository-relative source range 坐标系关联输出。

View物理实现输出类型适用场景
LexicalBM25 + Zoekt trigramRanked file/block matches精确标识符搜索
DenseFAISS L0/L2 (5 embedder)Ranked vector-similar blocks自然语言→代码映射
StructuralSymbol graph (tree-sitter+SCIP)Deterministic source locations"X 的定义在哪里"

不同 view 的返回类型和更新策略完全不同。合并成一个索引会丢失类型信息，且无法独立更新。

增量更新：不信任，比对验证

CodeNib 的增量维护机制有一个不寻常的设计：正确性不靠信任，而是 offline 与独立全量重建的结果比对。

Graph repair：Git diff → LSP 获取 changed symbols → 删受影响节点+边 → 重建 changed files → 重连边。之后 offline 与独立 LSP 全量重建比对 node/edge 集合。

Vector reuse：diff 中未变文件的内容哈希不变 → 直接复用 embedding。仅 re-embed 变更文件。之后比对 exact document identities + numerical vector equivalence + exact top-k replay。

结果揭示了维护质量的巨大差异：

维护方式匹配率Median Speedup备注
Vector reuse90.3% (28/31)25.4×3 个 Rust transition 的 top-10 replay 不匹配
Graph symbol repair45.5% (15/33)8.7×Go/Python 全过，Rust/TS 全败

Rust 和 TypeScript 的 graph repair 为什么全失败？不是算法有 bug，而是冷 LSP 重建自身就不确定——同一个 commit 用同一个 LSP 重建两次，产出的 symbol graph 就不同。Oracle 本身就不完美，所以比对的"正确答案"就不存在。这是论文最诚实的发现之一。

Static vs Live Navigation：不能无脑替换

CodeNib 提供了静态（预计算 graph）和动态（live LSP）两种 symbol navigation 后端。在 1,000 个请求上的比对结果：

请求类型匹配率Live/Static Latency Ratio
Definitions87.4%—
References39.0%—
总体63.2%4.72×（匹配子集）

References 的匹配率分语言差异巨大——Go 73%，Rust 仅 33%，C/C++ 仅 22%。论文明确说：这不是一个 "63% 工作负载可替换" 的声明，因为 references 匹配率太低，且没有 online classifier 能预测哪些请求会匹配。

4.72× 的延迟优势是 conditional opportunity，不是 achieved workload speedup。这种"有条件加速比"的报告方式值得所有系统论文学习。

五模型 Context Policy 扫描

Q5 是论文最贴近 agent 实际使用的实验。三种 context delivery 策略：

  • grep/read：无预注入，agent 自己搜索
  • eager：预注入 frozen top-10 dense retrieval candidate
  • compact：预注入 + 首次成功 read 后一次性压缩探索历史

在 Claude Haiku 4.5、Qwen3.5-9B/27B、Gemma 4-12B、Gemini 2.5 Flash 五个模型上，selected policy 用 12.9–49.9% 的 grep/read token 保持了定位精度（ΔAnswerRecall@5 ≥ −0.05）。

但 compaction 不是 uniformly dominant：Haiku 上 compact 反而比 eager 多用 23.3% token——因为它的探索模式本身就很高效，压缩反而破坏了有用的上下文。最优 policy 是模型依赖的：Haiku→Eager，Qwen/Gemma→Compact。

对 Agent 基础设施的工程启示

1. Multi-view 解耦是 repository context 的正确架构

不要试图找一个"最好的 embedder"或"最好的 index"。lexical、dense、structural 三种 view 的物理实现、维护路径、输出类型都不相同——解耦后各自优化，通过 manifest + source range 坐标系关联，是比"一个 index 打天下"更正确的设计。

2. Validity boundary 显式化

CodeNib 每个 Q 都带一个 conditional answer——"在匹配的子集上""63.2% 不等于可替换""graph expansion 的 CI 包含零"。这在 agent infrastructure 评测中是稀缺品质。大多数系统 paper 会掩盖这些条件，CodeNib 反而把它们作为核心发现。

3. Harness + 数据飞轮

§10 提出的方向最值得关注：runtime 记录每次交互的 view selection、tool call、context delivery、cost，这些 trace 反过来训练 retrieval routing、tool use、context selection——serving layer 既是执行平台也是可控训练数据源。这是 Harness Engineering 的下一步。

局限与诚实标注

  • 无并发支持（论文自认）：当前只支持 quiescent snapshot，不支持并发 agent 和 concurrent update。
  • Graph repair 在 Rust/TS 全失败（论文自认）：原因是 LSP 本身的不确定性，不是算法问题。但这限制了 graph repair 的适用范围。
  • Compaction 非 uniformly dominant（论文自认）：Haiku 上反而更差。需要模型特异的 routing。
  • 无 patch generation 评估（论文自认）：只测了 repository localization 和 context serving，没测实际的代码修改。
  • 无 learned online scheduling（论文自认）：retrieval routing 和 context selection 是固定 policy，没有在线学习。
  • 两篇论文的数据飞轮方向都未实现（我的推断）：CodeNib 的 harness+post-training flywheel 和 DataFlow-Harness 的 pipeline-as-training-data 都是 §10 的未来方向，两篇都没做。

与 DataFlow-Harness 的对偶

两篇都是今天分析的论文，形成精确的输入/输出对偶：

两者共同指向一个趋势：agent infrastructure 的重心正在从"让 agent 更强"转向"给 agent 更好的约束和上下文"。

一句话

CodeNib 把 repository context 从 agent 的重复劳动变成预计算的多维视图——50–87% token 节省、25× 增量更新加速、4.72× 导航延迟降低——但每个数字都带着条件：只在匹配的子集上、不能无脑替换、compaction 不是 always-win。这就是好的系统研究：给你数字，也给你边界。
