端侧小模型后训练技术蓝图：3 平面 × 8 模块 × 2 闭环

August 27, 2026

上一层我们把它定义成：

端侧小模型的能力提升，不是单独训练 Model，而是优化 Model × Harness × Environment 的闭环。

再往下拆，建议把整个系统拆成 3 个平面、8 个核心模块、2 个闭环。其中第一闭环是 Model Learning Loop，第二闭环是 Harness Evolution Loop。

第一平面：Execution Plane

这一层不是训练系统，而是真正的 Agent Runtime。

它决定了 Small Model 实际需要学习什么。

┌────────────────────────────────────────────┐
│              Agent Runtime                 │
│                                            │
│   Task Input                               │
│       ↓                                    │
│   Context Builder                          │
│       ↓                                    │
│   Small Model                              │
│       ↓                                    │
│   Action Parser                            │
│       ↓                                    │
│   Validator                                │
│       ↓                                    │
│   Tool / API / Device                      │
│       ↓                                    │
│   Result                                   │
│       ↓                                    │
│   State Update                             │
│       └───────────────┐                    │
│                       ↓                    │
│                   Next Step                │
└────────────────────────────────────────────┘

对于端侧模型，建议把 Runtime 明确分成 6 个层。

1. Context Manager

Raw History
    ↓
State Extraction
    ↓
State Compression
    ↓
Relevant Context Retrieval
    ↓
Prompt Assembly

核心原则：

端侧模型尽量不直接处理"历史"，而处理 Harness 编译后的"状态"。

例如：

传统：

Task
+ 8000 tokens history
+ 30 tools
+ long system prompt
          ↓
        Model

端侧：

Task
+ Current State
+ Relevant Memory
+ 5 Candidate Actions
          ↓
        Model

这个差别非常重要。

因为：

Model Size ↓

不应该简单意味着：

Reasoning Depth ↓

而应该意味着：

Raw Cognitive Load ↓

2. Tool Router

端侧模型不应该直接面对：

100 Tools

而是：

Global Tool Registry
         │
         ▼
┌──────────────────────┐
│ Tool Retrieval Layer │
└───────────┬──────────┘
            │
            ▼
     3~8 Candidate Tools
            │
            ▼
       Small Model

这里其实存在一个重要的后训练策略。

模型不需要学习：

Intent
→ Search 100 tools
→ Select

而是只学习：

Candidate Tools
→ Select
→ Fill Arguments

也就是说：

Harness 在前面做检索，Small Model 在后面做决策。

这是非常典型的 Cognitive Load Externalization。

3. Action Compiler

Small Model 输出：

Semantic Action

Harness 编译成：

Executable Action

例如：

{
  "intent": "search_file",
  "target": "report.pdf"
}

Harness：

Semantic Action
      ↓
Schema Validation
      ↓
Argument Completion
      ↓
Executable Tool Call

这允许 Small Model：

只学习"我要干什么"

而不一定学习：

"每个 API 参数如何精确填写"

因此后训练可以变成：

Train:
State → Intent

Instead of:
State → Exact API Syntax

对于 1B 以下模型，这个差别可能非常大。

4. Deterministic Recovery

这是端侧 Harness 最应该承担的东西。

Model
  │
  ▼
Action
  │
  ├──── Invalid Schema
  │          ↓
  │      Auto Repair
  │
  ├──── Tool Timeout
  │          ↓
  │        Retry
  │
  ├──── Recoverable Error
  │          ↓
  │      Alternative Tool
  │
  └──── Success

因此：

Recovery Policy

不一定都要：

Small Model Learned

可以拆成：

┌────────────────────┐
│ Deterministic      │
│ Harness Recovery   │
└────────────────────┘
          +
┌────────────────────┐
│ Semantic Recovery  │
│ Model Policy       │
└────────────────────┘

前者外化，后者后训练。

第二平面：Trajectory Plane

这是整个系统最重要、但当前工业界还没有完全标准化的一层。

核心对象应该不是传统：

Chat Dataset

而是：

Agent Trajectory

建议定义统一的数据模型：

Trajectory
├── Task
├── Initial State
├── Harness Configuration
├── Context Snapshot
├── Model Input
├── Model Output
├── Action
├── Tool Result
├── State Transition
├── Reward
├── Failure Type
└── Final Outcome

① Trajectory Capture

建议在 Harness 内建立一个：

Trajectory Event Bus

所有 Runtime Event 统一写入。

┌───────────────────────┐
│       Event Bus       │
├───────────────────────┤
│ ContextEvent          │
│ ModelRequestEvent     │
│ ModelResponseEvent    │
│ ToolCallEvent         │
│ ToolResultEvent       │
│ ValidationEvent       │
│ RetryEvent            │
│ StateTransitionEvent  │
│ ErrorEvent            │
│ RewardEvent           │
└───────────────────────┘

最终：

Event Stream
     ↓
Trajectory Builder
     ↓
Canonical Trajectory

近期 Agent Lightning 明确采用了这种思路：Harness 自己拥有环境交互循环，训练器通过 LLM 请求/响应对重建训练样本，而不是要求重新实现整个 Agent Runtime。(arXiv)

② Failure Mining

这是端侧 Agent 后训练的核心竞争力。

不要：

Success → Keep
Failure → Delete

应该：

All Trajectories
        │
        ▼
Failure Taxonomy

至少分成：

Failure
├── Model Failure
│   ├── Wrong Plan
│   ├── Wrong Tool
│   ├── Wrong Argument
│   └── Wrong Interpretation
│
├── Context Failure
│   ├── Missing Context
│   ├── Context Too Long
│   └── Wrong Memory
│
├── Harness Failure
│   ├── Bad Tool Description
│   ├── Bad Routing
│   ├── Bad Validation
│   └── Bad Retry
│
└── Environment Failure
    ├── Tool Unavailable
    ├── Timeout
    └── External Error

这个分类决定后续：

Failure
   │
   ├── Model Problem
   │        ↓
   │    Train Model
   │
   ├── Context Problem
   │        ↓
   │   Change Context
   │
   ├── Tool Problem
   │        ↓
   │   Change Tool Surface
   │
   └── Harness Problem
            ↓
        Patch Harness

Harness-R1 代表了后面的极端路线：直接从失败轨迹学习可执行的 Runtime Patch，用实际重跑结果而不是纯文本判断来优化 Harness。(arXiv)

③ Trajectory Store

这个模块建议不要理解成 Dataset Storage。

它更像：

Agent Experience Database

数据结构：

Experience Store
├── Successful Trajectories
├── Failed Trajectories
├── Repaired Trajectories
├── Teacher Trajectories
├── On-policy Trajectories
├── Harness Versions
└── Environment Snapshots

每个 Trajectory 应该有：

Task ID
Model Version
Harness Version
Tool Version
Prompt Version
Environment Version

否则会出现一个非常严重的问题：

Model v2
+
Harness v5
+
Trajectory v1

训练后：

Model learns behavior
that no longer matches runtime

所以建议：

Trajectory = f(
  Model,
  Harness,
  Tools,
  Context Policy,
  Environment
)

而不是简单：

Trajectory = f(Task)

④ Trajectory Compiler

这是现在最缺的模块。

一个原始 Agent Trace：

System Prompt
User Input
LLM Call
Tool Call
Tool Result
LLM Call
Retry
Tool Call
Error
LLM Call
Success

不应该直接全部用于训练。

需要：

Raw Trajectory
      ↓
Trajectory Compiler
      │
      ├── SFT Sample
      │
      ├── Preference Pair
      │
      ├── RL Rollout
      │
      ├── Recovery Sample
      │
      └── Harness Patch Sample

同一个失败：

Wrong Tool Call

可以生成 5 种训练数据：

① SFT
Correct Action

② DPO
Wrong vs Correct

③ RL
Negative Reward

④ Repair
Failure → Corrected Action

⑤ Harness Training
Improve Tool Description

所以未来核心基础设施不是：

Dataset Generator

而是：

Trajectory Compiler

第三平面：Learning Plane

这里包含 4 个模块。

⑤ SFT / Distillation

端侧小模型的第一阶段：

Teacher
   ↓
Successful Trajectory
   ↓
Trajectory Compression
   ↓
Student SFT

但当前更好的路线已经变成：

Success
  +
Near Miss Failure
        │
        ▼
Reflect / Repair
        │
        ▼
Corrected Demonstration
        │
        ▼
SFT

Apple 的 PROOF-Gen 代表了这一思路：失败轨迹不再直接丢弃，而是利用轨迹和评估反馈生成纠正指导，重新获得可训练的成功轨迹，并报告了对实际端侧模型的正向迁移。(Apple Machine Learning Research)

更适合端侧的 Trajectory Compression

Teacher：

20 Steps

Student 不一定学习：

20 Steps

而应该：

20 Step Teacher Trace
        ↓
Trajectory Compiler
        ↓
Minimal Sufficient Trace
        ↓
5 Step Student Trace

例如：

Teacher:

Think
Search
Think
Read
Think
Compare
Think
Search Again
Think
Select

压缩成：

State
↓
Search
↓
Relevant Result
↓
Select

这是端侧模型非常关键的一种：

Behavioral Compression

⑥ On-policy Distillation

这是 1B–4B 模型最关键的一层。

不要只做：

Teacher Output
↓
Student Imitation

而是：

Student
   ↓
Generate Trajectory
   ↓
Teacher Inspect / Correct
   ↓
Dense Supervision
   ↓
Student Update

原因是：

Teacher Distribution
≠
Student Distribution

例如：

Teacher：

A → B → C

Student：

A → X → ?

如果 Student 只学习 Teacher Trace：

A → B → C

它永远没有训练：

A → X

如何恢复。

所以需要：

Student On-policy
        ↓
Actual Failure State
        ↓
Teacher Repair
        ↓
Train Recovery

Liquid AI 在 LFM2.5-2.6B 上采用了非常有代表性的四阶段配方：SFT、领域专门 Teacher、Multi-Domain On-Policy Distillation、最后的真实 Harness 内 Agentic RL。(Liquid AI)

⑦ Harness-in-the-loop Agentic RL

这是后训练系统真正的核心。

传统：

Trainer
   ↓
Environment

Harnessed RL：

Trainer
   ↓
LLM Endpoint Proxy
   ↓
Production Harness
   ↓
Environment

具体：

┌─────────────────────────┐
│     RL Trainer          │
│                         │
│ GRPO / PPO              │
└────────────┬────────────┘
             │
      LLM API Proxy
             │
             ▼
┌─────────────────────────┐
│    Target Harness       │
│                         │
│ Context                 │
│ Tools                   │
│ Memory                  │
│ Recovery                │
└────────────┬────────────┘
             │
             ▼
        Environment

Liquid AI 的公开架构中已经将 Training Engine、Rollout Engine、RL Orchestrator、Sandbox Service 和 Blackbox Harness 解耦，并通过 Harness Proxy 捕获 token-level trajectory，目标就是让生产 Harness 无需为训练重写。(Liquid AI)

⑧ Harness Optimizer

这是下一代。

Failure
   ↓
Root Cause Analysis
   │
   ├── Train Model
   │
   └── Train / Modify Harness

Harness 可以优化的参数包括：

Harness Config
├── System Prompt
├── Context Order
├── Context Compression
├── Tool Description
├── Tool Retrieval
├── Validator
├── Retry Policy
├── Recovery Policy
└── Memory Policy

进一步可以形成：

Meta Agent
      ↓
Read Failure Trajectories
      ↓
Generate Harness Patch
      ↓
Sandbox
      ↓
Regression Test
      ↓
Evaluate
      ↓
Accept / Reject

Harness-R1 已经公开验证了"训练一个 Harness Engineer，根据失败批次生成可执行 Runtime Patch，再用实际重跑成功率作为奖励"的路线。(arXiv)

两个闭环

Loop A：Model Learning Loop

Runtime
   ↓
Trajectory
   ↓
Failure Analysis
   ↓
Trajectory Compiler
   ↓
SFT / Distillation / RL
   ↓
New Model
   ↓
Runtime

优化：

Model Weight θ

Loop B：Harness Evolution Loop

Runtime
   ↓
Failure
   ↓
Root Cause
   ↓
Harness Patch
   ↓
Regression Test
   ↓
New Harness
   ↓
Runtime

优化：

Harness Policy H

最终系统：

Agent = Model θ × Harness H

优化目标：

max R(θ, H)

subject to:

Latency < L
Memory < M
Energy < E
Context < C

端侧最关键的进一步变化：Quantization 必须进入训练闭环

对于端侧还有一个很容易被忽略的问题：

Train BF16 Model
      ↓
Train Agent Behavior
      ↓
Quantize Q4
      ↓
Deploy

可能出现：

Tool Selection Degradation
Schema Degradation
Long-horizon Error Accumulation

所以未来应该：

Teacher BF16
    ↓
Quantization-Aware Distillation
    ↓
Q4 Student
    ↓
Harness Evaluation
    ↓
On-policy Fine-tuning

Liquid AI 最近公开的 QAD 路线已经将量化感知蒸馏直接用于多个端侧模型，以尽量保留 BF16 Agent 能力。(Liquid AI)

因此完整闭环实际上是：

FP Model
   ↓
Quantization
   ↓
Quantized Model
   ↓
Real Harness
   ↓
Real Device
   ↓
Failure
   ↓
Post-training

不是：

Train
↓
Quantize
↓
Done

最终会形成一个新的技术栈

                    EDGE AGENT STACK
┌─────────────────────────────────────────────────┐
│                                                 │
│                 Runtime Plane                   │
│                                                 │
│ Context │ Tools │ Memory │ Validator │ Recovery │
├─────────────────────────────────────────────────┤
│                                                 │
│               Trajectory Plane                  │
│                                                 │
│ Capture │ Store │ Failure │ Compiler │ Replay   │
├─────────────────────────────────────────────────┤
│                                                 │
│                Learning Plane                   │
│                                                 │
│ SFT │ Distillation │ On-policy │ RL │ QAD       │
├─────────────────────────────────────────────────┤
│                                                 │
│              Evolution Plane                    │
│                                                 │
│ Model Optimizer │ Harness Optimizer │ Evaluator │
└─────────────────────────────────────────────────┘

对这个方向的核心判断

未来真正有价值的不是：

Edge Model Post-training

而是：

Edge Agent Behavioral Optimization

优化对象变成：

Model
+
Context
+
Tools
+
Memory
+
Recovery
+
Runtime

所以端侧小模型的竞争将发生一个非常重要的转移：

从
"谁的模型参数更聪明"

转向：

"谁能更高效地把失败经验
编译成 Model Update 和 Harness Update"

如果进一步收敛成一个具体工程方案，建议下一步直接拆成 P0/P1/P2 的完整技术蓝图：

  1. P0：MVP——Harness Proxy + Trajectory Store + SFT
  2. P1：On-policy Distillation + Failure Mining
  3. P2：Harness-in-the-loop RL
  4. P3：Harness Optimizer + Model/Harness Co-evolution

其中最建议先深入的是 "Trajectory Compiler + Failure Taxonomy"：这两个模块实际上是整个端侧小模型后训练与 Harness 联动的"数据操作系统"。
