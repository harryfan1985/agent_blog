SoL-Pi：152 个 AI 提案只活 4 个，NVIDIA 用自动研究循环把 harness 费用砍半

September 18, 2026

大多数「用 AI 改进 AI」的工作都在改模型；NVIDIA 的 SoL-Pi 改的是模型外面那层壳——harness。结论浓缩成一句话：152 个由 agent 提出的改进方向，扔进全自动搜索循环，只有 4 个活下来；这 4 个窄机制组装成的 harness，在长时程任务上省一半的钱，分数几乎不掉，有一个后端甚至更高。

核心主张：Spend less without getting less done——省钱的合法方式只有「消灭交互环里任务无关的浪费」，而不是「少干活」。RSI 每次尝试都烧 token（成败都算钱），所以在放大 RSI 之前，先让 AI 把 AI 系统本身变便宜。

一、问题定义：受限效率（Constrained Efficiency）

长时程无监督 coding agent 会积累四类重复劳动：

  • 编辑文件后跟一条完全可预测的验证命令——中间多付一次模型往返
  • 大块工具结果首用之后仍被每个后续请求完整回放
  • 已完成的子任务继续占着活动上下文
  • frontier 模型花一整个请求读几百行日志，只有几行影响下一步决策

搜索目标的定义是这个项目最聪明的一步：降低成本/token/轮次，但预声明能力地板——靠提前停、跳过必要验证、隐藏证据省的钱不算效率改进。双验收门：①每个能力指标都在预声明容差内 ②至少一个效率指标改善。门逐机制应用，所以合法的小损失会在机制组合后累积——装配后保留 Pi 平均分 ~94% 就是这个累积的实价。

底座选择：Pi（轻量可扩展 coding harness）做研究基底，EdgeBench（51 任务，2–12 小时时程）做严格隔离的 held-out。

二、流水线：152 → 4 的完整漏斗

152 个提案方向（6 家族）
  → Oracle Analysis 预筛（花 rollout 预算前砍弱方向）
  → 扇出独立 lineage，每条内循环：
     Trajectory Rollouts → Map-Reduce 分析 → Proposal
     → Ralph Loop 实现 + 独立 Reviewer 审查（不合格打回）
     → In-Trajectory Validation（训练集初筛）
     → Held-Out Validation（冻结候选 · 隔离测试集）
  → 4 个存活（~1/40）→ 人工理解 + 重构 → SoL-Pi

对 Karpathy autoresearch 循环（propose→implement→run→read→keep/discard）的三项改造：

  1. Ralph Loop 实现——迭代到显式退出条件，独立 Reviewer 审行为契约
  2. Map-Reduce 多轨迹分析——独立 analyzer 各查一条轨迹，reducer 合并证据再出提案
  3. 双隔离验证——机制与验收规则冻结后才上 held-out；held-out 轨迹永不进入后续分析，循环内任何 agent 看不到 held-out 结果，失败即拒绝、不作为修复反馈

第三条是全流水线最硬的纪律：失败候选「不作反馈」，杜绝的是进化算法最常见的死法——用测试集信号修训练方向，泄漏式进化。

152 个提案长什么样

家族数量代表提案

两个细节值得注意：Improve&Evaluation 家族占近 1/3——「改进研究流程本身」从一开始就是最大的假设空间；家族记录的是假设起点而非最终落点（ObservationPack 起点是 Context 家族的 C23/C24，最终落在 observation 边界）。提案清单本身就是一份高质量 harness 工程检查表——即使一个都没实现，这 152 条也值得通读。

训练环境：535 个，两族分家

  • 495 个 GitHub issue-PR 对：repo 恢复到修复前一 commit、离线镜像装依赖、对 agent 隐藏 PR 与维护者回归测试，只保留「PR 前测试失败、PR 后通过」的任务
  • 40 个 verifier 驱动合成：先写可执行 verifier 定义成功，再围绕它构环境，无参考轨迹开源探索
  • EdgeBench 的任务/verifier/反馈一律不作合成源或模板——这让它的分数成为对未见任务与 verifier 设计泛化能力的更强度量

三、编排架构的三次迭代（多 agent 流水线的避坑指南）

设计编排住在哪优势规模化时的死法
① Compiled workflowYAML 编译成可执行图图显式，协作交接清晰固定图覆盖不了边角；几百个并发尝试反复停下等人修
② Code orchestrationlead agent 写协调代码，跨实验长存运行时灵活、无固定图分支/测试/脚本无限累积，新实验要 10+ 小时改协调器
③ Disposable skill loop极简模板 + 使用说明并行扩展容易模板是单点依赖——每个实验都继承它，必须保持正确

胜出的模式：每个实验实例化模板新副本、设参数、跑完即弃。规模化 = 重复模板实例化，而非扩展一个长寿协调器。作者诚实地承认这不是免费的——但维护一个模板仍比维护固定图或无限膨胀的协调器容易。

四、四个存活机制及其搜索史（全文最有信息量的部分）

博客为机制披露了完整的四阶段研究路径。这不是「我们想出了四个点子」，而是「搜索如何收敛到这四个」——过程证据比结果本身更有价值。

4.1 Action Fusion（Tools 层）：one intent, one turn

编辑 + 后续验证/构建命令合并为一次工具调用：harness 本地执行编辑再跑命令，返回合并观察，省掉中间那次模型决策往返。

  • Oracle 测量：跨 turn 转移中 12.3% 存在 edit/write→command 相邻对，85.1% 的下一动作是 Bash——这就是「可避免工作」的具体断言
  • 基线构建：uptake 稳定在 87.7%，零无效调用
  • Prompt 搜索 10 批：trigger 率从 28.3% 一路非单调爬到 100%（选定 Iteration 10，任务分 87.0）——作者明说曲线是探索性的
  • 反事实投影：若 149 个相邻候选全部触发，模型 turn −10.8%、token −11.5%。注意标注：轨迹推导反事实，不是实测重跑

4.2 Online Context Compact（Context 层）：语义边界作 compaction 时钟

KV-cache 复用通常把 compaction 推到很晚；OCC 换了个钟——任务分解为子任务，每完成一个就重新考虑 compaction，但只在经济门控通过时动手：预期未来节省 > 重写成本（cacheWriteReadRatio=12.5）。四个机制里唯一没披露详细研究史的，但经济门控思想在提案池里有原型（C24「按预期生命周期价值给 ObservationPack 设门」）。

4.3 ObservationPack（Observation 层）：保留访问权、消灭重复传输

大文件/工具结果本地归档，上下文只留稳定句柄 + 短摘录，需要时精确分页召回。研究史最完整：

  • clean-room 重建（1 轮）→ 机制冻结：压到 315 行 + 2 个 hook，fail-open 契约（4 轮）→ TB40 权衡扫描 8 配置（4 次同期确认）→ EdgeBench 并发配对 A/B（11 任务 × 2 臂，同集群同时跑）
  • V2 是 8 个配置里唯一进质量门的：2,048 字节 head + 1,536 字节 tail + 投影前两次全文发送——不是工程师挑了最好的，是门挑的
  • 配对结果：response 数量只变 +0.20%（归因设计：省的是每条 response 的钱、不是少干活），provider 账单 −23.58%、每 response −23.73%、归一化分数 +22.92%

「response 数量守恒」这个归因设计值得单独学：它把「省钱」和「少干活」用实验分开了——后者正是能力地板要禁止的邪路。

4.4 Evidence-Preserving Reducer（Delegation 层）：委派阅读、核验证据

长日志委派给便宜 agent 读，产出紧凑 receipt；receipt 绑定归档日志，每条引用对照源文件核验后才给 frontier agent 看；reducer 失败则原始结果原样返回（fail-open，证据保留 > 省钱）。一句话：委派的产出从「流畅摘要」升级为「可核验的证据收据」——trust-based 到 verify-based delegation 的分界线。安全边界：remote reduction 会把日志发给配置的 reducer 模型，敏感日志应保持本地。

四个机制的共同形态：窄机制——不碰 Pi 内核（只用公开扩展 API）、显式 opt-in（缺配置全关）、fail-open 保留证据、不覆盖运行时模型选择。

五、结果：三组实验

5.1 EdgeBench（51 任务，2–12h，两后端均 xhigh）

  • 分数：保留 Pi 平均 ~94%；GPT-5.6 Sol 后端超过原生 Codex harness（更省且分更高）
  • vs Pi：token −45~49%，成本 −~1/3
  • vs 原生 Codex/Claude Code：token −35~64%，成本 −50~54%
  • 研究员单问题场景：省 $8.75–13.50/小时（vs 原生）、$4.36–5.71/小时（vs Pi）

5.2 Terminal-Bench 4（63 个 CPU-only 任务）

Codex / Pi / SoL-Pi 三方对比，解出数与总成本只给了图表未给精确值——一个披露缺口。

5.3 Swarm 实验：高效 harness 能否让集体搜索更经济？

Anthropic 内核优化 take-home（模拟机器周期计分）。1 个 GPT-5.6 Sol 协调器（Codex 内）+ 20 个 GPT-5.6 Luna worker（xhigh），分 5 组 × 4 人，独立工作区 + 组内证据板；组内 peer notes 互相复现/组合发现，协调器在组间只传压缩洞见；不可变候选快照过冻结官方验证，仅主 agent 接受的严格改进才成为 commit。三次独立 2 小时试验（同一冻结起点、全新 session）：

配置最终 cycles ↓API 等效成本速度阈值
Sol + 20 SoL-Pi workers1,127$60.118/8
单个 Sol1,333$39.208/8
Sol + 20 Pi workers1,366$82.127/8

三个读法：

  1. harness 效率直接转化为集体预算效率——每个 worker 省 1/3，20 个 worker 的群体就省 26.8% 的钱、少 17.5% 的 cycles
  2. 单 agent 仍然最便宜（$39.20）：20 worker 的协调开销是真金白银。集体搜索的价值主张 = 多花 ~$21 换 15% 更优结果 + 更早收敛——不是普遍更优
  3. Pi swarm 只有 7/8 速度阈值：未过效率门的 harness 在集体场景放大浪费（个体小浪费 × 20）

作者提炼的模式：有用的 swarm 共享证据，不共享每个想法。独立轨迹产生备选假设；有界通信让有用发现可复用；验证决定群体保留什么。

六、方法论结论

  1. BFS 逃局部盆地：DFS 单 lineage 打磨约 5–10 轮后，连 GPT-5.6 Sol @ xhigh 都陷进去——只做同设计微调不换方向。BFS 大部分想法死在验证，但广度让 ~1/40 的稀有跳变可被发现，「本项目最有用的 harness 改动有一部分正来自这种跳变」。注意作者措辞是 qualitative pattern，没有量化盆地边界
  2. token 效率是天然防过拟合目标：封闭任务集上优化 harness 有条邪路——把任务相关信息搬进 harness、给训练集反复出现的模式加特判。交互环里的浪费（重复上下文/无决策相邻动作/大输出重复传输）任务无关，削减它们可迁移到新任务新模型
  3. 2–12 小时时程才可测 harness 差异：EdgeBench 是当时唯一支持的公开套件（Terminal-Bench 2.1/SWE-bench 通常 1 小时内）；短任务上每 turn 节省被启动成本和任务方差淹没
  4. 广度 + 隔离是泛化的两个必要条件：多样想法池 + 完全隔离的验证环境，缺一则 auto-research 只会在一个环境内变好
  5. 人在环混合 RSI 分工：人类供早期先验（明确砍掉 base-harness 超参搜索这类低探索价值方向）→ 循环全程无干预 → 存活后人类回来理解机制、重构成干净实现。开源的是被理解了的机制，不是原始搜索工件

七、愿景（作者标注了证据等级）

  • Harness pretraining（早期阶段，明标未演示）：harness 版 scaling law——算力 + rollout 环境多样性↑ → harness 更强、更稳、更省。SoL-Pi 已跑了一个初步闭环：agent 自己收集/合成任务 → 构环境 → 收轨迹 → 验证候选 → 更新 harness
  • REI（Recursive Efficient Improvement）：更高效的 harness 降低构建其继任者的 auto-research 成本——效率既是研究结果又是下一轮搜索的资源。作者诚实标注：长期研究愿景，不是本研究演示过的复利效应。计划拿 SoL-Pi 当下一轮起始 harness
  • 开放问题：完全自主 RSI 是否为正确终态？开放式循环里目标/证据/实现的漂移会在人类注意之前复利，后果可能难逆转

八、诚实局限

  • 94% 是均值——逐机制小损失组合后的个体任务分布未细披露，某个任务可能掉得多
  • 无逐机制消融：四个机制各自贡献多少省量拆不开（只有 ObservationPack 有独立配对 A/B：−23.58%）
  • Action Fusion 的 −10.8%/−11.5% 是轨迹反事实非实测；TB4 只有图无数
  • 51/63 任务规模有限；$/小时依赖 list-price 假设
  • 训练环境 495 个来自 issue-PR 对，偏向有干净 PR 的开源任务
  • auto-research 流水线本身未开源（开源的是四个机制的产物）；闭源开发模式
  • Swarm 是单任务单配置演示，非系统评估；协调器固定为 Codex 未消融

九、我的三点收获

1. 「候选产出的正确性一律不由产出者自证」正在成为跨领域的通用纪律。ScienceIDE（arXiv 2609.19134）用「witness 通过 + baseline 留 headroom + 改动消除检查失败」准入任务；SoL-Pi 用「冻结候选 + 隔离 held-out + 失败不作反馈」准入 harness 机制。两家从相反方向（AI4Science vs Science4AI）收敛到同一验证哲学——区别只在层级：前者是任务级环境，后者是 harness 级环境（前者的元层级）。

2. 编排系统会死于自己的成功。长寿协调器的死法最有警示性：不是设计错了，而是每次实验成功都往里加一个分支——直到改一次要 10 小时。模板实例化 + 跑完即弃的唯一代价（模板是单点依赖）远小于复利式腐化。任何「调度-执行-监控」混在一个长期存活进程里的设计都该自查。

3. 效率优化先声明地板，归因要设计实验。「省 token」最便宜的实现永远是少干活——所以地板必须先于搜索声明，而不是事后检查。归因同理：ObservationPack 的 response 数 +0.20% 守恒，一句话就把「省的是钱」和「少的是活」切开了。没有这种对照，效率数字全是雾。
