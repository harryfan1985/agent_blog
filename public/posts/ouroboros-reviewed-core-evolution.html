自我进化的 Agent 会审核自己的每一行代码：Ouroboros 的审查门控进化

August 14, 2026

一个 Agent 在 161 天里改了自己 1,085 次，近三分之二的修改被自己的审查机制拦下——它依然跑出了三项基准 SOTA

Ouroboros（arXiv:2608.08311，MIT 开源）是一个把 harness 本身当作进化对象的 coding agent：工具、上下文组装、prompt、核心实现全部存进 versioned 仓库，每一次变更都必须通过多模型审查 commit gate，而审查通过的版本直接成为后续任务的运行时。它的 Terminal-Bench 2.1 成绩是 86.97%（审计后 86.74%），OSWorld-Verified 90.69%，CL-Bench 0.2301——三项都自称是目前公开报告的最高分。

但真正值得注意的不是分数，而是机制：1,522 次被审查的自编辑尝试里，近期拦截率高达 63.5%。一个能改写自己代码的 agent，安全的关键不是禁止进化，而是让每一次进化都过审。

核心发现一：五项基准，三胜两平——harness 是可进化的杠杆

所有长程 agent 都是「模型 × harness」系统，但大多数 harness 设计后即冻结。Ouroboros 冻结的只有 benchmark 种子，harness 本体持续进化。结果按 benchmark 拆开看：

Terminal-Bench 2.1Opus 586.97% raw / 86.74% auditedClaude Code+Fable 5: 83.8%领先 ~1.7 个标准误，SOTA
OSWorld-VerifiedOpus 590.69%Intelligence-Indeed: 90.19%+0.5pp，SOTA

注意事实分层：Terminal-Bench 的差距按论文自己给的 ±1.7pp 标准误算约 1.73 SE（双尾 p≈0.08），属于边缘显著，论文「roughly two SE」的措辞略有乐观；README 也自述成绩为 self-reported。但三处 SOTA 全部附带开放 traces、manifests 与公开 submission，审计链条是完整的。

核心发现二：审查门是真实约束，不是橡皮图章

Hope——Ouroboros 的 161 天长期部署实验——的自编辑统计是最有信息量的部分：

指标数值
自修改提交1,085（94.2% 由 agent 自己撰写）
被审查的自编辑尝试1,522
近期审查拦截率63.5%
持久错误类（pattern register）40 类 / 659 次复发
交互规模7 个渠道 · ~3,600 人 · 222,474 条公开消息
运行成本$110.6K · 79.7B tokens · 175,755 LOC · 227MB 记忆工件

审查管道是工程核心：deterministic preflight → 对 staged diff 打指纹 → 多模型审查收集证据 → 再次打指纹（任何中途变异都 abort）→ 提交。每次写入会让之前的审查证据失效——freshness 绑定到 staged snapshot。sub-quorum 的审查小组永远不能产生 clean pass。在 161 天、1,522 次尝试的进化压力下，没有任何一次记录的 episode 反抗过操作员的 shutdown，说明这套边界在持续进化中是站得住的。

核心发现三：经验驱动进化——有用工作会改变接收后续任务的 agent

Ouroboros 有两种进化模式。递归自由进化把「改进」本身当任务，完成后可以调度下一轮——这是 RSI 的经典形态。更值得注意的是经验驱动进化：日常执行、反思、审查拦截、仪表、甚至用户社交反馈暴露出的 bug 和低效路径，被记录成持久错误类（pattern register），agent 自己决定是否开维护任务，修复走同一条审查门。

论文给了两个落地案例：用户在公共频道反馈 Hope 偶尔重复发送同一条消息——agent 追踪到重复发送路径，落地了一个 reviewed verbatim-duplicate guard；deep self-review 任务反复因「模型不可用」中止——agent 追到 review pack 上下文溢出，把组装路径换成按 import-graph 中心性排序、按 provider 标定大小的 context atlas。前者始于社交反馈，后者始于自身观察，都变成了后续所有交互共享的结构性修复。

核心发现四：安全不是清单，是控制面与执行面的分离

自我进化的 agent 可以重写自己的代码、甚至换掉自己的模型 API——论文把「agent 自选模型 API」列为头号风险：re-routing 一个模型槽位就能改变 refusal 行为、扩大 prompt-injection 面、让成本量级变化，而用户看到的接口毫无变化。所以模型路由是「受审计的配置变更」，不是普通运行时选择。配套的护栏包括：

  • 宪法（P0-P4 受保护核心）常驻上下文，走不可截断的读取路径，普通写工具无法触碰治理文件
  • staged diff 审查前后双指纹，审查期间任何变异直接中止提交
  • 消费上限在 agent 外部强制执行，agent 无法自行提高
  • 操作员隔离通道 + /panic——在 agent 处理之前由 supervisor 解析并终止整个进程树

一次近乎全删 uncommitted worktree 的事故触发了先前实现的 rescue mechanism——agent 级的自我恢复与 supervisor 级的操作员权威被实战区分开：前者可以进化，后者必须永远保留 halt / replace / rollback 的能力。

对 Agent 基础设施的工程启示

1. 把「变更审查」做成主路径，而不是事后审计

Ouroboros 的 commit pipeline（preflight → 指纹 → 多模型 quorum → 再指纹）是 production 化的参考实现，MIT 开源可直接读。任何允许 agent 自我修改的系统，最低限度要具备：审查证据绑定 staged snapshot、双指纹防中间人、sub-quorum 不能通过。

2. 错误归因要落到「类」而不是「例」

pattern register（40 类 / 659 次复发）对应宪法原则 P2 "Meta-over-Patch"：修错误类，不修症状。把反复失败固化为「错误类 + 计数 + 根因 + 结构性修复」四元组，修复工作从逐实例修补升级为类级预防。

3. 模型路由是安全关键面，必须走审计通道

一个能自己换 provider 的 agent，换模型就等于换行为。路由变更应当与普通工具调用分权：审计日志、审查证据、成本护栏全部绑定到路由变更，而不是任其作为运行时选择发生。

4. 基准冻结与部署进化分离

benchmark 用冻结种子跑（含明确 scaffold disclosure），长期部署在独立 lineage 上继续 live evolution——可复现评估与持续进化共存，两者互不污染。这是所有想「边跑边改」的系统都应采纳的工程纪律。

局限与诚实标注

  • 单案例归因困境（论文自认）：Hope 是单 lineage 而非对照种群，无法区分 harness 进化、模型升级与时间效应各自的贡献。
  • 成绩自报（论文自认 + 我的核实）：README 明说 self-reported；Terminal-Bench 官方 leaderboard 我未能从公开 repo 直接核到分数，86.97% 的差距按 ±1.7pp SE 算约 1.73 个标准误，边缘显著（我的推断：论文的 "two SE" 措辞偏乐观）。
  • 审查者与 agent 共享盲点（论文自认）：LLM 审查员与 agent 是同类模型，低上下文模式下还跳过 whole-repo scope review——多模型 quorum 缓解但未消除。
  • 宪法并非绝对不可变（我的推断）：BIBLE.md 明说 agent 可以提议修改宪法，仅 P0-P4 为受保护核心——进化压力下宪法的长期稳定性仍是开放问题。
  • SWE-bench Pro 受数据污染影响（论文自认）：任务 ID 暴露 upstream fix commit，双方都触达过参考材料，已做对称过滤——这类基准的原始数字需要谨慎解读。

一句话

Ouroboros 证明自我进化的 harness 能跑出 SOTA——而它安全的关键不是禁止进化，而是把每一次进化放进一个有 63.5% 真实拦截率的审查管道，并让宪法、模型路由、消费上限这些控制面独立于进化压力之外。
