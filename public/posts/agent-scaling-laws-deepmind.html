Agent系统缩放定律：260配置实验揭示何时多Agent真正有用

August 4, 2026

当整个行业还在争论"more agents is all you need"时，Google DeepMind 联合 MIT 的 20 人团队扔出了一份 260 配置的受控实验报告，用数字回答了一个更根本的问题：什么时候多 agent 系统真的有用，什么时候它只是在浪费 token？

一句话结论

多 agent 系统的效果跨度从 +80.8% 到 -70.0%，取决于架构-任务对齐度，而非 agent 数量。论文建立的缩放定律模型（R²=0.413）能以 87% 的准确率预测给定任务的最佳架构。

实验规模：空前的控制变量

260 个配置，每项严格控制 prompts、tools、compute budget 一致，仅变化协调结构和模型能力：

  • 5 种架构：Single Agent (SAS)、Independent、Centralized、Decentralized、Hybrid
  • 3 个 LLM 家族：OpenAI (GPT-5 系列)、Google (Gemini 系列)、Anthropic (Claude 系列)
  • 6 个 Agentic Benchmark：BrowseComp-Plus（网页浏览）、Finance Agent（金融分析）、PlanCraft（Minecraft 规划）、WorkBench（业务自动化）、SWE-bench Verified（软件工程）、Terminal-Bench（CLI 任务）

核心发现：三条缩放定律

1. 工具-协调权衡（Tool-Coordination Trade-off）

β̂ = -0.096，p = 0.002

单 agent 系统的效率 E_c=0.466，多 agent 降至 0.074~0.234（2~6× 惩罚）。工具越多的任务（如 16-tool 的 WorkBench），MAS 的协调开销越致命。Hybrid 架构在 WorkBench 上坍塌到成功率 0.21。

机制解释：多 agent 碎片化每个 agent 的 token 预算，不足以承载复杂工具编排。

2. 能力天花板（Capability Ceiling）

决策边界：P_SA* ≈ 45%

当单 agent 基线超过 45% 时，MAS 的协调成本超过改进空间。SWE-bench 上所有 MAS 架构都轻微退化（-2% ~ -15%），因为 SAS 均值 0.522 > 0.45。

最简洁的行动规则：如果你最好的单 agent 已经答对 45% 以上的问题，别加 agent——那是纯开销。

3. 架构决定错误放大

Trace 级错误放大因子（A_e^trace）：

架构A_e^trace机制
SAS（基线）1.0×无传播
Independent17.2×无校验——每个 agent 独立出错，聚合无纠错
Decentralized7.8×peer 通信部分纠错
Hybrid5.1×部分验证
Centralized4.4×验证瓶颈——orchestrator 在聚合前检查

Centralized 架构通过验证瓶颈将错误传播控制在 4.4×，而 Independent 让每个 agent 的错误不加阻拦地流向最终输出，放大到 17.2×。

为什么 PlanCraft 全败而 Finance 全胜？

论文从执行轨迹层面揭示了机制差异：

PlanCraft（序列规划，D=0.419）——SAS 只需 3 步：search("diorite_wall") → move → craft。但 Centralized MAS 将本质序列任务人为分解为冗余子任务（研究配方 + 检查库存 + 执行制作），协调消息消耗的 token 预算远超过序列执行本身。

Finance Agent（可分解推理，D=0.407）——SAS 受限于序列搜索瓶颈（7 步顺序查询）。Centralized MAS 自然并行化：A1 分析新闻、A2 研究 SEC 文件、A3 评估运营影响，Orchestrator 综合——任务的自然可分解性完美对齐了协调结构。

两个 benchmark 的域复杂度几乎相同（0.407 vs 0.419），但结果天差地别：决定因素不是复杂度，而是任务可分解性。

架构选择决策树

条件推荐架构原因

该决策树在 held-out 配置上达到 87% 架构选择准确率，远超随机选择（20%）和仅基于模型能力的模型（54%）。

异构 Agent：混合模型没有"多样性红利"

论文还测试了异构配置（不同模型混用）：

  • Centralized 异构：一律劣于强模型的同构基线（-0.01 ~ -0.20）
  • Decentralized 异构：小幅改善，但可归因于更强的模型本身

也就是说——把 GPT-5 和 GPT-5-nano 混用不会产生"多样性红利"，核心收益始终来自更强的模型。

局限性与推断边界

  • R²=0.373 并非很高：62.7% 的方差仍未被模型解释，prompt engineering、领域知识偏见等关键因素未捕捉
  • Agent 数量受限：n_a ∈ {1, 3}，未探索 5/10/50 agent 的极限缩放行为
  • 架构覆盖面有限：仅 5 种拓扑，未涵盖 MoA、分层递归、动态路由等更复杂设计
  • Hybrid 外推失败：在 held-out 模型上 Hybrid 被系统性高估 +37%——说明模型在未见能力区间的泛化存在结构性偏差
  • 跨家族 Intelligence Index 不可比：同样的 II=75，GPT-5.2 的 P_SA=0.45 但 Gemini-3.0-Flash 仅 0.34
  • 静态协调结构：未涉及自适应架构切换或递归自我改进

工程启示

不要因为"大家都在用多 agent"就默认加 agent。 这篇论文提供了首个定量框架来回答"要不要加"和"加哪种"：

  1. 先用单 agent 跑你的任务，看基线是否超过 45%
  2. 分析任务是否可分解为并行子任务
  3. 评估工具数量和协调开销的性价比
  4. 参考决策树选择架构，而非跟风"more agents"

论文代码开源在 github.com/ybkim95/agent-scaling，使用 LiteLLM + LangChain 实现，含完整评估框架和 prompt 模板。另有一个独立社区实现：agent-scaling-laws（MIT License）。
