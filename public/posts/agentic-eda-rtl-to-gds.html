Agent 能力的真相：同一模型换层壳，分数差 86 分，Token ROI 差 141 倍

AI 做芯片设计的叙事已经悄悄升级了——从"AI 帮你写 Verilog"变成"AI agent 跑完整条 RTL-to-GDS 流程"。但浙大团队用 24 次商业 EDA 工具实验给了我们一记清醒剂：可靠完成的关键不是模型有多强，也不是塞了多少领域知识，而是 agent 下面的那层执行基础设施。

这篇 arXiv:2607.17528 选了 PicoRV32 RISC-V 核心，在商业 55nm 工艺下设了两个时钟目标（350MHz / 700MHz），用 3 种架构 × 4 个模型跑了完整的综合→布局布线→ECO→签核。结果不只是数字，是三条工程铁律。

核心发现一：FluxEDA 8/8 全通，裸 Claude Code 仅 3/8 完成 ECO

架构综合物理实现ECO分数范围
Claude Code8/87/83/810.00–87.05
CC + EDA Skills8/83/82/811.67–95.97
FluxEDA8/88/88/890.99–98.26

所有架构都能完成逻辑综合（前端任务，接近代码生成），但一到物理实现就迅速分化。FluxEDA 不是更强的模型——它是把 EDA 工具封装成结构化 API 的 execution harness，管理持久 session、设计状态和操作合法性。

最扎眼的数据点：DeepSeek-V4 同一模型，在不同架构下分数从 11.67 跃升到 97.94——差 86.27 分。这是 infrastructure gap，不是 model gap。

核心发现二：塞领域知识可能适得其反——GLM-5.2 涨 83 分，Claude Sonnet 5 跌 75 分

给 Claude Code 加上 EDA Skills（来自 IC Agent Hub 的领域 procedural knowledge），效果极度分化：

模型裸 Claude Code+ EDA SkillsΔ
GLM-5.213.3395.97+82.64 ✅
Claude Sonnet 587.0511.67-75.38 ❌
Kimi K382.3311.67-70.66 ❌

这揭示了一个危险的模式：domain skill injection 的效果是强模型依赖、强任务依赖的。对于某些模型，额外注入的 EDA 知识不是帮助，是 prompt 污染——模型被塞进一堆 Tcl 命令模板和流程建议后，反而偏离了它的有效推理路径。这也意味着"给 agent 加 skills"这种直觉做法需要量化验证，不能想当然。

核心发现三：Tcl 命令兼容性占物理设计失败的 31.7%——FluxEDA 把它归零了

论文将物理设计阶段的错误按类别分解（Figure 3），最大的单一类别出人意料：

架构Tcl 兼容性错误占比
Claude Code + DeepSeek-V448.7%
Claude Code + GLM-5.228.0%
CC + EDA Skills (DeepSeek-V4)10.0%
CC + EDA Skills (GLM-5.2)7.7%
FluxEDA（所有模型）0.0%

这些错误不是 agent "不知道怎么优化时序"，而是 agent 生成了语法正确但对当前工具版本/模式/MMMC 初始化无效的 Tcl 命令，直接炸掉了数小时的 EDA run，还消耗了商业 license。FluxEDA 的 structured wrappers 和 registered APIs 让这类错误不再可能发生。

核心发现四：Token ROI 差 141 倍——便宜 ≠ 高效

论文引入 Token ROI = 归一化 EDA 回报 ÷ (token 消耗 × 执行时间)。两个都得分 13.33 的 run（完成了综合和物理实现，但卡在 ECO）：

  • Claude Code + DeepSeek-V4：$0.11，58.78 min，Token ROI = 12.71
  • CC+EDA Skills + Kimi K3：$29.77，472.13 min，Token ROI = 0.09

差 141.2 倍。同样没完成 ECO，一个高效失败（快速试错后停下来），一个低效失败（反复跑无效 EDA 工具烧时间和钱）。传统的 pass/fail benchmark 会把它们归为同一类"失败"——完全抹杀这个差异。

对 Agent 基础设施的工程启示

1. Execution harness 是第一要素，不是加分项

FluxEDA 的设计——managed gateway、persistent sessions、registered actions、structured observations——不是 EDA 特化。这套抽象（能力注册 → 合法性校验 → 状态管理 → 结构化反馈）是任何 long-horizon tool-interactive agent 的通用需求。你的 agent 跑不通不是因为模型不够好，是因为下层没有管住"哪些操作是合法的"。

2. 过程级评估替代最终 QoR 评估

Gated scoring = 不完成前面阶段，后面就算零分。Token ROI = 把进度和成本放在同一个分数里。这两条规则一起避免了 benchmark 中最常见的作弊：agent 只做简单的前几步，拿 partial credit，然后被标记为"部分可用"。

3. Domain knowledge injection 需要量化验证，不能想当然

EDA Skills 在 GLM-5.2 上逆天改命（+83），在 Claude Sonnet 5 上毁灭性打击（-75）。如果你在做 domain-specific agent，加 skills 前后都要跑完整的 benchmark——不要假设"更多知识 = 更好结果"。prompt engineering 的负迁移风险在 agent 场景下被剧烈放大。

局限与诚实标注

  • 单设计单工艺（论文自认）：PicoRV32 + 55nm 不覆盖大规模 SoC 和先进工艺。论文明确说结果应理解为"workflow behavior evidence"，不是 universal ranking。
  • 单次 run（论文自认）：每个配置只跑一次，无法评估 agent 稳定性方差。
  • FluxEDA 代码不可获取（我的观察）：FluxEDA 的 arXiv:2603.25243 也是 preprint，无公开仓库。复现性受限。
  • Session 长度未报告（我的推断）：只知道 token cost 和 wall time，不知道 agent 实际做了多少次 action。如果要复现 Token ROI，需要更细粒度的 trace。
  • Gate 机制双刃剑（我的推断）：不完成 = 零分的规则防止了 partial credit 作弊，但也可能低估了"前两个阶段完美、卡在 ECO"的 agent 的相对能力。

一句话

Agent 的能力不是模型属性，是系统属性。FluxEDA 用 24 次商业 EDA 实验证明：一个管理工具状态和操作合法性的 execution harness，比换更强的模型或塞更多的领域知识更能决定 agent 能否走完整条芯片设计流程。
