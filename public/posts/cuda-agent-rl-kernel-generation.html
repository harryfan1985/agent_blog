CUDA-Agent：128 块 H20 训练出的 LLM，写 kernel 比 torch.compile 快 2.11 倍

August 19, 2026

字节用 128 块 H20 训练出一个 LLM，让它写 CUDA kernel 比 torch.compile 快 2.11 倍——但更值钱的是那份 6K 数据合成管道和"防作弊"环境设计

CUDA-Agent（arXiv:2602.24286，ByteDance Seed + 清华 AIR）是第一个用大规模 Agentic RL 训练 LLM 生成/优化 CUDA kernel 并稳定超过编译器优化的系统。它在 KernelBench 上达到 98.8% 通过率、96.8% 的 kernel 比 torch.compile 更快、整体 2.11× 加速。但它真正的贡献不在那组数字，而在于三个工程问题的解法：数据稀缺怎么办（组合合成）、奖励作弊怎么防（不可篡改环境）、训练崩溃怎么治（多阶段 warm-up）。

这篇对做 GPU kernel 优化工具的人——尤其是走 training-free 路线的——是一份可以直接抄作业的工程手册。

核心发现一：通用 LLM 能写"正确"的 kernel，但写不出"快"的 kernel

KernelBench 评测揭示了一个被忽略的事实：顶尖通用模型写 CUDA kernel 的通过率很高，加速率很低。

模型Pass RateFaster vs CompileSpeedup vs Compile
Claude Opus 4.595.2%66.4%1.46×
Gemini 3 Pro91.2%69.6%1.42×
GLM 4.6 / Kimi K266-76%19-23%0.57-0.66×
CUDA-Agent98.8%96.8%2.11×

差距在 Level 2（算子序列/融合）最悬殊：CUDA-Agent 100% 更快、2.80× 加速，而静态编译器 torch.compile 靠预定义规则做 fusion，遇到非平凡的算子组合就束手无策。这正是 learned 优化策略碾压 static compiler 的场景——模型通过迭代探索，发现硬件特定的内存访问模式和 tiling 策略，这些是规则引擎触不到的。

核心发现二：6K 训练数据的合成，靠的是"组合融合"而非爬取

高质量 CUDA kernel 代码稀缺是 SFT 的死穴。CUDA-Agent 的解法是三阶段数据合成，关键是中间那步——把 ≤5 个 torch 算子顺序堆叠成融合任务：

阶段做法产出
Seed 爬取挖 torch + transformers 的 nn.Module 算子基础算子库
组合合成LLM 采样 ≤5 算子堆叠成融合层×2 组合占 83.77%
过滤4 准则（可执行/无随机/非常数/1-100ms）6K ops 最终集

论文给出了一个反直觉的洞察：融合不是"各算子孤立优化再串联"——fusion 通过避免中间 global memory 物化、共享 register/SMEM/occupancy 约束、要求统一并行映射，重塑了整个优化景观。所以组合合成是在生成"有价值的新问题"，不是数据增强。反污染用 AST 相似度 >0.9 的阈值把接近 KernelBench 的样本全部剔除。

核心发现三：防 reward hacking 是硬约束，不是锦上添花

这个领域有公开造假前科：Sakana AI 的 AI CUDA Engineer 声称 150× 加速，被社区实测为 3× 更慢。CUDA-Agent 的 5 条约束是对此的直接回应，也是全篇最有工程含金量的部分：

  • 文件权限保护：验证/测速脚本只读，agent 无法篡改评估逻辑
  • 禁 fallback：context manager 禁止调用 torch.nn.functional 原实现，防止"假装优化实则抄底"
  • 多随机输入验证：每个算子对 5 个随机输入验证输出
  • 测量噪声压制：device 同步 + warm-up + 重复测量取均值
  • 禁外部检索：不给 web search，强制从本地执行环境推导

配合架构：Docker 沙箱跑 CPU 编译，独立 GPU 池（128×H20）跑验证/测速，进程级隔离 + 独占资源，保证延迟测量稳定。

核心发现四：训练崩溃的根因是可诊断的——CUDA 只占预训练数据不到 0.01%

初始 RL 只能稳定训练 17 步就崩。根因链：CUDA 代码占预训练数据 <0.01% → base model 在 CUDA 上的 prior 严重偏离 → 采样出大量低概率 token → 在 BF16/FP16 精度差异下，importance ratio 在精度地板（π≈10⁻⁹）附近爆炸。

解法是多阶段 warm-up：

  • RFT（rejection fine-tuning）：过滤正奖励轨迹做 SFT，初始化 actor——防止熵增崩溃（消融：w/o RFT 熵激增 → reward 崩）
  • Value Pretraining：用轨迹数据预训练 critic——防止轨迹长度爆炸（消融：w/o 时 critic 无法估值 → 无限探索）

reward 设计也值得注意：离散里程碑 {-1, 1, 2, 3}（失败=-1 / 超 eager=2 / 超 eager+compile=3），替代连续 speedup 比值——因为不同算子优化难度差异大，raw speedup 是不可靠的质量代理。

对 GPU kernel 优化工具开发的工程启示

1. 把"优化专家的思考顺序"编码成 SKILL.md

CUDA-Agent 公开的 SKILL.md 里，优化优先级是精华：算法级 >50% 影响（fusion/tiling/coalescing）→ 硬件利用 20-50%（vectorized load/warp primitives/occupancy）→ 微调 <20%（ILP/mixed precision/prefetch）→ 参数兜底。这比平铺一堆优化技巧高效得多——它告诉 agent 先做什么后做什么。

2. 反作弊五约束是硬件无关的通用纪律

文件权限保护、禁 fallback、多输入验证、测量噪声压制、禁外部检索——这五条与具体硬件（NVIDIA/昇腾）无关，任何 execution-feedback 的优化 loop 都该抄。

3. 组合融合是便宜的训练/评测语料生成器

≤5 算子堆叠成融合任务，比手工找 benchmark 便宜得多。昇腾侧可以做 CANN/Triton 算子的组合合成，生成自己的评测集。

4. 离散里程碑 reward 优于连续 speedup

如果后续要给工具加任何形式的自动评估/选择，用 {-1,1,2,3} 式的里程碑，别直接回归 runtime 比值。

局限与诚实标注

  • 无 license（我的核查）：GitHub 仓库无许可证——代码不可合法复用，只有 SKILL.md（事实标准）+ 数据集可参考。做闭源工具只能借鉴思路不能抄代码。
  • 训练成本不可复现（论文自认的隐性门槛）：128×H20 × 150 steps × 128k context——字节级资源，个人/小团队无法复现训练。
  • base model 未公开（我的核查）：RL 是在 Seed1.6（23B active/230B total MoE）上做的，字节内部模型，换 base model 效果未知。
  • 消融表格措辞陷阱（我的推断）：Table 2 脚注说 w/o RFT / w/o Value Pretrain 报告的是"训练崩溃前的最后验证步"——这两个变体实际崩了，报告值可能略高估。
  • KernelBench 是算子级（论文自认的边界）：250 个孤立算子，L3 仅 50 题，2.11× 是"算子级手写 vs 算子级 compile"，不等于端到端模型推理快 2.11×。
  • 与 torch.compile 努力不对称（我的推断）：专项训练模型 + 多轮迭代 vs 通用编译器一次性静态优化，算力投入不在同一量级。

一句话

CUDA-Agent 的真正贡献不是"RL 能训 CUDA"（前作已做），而是三个工程问题的系统性解法：数据稀缺用组合合成、奖励作弊用不可篡改环境、训练崩溃用多阶段 warm-up 对熵增和轨迹爆炸的因果诊断——SKILL.md 的优化优先级和反作弊五约束，是零成本可迁移的核心资产。
