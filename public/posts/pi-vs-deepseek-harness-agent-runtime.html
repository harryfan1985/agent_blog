Pi 与 DeepSeek Harness：编码 Agent 运行时的两条架构路线

August 18, 2026

两个开源编码 Agent 运行时，两种几乎相反的架构哲学

Pi（pi-mono）和 DeepSeek Harness（dsh）解决的是同一个问题：让 LLM 在循环里调用工具、管理对话状态、可被扩展。但读一遍两者的源码会发现，它们的架构哲学几乎相反——Pi 是一个「带扩展系统的单体库」，dsh 是一个「纯插件组合的 harness」。本文从分层、运行循环、状态模型、工具执行、扩展机制五个维度做一次对比。

一、分层对齐：Pi 的三层 vs dsh 的插件树

先纠正一个常见误读。Pi 不是只有一个 pi-agent-core 内核库，它的完整形态是三层：

Pi 分层对应 dsh职责
@earendil-works/pi-aillm/llm + 各 adapterprovider 抽象、模型目录、流式
@earendil-works/pi-agent-corecore/agent-loop + core/agent运行循环、工具调度、状态
@earendil-works/pi-coding-agentapps + bundles + core/session + tool/compaction 插件CLI、会话持久化、内置工具、扩展系统

所以正确的问题不是「Pi 是库、dsh 是框架」，而是「Pi 的 coding-agent 层 vs dsh 的 harness 层」。

二、Pi agent-core：纯内存的运行时内核

pi-agent-core 刻意保持无 IO、无持久化：Agent 只负责「一段对话的运行循环」，会话怎么存、工具怎么落盘都交给上层。

2.1 核心循环是双层结构

真正干活的是 runLoop，它是一个双层循环：外层 while(true) 处理 follow-up 队列（只在 agent 本来要停止时才 poll）；内层 while(hasMoreToolCalls || pendingMessages) 驱动一个 turn——一次 LLM 调用加上它引发的工具执行。

单个 turn 的顺序：注入 pending 消息 → 流式产出 assistant 消息 → 若 stopReason 为 error/aborted 则直接结束 → 提取 toolCall 并执行 → turn_end → prepareNextTurn（可替换下一轮的 context/model）→ shouldStopAfterTurn（优雅停止）→ poll steering 队列。

两个值得注意的细节：

  • length 截断不执行工具：输出被 token 上限截断时，流式 tool-call 参数可能被 JSON salvage parser 解析出「合法但不完整」的结果，全部标记为错误而不是执行，让模型重新发。
  • streamFn 契约：流函数不允许 throw，请求/模型/运行时错误必须编码进返回流（stopReason: "error"/"aborted" + errorMessage）。

2.2 消息管道只在 LLM 边界做转换

Agent 内部用 AgentMessage 工作，只有在 LLM 调用边界才转成 provider 的 Message：

AgentMessage[] → transformContext() → convertToLlm() → Message[] → LLM

AgentMessage 通过 TypeScript 声明合并支持自定义消息类型（bashExecution、compactionSummary 等），convertToLlm 负责过滤 UI-only 消息、把自定义类型转成 LLM 格式。

2.3 工具执行：preflight + before/after hook + terminate

工具调用先经过 prepareToolCall（查 tool → prepareArguments → validateToolArguments → beforeToolCall），返回「可执行」或「立即错误/被阻止」。执行支持 sequential/parallel 两种模式：parallel 先顺序 preflight 全部调用，再并发执行，tool_execution_end 按完成顺序发出，但 toolResult 消息按 assistant 源顺序写入。terminate: true 只有在整批所有结果都设置时才提前停止。

三、Pi 的完整形态：coding-agent 产品层

pi-coding-agent 才是 Pi 对外发布的产品。它的 AgentSession 把 agent-core 包装成完整产品：会话持久化、compaction、自动 retry、bash 执行、会话切换与分支（fork / navigateTree）。

更关键的是它有一套扩展系统（ExtensionAPI）：on(event) 订阅生命周期事件、registerTool、registerCommand、registerShortcut、registerFlag、registerProvider。表面看和 dsh 的 Cordis 插件几乎同构。

但有一个决定性的事实：Pi 是两层扩展机制叠加。agent-core 层只有回调（beforeToolCall、afterToolCall、transformContext），coding-agent 层的 ExtensionRunner 把这些扩展事件桥接到回调上：

this.agent.beforeToolCall = async ({ toolCall, args }) => {
  return await runner.emitToolCall({ type: "tool_call", ... }); // 扩展事件 → 内核回调
};

所以 Pi 的扩展本质是「给一个固定内核打补丁」：扩展能拦截工具调用、改写消息、注册工具/命令，但不能替换内核本身——agent loop、会话存储、工具调度器都是 coding-agent 内建、不可替换的。

四、三个本质差异

4.1 库 + 回调 vs 插件 + 事件

Pi 的 Agent 是一个自包含类，扩展点是构造时传入的回调。dsh 里连 agent loop 本身都是插件，扩展点是 Cordis 的类型化事件，有五种分发语义：emit（同步通知）、parallel（并行等待）、serial（顺序短路）、bail（同步短路）、waterfall（next() 委托）。这是「枚举扩展点」与「开放扩展面」的差别。

4.2 内存态 vs 事件溯源

这是最核心的架构差异。Pi 的核心 Agent 是纯内存：_state.messages 数组就是对话真相，事件监听是副作用的出口。dsh 反过来：Session 是 append-only 的 SessionEvent 日志，有一个硬不变量——「模型可见即已入日志」（Model-visible means logged）：每次请求的 messages 通过 deriveMessages() 从日志投影得出，连 inbox 队列都是 durable 事件的增量投影。

这个差异在 coding-agent 层依然成立：Pi 的 SessionManager 持久化是副作用式的——订阅 agent 事件，在 message_end 时顺带 appendMessage；而 dsh 的 driver 每产生一个事件就直接写 log，log 是循环的输入和输出，不是副产物。

4.3 扁平 turn vs turn/step 双层

Pi 的 turn = 一次 LLM 调用 + 工具执行，没有 step 概念。dsh 把层级拆开：step = 一次模型请求 + 它请求的工具调用（持久化 step/start/step/end），turn = 0 或多个 step，在第一个输入被 claim 前打开，直到「无所欠」才闭合。这意味着 dsh 能在 step 边界注入 steering，而 Pi 只能在一个完整 turn 结束后注入；dsh 的 turn 甚至可以「零 step」——输入被 agent/pre-step 拒绝时仍记录一个 turn，保证失败的尝试也可追溯。

五、扩展系统分发语义：pipe vs around

两者表面都叫「事件」，但分发模型有本质区别。

5.1 Pi 的 6 种分发模式

Pi 的 ExtensionRunner 用 11 个 emitXxx 方法写死了 6 种语义：

模式事件规则
通知agent_start、turn_end、tool_execution_* 等全执行，返回值忽略，错误独立捕获
短路tool_call、user_bash、input(handled)first-wins：第一个 block/handled 立即返回
链式message_end、context、before_provider_requestlast-wins：上一个 handler 的输出是下一个的输入
字段合并tool_resultcontent/details/isError/usage 逐字段覆盖
就地 mutatebefore_provider_headershandler 直接改对象，返回值忽略
累积resources_discover、before_agent_start(messages)所有 handler 的结果 push 进数组

Pi 的「链式」本质是单向 fold：input → handler1 → handler2 → handler3 → output。handler 只能在进入时变换数据，看不到下游最终结果，也无法阻止下游执行（除非事件本身声明了短路规则）。

5.2 dsh 的 5 种分发模式

dsh 的模式是统一的，按 ctx 上的分发方法区分，不按事件写死。源码里的 DispatchMode 共 5 种（注：官方 cordis-primer.md 的 Dispatch Modes 表格只列了面向插件作者的 4 种——emit/waterfall/parallel/serial，省略了主要用于框架内部事件与同步短路场景的 bail）：

模式语义事件示例
emit同步 fire-and-forget，不 await，返回的 promise 被丢弃，返回值忽略agent/status、agent/error
parallel所有监听器并行执行并 await 全部 settle，无返回值；任一 reject 抛 AggregateErrorsession/flush
serial顺序 await，直到返回 bail 值（非 null/false/undefined），返回第一个 bail 值agent/turn-stopping
bail与 serial 同语义，但同步执行（不 await），第一个 bail 值赢slash/input-begin-command
waterfallaround-middleware，监听器必须调 next() 才委托，返回值从最外层冒出agent/pre-step、agent/request、agent/request-error

其中 serial 与 bail 的差别只在「是否 await 监听器返回值」，parallel 与 emit 的差别在「是否等待并聚合错误」。waterfall 的监听器有四种选择，这是 Pi 完全没有的：

// 1. 短路：不调 next，下游全部不执行
if (shouldBlock) return { kind: 'reject' }
// 2. 透传：调 next，原样返回
return next()
// 3. 改写下游结果：调 next 拿结果，修改后返回（后置处理）
const result = await next()
return { ...result, messages: [...result.messages, extra] }
// 4. 前置处理：先改 payload，再调 next
payload.messages.push(extra)
return next()

5.3 本质差别：pipe vs around（洋葱）

Pi 的链式是单向管线，dsh 的 waterfall 是洋葱模型：handler1 { handler2 { handler3 { next() } } }——handler3 先执行，结果逐层往外冒泡，每层都能在 next() 返回后做后置处理。

这带来能力上限的差异。dsh 的 agent/request-error 能实现「重试」这种跨层控制：监听器发现失败、执行恢复、返回 {kind:'retry'}。这在 Pi 的 pipe 模型里无法表达，因为 pipe 里下游已经跑完了。

一个具体对照：Pi 要拦截 provider 请求，只能用三个分离的事件（before_provider_request 改 payload、context 改 messages、before_provider_headers 改 header）模拟出 dsh 一个 agent/request waterfall 的能力。Pi 把「一个拦截点」拆成按数据位置命名的多个事件，每个有独立语义；dsh 把「一个拦截点」保持为一个 waterfall，语义由监听器通过 next() 决定。

六、结论

  • Pi 的优势是简单、可嵌入、心智负担小：一个类 + 几个回调就能跑起来，适合作为编码 agent 的运行时内核。代价是扩展是「纵向拦截」——只能在固定的生命周期点做 before/after 拦截和注册。
  • dsh 的优势是可组合、可持久、可恢复：插件化让 model adapter、tool registry、session log、agent loop 全部可替换，事件溯源让 fork/resume/replay/telemetry 共享一套真相。代价是心智负担和依赖复杂度都高。

两者不是竞品，而是不同抽象层级：Pi 是「agent 运行时内核 + 带扩展系统的单体产品」，dsh 是「agent harness 平台」。它们各自的核心设计决策——内存态 vs 事件溯源、回调 vs 事件、扁平 turn vs turn/step 双层、pipe vs around——都是不可调换的根基。选择哪条路线，取决于你要的是一个能塞进自己程序的内核，还是一个能横向替换任何能力的平台。

分析范围与说明

  • 本文基于对两个仓库源码的直接阅读：pi-mono 的 packages/agent 与 packages/coding-agent，以及 deepseek-harness 的 packages/core/agent、core/agent-loop、core/session、core/tools。
  • 两个项目都在快速迭代，本文结论反映的是阅读时的代码状态，不构成对任一项目完整性的评判。
  • 一个值得注意的交叉点：dsh 的 workspace 配置将 @earendil-works/pi-ai 作为可选 LLM API backend 引入——两者在 provider 抽象层存在真实交集。
