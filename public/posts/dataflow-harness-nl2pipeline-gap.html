DataFlow-Harness：给 Agent 套上 Harness，成本降 72.5% 产出可编辑 DAG

July 30, 2026

93.3% 端到端通过率，成本降低 72.5%——不是一个更好的 Agent，而是一个更聪明的 Harness

LLM coding agent 能帮你写数据处理脚本，但产出的是一堆 .py 文件——用完即弃，无法在平台上可视化为 DAG、无法增量编辑、无法审计。北大和上海 IAAR 的团队把这个问题定义为 NL2Pipeline gap：用户用自然语言表达 workflow 需求，但生产环境需要的是持久、可编辑、可治理的 platform-native pipeline 工件。

他们的答案不是「做一个更强的 agent」，而是 给 agent 套上一个 harness——限制其只能通过 typed mutation 操作平台 DAG，并注入领域 procedural knowledge。结果？93.3% 的端到端通过率（与最强代码生成 baseline 差距仅 0.9pp），但成本降低 72.5%，延迟降低 49.9%。

核心机制：四个组件构成的 Harness

DataFlow-Harness 的架构围绕一个核心原则：agent 不再直接写代码，而是通过 MCP tool call 对 pipeline DAG 发出 typed mutation。每次 mutation 必须通过两层验证才生效。

四个组件：

  1. Data Pipeline Backend：以五元组 P = (D, O, E, S, R) 建模 pipeline（数据源、operator 实例、有向边、schema 状态、运行时状态），是所有接口的单一真相源
  2. MCP Tools Layer：暴露 live operator registry + 当前 pipeline 状态，agent 通过 MCP tool call 发出 typed mutation，经 DAG acyclicity + schema compatibility 验证后才 commit
  3. DataFlow-Skills：注入领域 procedural knowledge——先做 schema 推断→再选 operator→再配参数→再验证 serving，以及 operator 兼容性规则（modality matching、field-flow conventions）
  4. DataFlow-WebUI：对话界面 + 可视化 DAG 编辑器，WebSocket 双向同步

关键设计决策：Validation 发生在 mutation 层，而不是最终产物层。这意味着 agent 每次尝试修改 pipeline 都会立即知道结果，不需要等整个 script 跑完才发现 DAG 有环。

数据：四个 Baseline 的梯度对比

实验设计很干净——四种配置形成从「自由编码」到「完全 harnessed」的梯度：

Method产物类型E2E PassCost ($)Latency (s)
Vanilla CCScript91.7%0.950190.7

MCP-only 的 83.3% 是整个实验中最有价值的数据点。它说明：只给 tool 接口不给 procedural knowledge，agent 在受限空间中反而挣扎。从自由编码（Vanilla CC 91.7%）到 DAG 约束（MCP-only 83.3%），通过率反而掉了 8.4pp。这是一个干净的 NL2Pipeline gap 量化——受约束的 agent 比自由的 agent 更难成功，除非给它足够的 scaffolding。

DataFlow-Harness 的 93.3% 说明 Skills 填补了这个 gap。而且它还比 Context-Aware CC 便宜 42.8%、快 17.6%。

Skills 到底在哪类任务上有用？

Ablation 实验把 12 个 task 分成三组（每组 10 次试验），揭示了一个清晰的模式：

任务组MCP-onlyDataFlow-Harness收益
过程知识依赖（QA basic/filter/chain）18/3029/30+36.7%
简单路由（field rename, filter）40/4040/400
非合成瓶颈（multi-field scoring）14/2014/200

Skills 的价值集中在「需要隐性领域知识」的场景——那些从 operator 描述中无法推断具体怎么组合的任务。对于简单路由（field rename），工具描述本身就足够，Skills 只是冗余。对于 multi-field scoring（失败受限于模型推理本身而非 pipeline 构造），Skills 也无能为力。

这个分层结果是 paper 最有工程价值的部分：它告诉你 procedural knowledge injection 的适用范围——不是 silver bullet，而是在「构筑知识密集但推理浅层」的任务上最有效。

对 Agent 基础设施的工程启示

1. Harness 设计：操作空间压缩比模型升级更高效

DataFlow-Harness 的核心效率来自操作空间压缩——agent 不再面对无限 token 空间（Python 代码），而是有限 operator 组合空间。Context-Aware CC 和 DataFlow-Harness 用的是同一个模型（Claude Opus 4.7），但 token 消耗差了 2.5 倍。如果目标是降低推理成本，限制 agent 的操作空间比换更强的模型更值得先尝试。

2. MCP 工具暴露 ≠ 平台 grounding

MCP-only 配置效果最差（83.3%），说明暴露工具元数据（名称、参数、描述）不等于平台 grounding。真正的 grounding 需要：(a) agent 看到的 operator 是 live registry 而非静态列表；(b) agent 的操作受平台约束（typed mutation + validation）；(c) agent 有 procedural knowledge（Skills）指导「怎么组合」而非「有什么可用」。

3. Skills 是一种可复用的 Harness 组件

DataFlow-Skills 的设计（procedural blueprints + compositional constraints）是一种可以跨领域迁移的模式。不管是 data pipeline、code review pipeline 还是 agent evaluation pipeline，只要领域有「隐性过程知识」，就可以用同样的方式编码为 Skills。这种 Skills ≠ prompts——它们是结构化的、可版本管理的、平台绑定的配置。

局限与诚实标注

  • 单一模型家族（论文自认）：只测了 Claude Opus 4.7。其他模型（GPT、Gemini、DeepSeek）在受限操作空间中的表现未知。
  • Benchmark 不可迁移（论文自认）：12-task benchmark 是 DataFlow 平台定制的，不能直接推广到其他数据工程平台。
  • Schema validation ≠ 语义正确（论文自认）：DAG acyclicity + schema compatibility 只能保证 pipeline 结构合法，不保证产出的数据有用。语义正确性只有下游训练效用间接衡量。
  • 下游实验样本不足（论文自认）：RQ4 两个 case study，不是独立重复实验。作者明确说「不应解释为一般因果估计」。
  • Skills 创作成本未讨论（我的推断）：谁写 Skills、怎么维护、跨领域迁移需要多少改写——paper 完全没有涉及。但如果 Skills 是 Harness 的核心组件，这个创作成本决定了系统的可推广性。
  • Skills 可能降低灵活性（实验证据暗示）：Table 3 中 task 2b 上 MCP-only 10/10 vs Harness 9/10，论文解释为「prescriptive procedures may reduce flexibility when multiple execution strategies are valid」。Skills 的过度约束是一个真实风险。

一句话

DataFlow-Harness 不是让 agent 更强，而是让它更受控——用 typed mutation + procedural knowledge 把 agent 从「自由编码」拉到「平台约束」，在降低 72.5% 成本的同时产出持久可编辑的 DAG。如果 Harness Engineering 需要一个干净的、可量化的案例，这就是。
