10 种搜索算法 + LFBO + LLM 混合 + AOT：Helion Autotuning 全栈拆解

Helion 的核心卖点不是"15 行代码写 kernel"——而是其 autotuner。源码显示，Helion 注册了 10 种搜索算法、5 种缓存策略、3 级 effort profile、AOT 离线编译系统和 LLM-guided 搜索。默认算法是 LFBO（Random Forest 代理 + Pattern Search），full 模式实际运行 LLM-Seeded LFBO 两阶段混合。本文从源码逆向分析 Helion autotuner 的完整技术栈。

核心算法 1：LFBO（Learned Function By Optimization）

LFBO 是 Helion 的默认算法，源码在 surrogate_pattern_search.py（40K）。核心是 Random Forest 二分类代理 + Pattern Search 局部精炼。

算法流程

  1. 生成初始种群（100 个 random configs）
  2. Benchmark 初始种群 → 获得性能数据
  3. 训练 Random Forest 分类器：
    • 特征：config 编码（block_sizes, num_warps, num_stages, indexing, ...）
    • 标签：性能 < quantile(0.15) → "good"(1)，否则 "bad"(0)
    • 样本权重：好 config 权重 ∝ (quantile - perf)，坏 config 权重=1
  4. 对每个 generation（最多 20 代）：
    • 从 top-5（copies=5）当前最佳 config 生成邻居
    • 用代理模型预测邻居的 "good" 概率
    • 只 benchmark 概率最高的邻居
    • 用新结果全量重训代理模型（非增量）
  5. 返回最佳 config

关键设计决策

1. 分类而非回归：代理模型不预测"这个 config 跑多快"，而是预测"这个 config 是否比 85% 的其他 config 快"——二分类。原因：在搜索空间中，绝大多数 config 是差的，二分类比回归更容易区分好坏。加权分类进一步强调接近最优的 config。

2. 全量重训：每代用所有观测数据重新训练 Random Forest（RandomForestClassifier(criterion="log_loss", n_estimators=100, n_jobs=-1)），而非增量更新。100 棵树并行训练。全量重训避免偏差累积——代价是计算开销，但 RF 训练相对于 kernel 编译是微不足道的。

3. 代理模型特征空间：encode_config() 将 config 展平为浮点向量。block_sizes 编码为 [64.0, 64.0, 32.0]，indexing 编码为 one-hot [1, 0]。当前特征空间不包含任何编译器诊断信息——没有寄存器使用量、shared memory 占用、PTX 指令数。这是最大的机会点。

4. Pattern Search 邻域：LFBO 的搜索不是全局的，而是从 top-5 config 出发做单参数扰动（改一个维度 ±1 step）。代理模型过滤邻居——只 benchmark 预测概率最高的。这是局部搜索 + 代理过滤的组合。

核心算法 2：LLM-Guided Search

源码在 llm_search.py（28K）+ llm/ 子目录（prompting 15K + feedback 7K + transport 29K + workload 15K + configs 6K）。

算法流程

  1. Round 0：构建 prompt（kernel 源码 + tensor 形状 + GPU 硬件 + config space）→ 异步发起 LLM 请求 → 同时 benchmark default + 10 个 random seed
  2. LLM 返回 15 个 config → benchmark 新 config
  3. Round 1-N（最多 4 轮）：选 top configs → rebenchmark 稳定化 → 构建 refinement prompt → LLM 返回 15 个新 config → benchmark
  4. Early stop：连续 2 轮无改善 → 停止
  5. 返回 rebenchmarked 最佳 config

关键设计决策

1. 异步 Round 0：LLM 请求与 seed benchmark 并行——不浪费时间等待 LLM 响应。Round 0 的 LLM 请求和 10 个 random config 的 benchmark 同时进行。

2. Rebenchmark 稳定化：每轮先重新 benchmark top configs，再发给 LLM。LLM 看到的是稳定数字而非一次性噪声。rebenchmark_threshold=1.5（full 模式）——只有性能差异 > 1.5× 的 config 才重新 benchmark。

3. 上下文窗口管理：_MAX_CONTEXT_ROUNDS = 3——只保留最近 3 轮对话历史，避免超出 LLM context limit。

4. Default LLM model: gpt-5-2（DEFAULT_LLM_MODEL = "gpt-5-2"）。Transport 层（29K）支持 OpenAI Responses API、Anthropic Messages API、兼容代理——通过 HTTP 直连，无额外依赖。

5. LLM prompt 信息量（从 workload.py 分析）：

信息是否包含
Kernel 源码（inspect.getsource()）✅
Input tensor shapes + dtypes✅
GPU 硬件（device name + SM 数 + total memory + max threads/SM）✅
Config space（所有可调参数 + 范围）✅
Benchmark 结果（top configs + 性能 + 失败数）✅
编译器诊断（寄存器/shared memory/失败原因）❌
Kernel 结构分析（reduction 类型、co-residency、matmul fact）❌

核心算法 3：LLM-Seeded LFBO（两阶段混合）

这是 full effort 的实际运行路径——LLMSeededLFBOTreeSearch（源码 llm_seeded_lfbo.py）。

阶段算法作用
Stage 1LLMGuidedSearch (1 round)LLM 提议 15 个 config → benchmark → 取最佳作为种子
Stage 2LFBOTreeSearch (20 gen)从 LLM 种子 + 缓存 config 启动 → RF 代理 + pattern search 精炼

设计逻辑：LLM 擅长全局探索（识别有希望的 config 族），LFBO 擅长局部精炼（微调参数）。两阶段混合利用各自优势。

关键细节：Stage 2 强制 FROM_BEST_AVAILABLE，注入 LLM 最佳 config——不是冷启动，而是从 LLM 种子开始局部搜索。如果 Stage 2 算法支持 best-available seeding（PatternSearch 和 DifferentialEvolutionSearch 都支持），则注入。

核心算法 4：DE-Surrogate Hybrid

差分进化 + Random Forest 回归代理（源码 de_surrogate_hybrid.py 13K）。与 LFBO 的关键差异：

维度LFBODE-Surrogate
搜索策略Pattern Search（单参数扰动）差分进化（多参数交叉变异）
代理模型RandomForestClassifier（二分类）RandomForestRegressor（回归）
代理用途过滤邻居（good/bad）从 3× 候选中选最优
代理激活时机立即100 次评估后
Refit 频率每代每 5 代
变异策略±1 step 扰动mutant = a + F*(b-c)

DE 变异（differential_mutation）：从种群随机选 3 个个体 a, b, c → mutant = a + F * (b - c)，crossover_rate=0.8 控制每个维度是否接受变异。生成 3× 候选，用代理模型预测性能，只 benchmark 预测最优的。

AOT Autotuning：离线编译 + Heuristic Dispatcher

这是 Helion 最独特的功能——将 autotune 结果编译为独立 .py 文件，运行时零 Helion 依赖。

流程

  1. 对多个 shape 运行 full autotune
  2. 收集 (shape, config, timing) 数据
  3. 训练 heuristic 模型（决策树或最近邻）
  4. 生成独立 Python 文件：
    • Triton kernel 代码（内联）
    • heuristic dispatcher（shape → config）
    • 零 Helion/Triton 依赖（运行时只需 torch + triton）

Heuristic Generator 关键设计

参数值说明
goal_typemax_slowdown允许的最大性能损失
threshold1.110% 性能损失容忍
min_configs1最少 1 个 config（全 shape 共享）
max_configs10最多 10 个 config
backenddecision_tree / nearest_neighbor两种后端
feature_selectionTrue自动剪枝冗余 shape 特征

输出人类可读的 Python 代码——可审查、可手动调整。其他 DSL（Triton/TileLang/CuTe）没有 AOT 系统，这是 Helion 的差异化壁垒。

缓存系统：Best-of-K + 跨运行复用

LooseAutotuneCacheKey：key 包含 kernel name + shape hash + device info。best_of_k 用不同随机种子跑 K 次 autotune，取最佳。K=1 时 hash 与历史格式字节一致（向后兼容）。

FROM_BEST_AVAILABLE 策略：从缓存目录加载最多 20 个历史最佳 config，按 shape 相似度排序，用缓存 config 作为初始种群——quick 模式的默认策略，10× 加速。

搜索空间规模

一个 3D matmul kernel 的搜索空间约为：

维度候选数
block_sizes (3D, each power-of-2)5×5×5 = 125
loop_orders (3D permutation)6
num_warps5
num_stages5
indexing3
pid_type3
l2_groupings4
其他 toggle × per-dim~50
总组合~2,000,000+

LFBO 代理模型的作用就是在这个空间中用 ~500-1000 次评估找到 top 配置——搜索效率约 0.025%-0.05%。

七个关键洞察

1. LFBO 是核心创新

Random Forest 二分类代理 + pattern search 局部精炼。不预测性能值，而是预测"是否比 15% 分位数好"——分类比回归更容易训练。全量重训避免偏差累积。搜索效率 ~0.025%。

2. LLM 不是噱头——是真实生产路径

full effort 的默认路径是 LLMSeededLFBOTreeSearch（LLM 种子→LFBO 精炼）。LLM 做 global exploration（识别 config 族），LFBO 做 local refinement（微调参数）。transport.py 29K 支持 OpenAI/Anthropic/代理三种 provider，默认 gpt-5-2。

3. AOT 是差异化壁垒

其他 DSL 没有 AOT 系统。Helion 的 heuristic_generator.py 训练决策树/最近邻模型，生成独立 Python 文件——运行时零依赖。这是生产部署的关键能力，也是从研究到生产的桥梁。

4. Best-of-K + FROM_BEST_AVAILABLE 是加速关键

quick 模式从缓存加载历史最佳 config 作为种子，rebenchmark_threshold=0.9 禁用二次验证——10× 加速。这不是算法创新而是工程优化，但效果显著。

5. 代理模型特征空间是最大机会点

当前 LFBO 的 train_x 只包含 config 编码（block_sizes, num_warps 等）。加入编译器诊断（寄存器、shared memory、PTX 指令数）可以显著提升代理模型预测精度——这是前文分析的 #19。

6. 搜索空间不感知硬件

ConfigSpec 的候选值是预设的 power-of-2。_hardware.py 只有 4 个字段。SM 数、寄存器数、shared memory 大小都在 _compat.py 但不被 ConfigSpec 用于推导搜索范围——搜索空间是硬件无关的静态枚举。

7. 编译失败处理粗糙

PopulationMember.status 只有 6 值枚举（ok/error/timeout/peer_compilation_fail/filtered/unknown）。logger.py 识别了 15 种具体错误（shared_memory_oom、register_pressure、tensor_numel_exceeded 等）但只用于日志分类。autotuner 把所有失败等同处理——perf=inf，代理模型把失败和慢等同。

局限与诚实标注

  • 性能数据来源（我的推断）：搜索效率 ~0.025% 基于搜索空间 2M+ 和评估 500-1000 次的估算，实际评估次数取决于 kernel 复杂度和 effort 级别。
  • 默认算法推断（我的推断）：代码中 default_autotuner_fn() 返回 LFBOTreeSearch，但 full profile 配置了所有算法参数。实际运行路径可能是 LLMSeededLFBOTreeSearch——取决于环境变量和 Settings 配置。
  • LLM transport 29K（源码特征）：支持三种 provider 但未验证实际可用性。gpt-5-2 是默认模型但可能需要用户配置 API key。
  • AOT heuristic 精度未验证（我的推断）：threshold=1.1（10% 性能损失）是默认值，实际精度取决于训练数据覆盖的 shape 多样性。
  • DE-Surrogate 的 surrogate_threshold=100（源码特征）：前 100 次评估不用代理——对于小搜索空间可能永远不激活代理。

一句话

Helion autotuner 的核心是 LFBO（Random Forest 二分类代理 + pattern search）+ LLM 全局探索 + AOT 离线部署——10 种搜索算法 + 5 种缓存策略 + 3 级 effort 在 2M+ 搜索空间中用 ~500-1000 次评估找到 top 配置，搜索效率 ~0.025%。
