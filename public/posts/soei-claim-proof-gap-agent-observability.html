别信 agent 说「做完了」：Intel 实测 45 个会话揭开 AI 编程的验证缺口

November 03, 2026
核心判断：agent 报告「完成」和证据证明「完成」是两码事——而在真实工作里，这个落差大到足以改变一个主管的决策。Intel 团队抓了 45 个真实 coding-agent 会话实测：约 1/4 的改代码交互最终没有任何独立验证，57.8% 的「改完代码后标记完成」的任务拿不出证据。

当 AI 编程 agent 从「补全一行」进化到「跑几小时、跨会话、链式子 agent」，人重新回到工位时的关键问题，已经不是「模型输出了什么」，而是：到底做了什么、是谁做的、我能不能信它说"做完了"。

这是 Intel 一份 arXiv 预印本（2026-10-29，v1.2，cs.SE，交叉 cs.AI / cs.HC）试图回答的问题。它叫 Soei（Structured Observability of Evidence and Intent），做法分两半：先用真实数据量出「可观测性要解决的证据问题」到底有多大，再据此设计并实现一套把 agent 报告当「声明」、把「先存证据再推理」落到实处的架构。下面拆解。

一、问题：可观测性工具为什么不够用

目前市场上两套工具各有各的盲区。第一类 LLM 追踪面板（LangSmith、Langfuse、Arize Phoenix 等，以及 OpenTelemetry 的 GenAI 语义约定）记录的是模型调用、prompt、延迟、token 成本——它们回答「模型做了什么」，但回答不了「我项目的哪个部分动了、它真的做完了吗」。第二类项目级可观测工具盯着仓库、计划文件、vendor 暴露的 agent 事件，以组件/任务为粒度可视化进度——但它们从不度量「它们显示的东西和实际发生的事差多远」。

论文的核心论点由此而来：可见性（visibility）本身不够，可见性背后的证据必须可信。而「可信」是一个可以测的命题。所以作者做两件事：(i) 在一个真实 corpus 上测量可观测性必须解决的问题有多大；(ii) 设计、实现并评估 Soei——一个把 agent 报告当「声明」、在推理之前先持久化证据、让所有视图都从同一条防篡改记录推导出来的架构。

论文自述这是「首个在真实工作会话上测量 claim–proof 缺口和交接召回率问题、并把基座做成对未改动的 vendor agent 的被动观察者」的工作。位置如图（论文 Table 1）：

二、方法：把「声明」和「证明」分开来量

corpus 很关键——它是真实的日常工作记录，不是为研究构造的任务：第一作者工作站上全部的 VS Code Copilot agent-mode 转录，时间跨度 2026-04-23 到 2026-10-05。规模：

  • 45 个会话，102,233 条原始记录（72.6 MB）
  • 20,577 次工具执行，跨 45+ 种工具类型
  • 2,336 个 human-to-agent episode（一个人 prompt 到下一个 prompt 之间算一个），其中 1,044 个含文件编辑，893 个编辑了代码
  • 工作内容横跨硅后验证内容（Python/PowerShell）、Web 门户、VS Code 扩展、数据流水线、文档

作者定义了四个关键测量，并围绕它们审计：

  • 未验证代码 episode：≥1 次被确认的代码编辑，但最后一次编辑后没有任何被确认的「证明」活动。
  • 无证据完成：一个 to-do 在其 in-progress 期间做过编辑、之后被标记 completed，但编辑和完成之间没有证明。
  • 血缘链接：会话 S2 读取了制品 a，而 a 上一次被确认的写入来自另一个会话 S1（路径级别）。
  • 幻影修改：一次编辑请求，其完成是失败或缺失的。

方法学上一个值得称道的地方：证明分类器是规则型的，作者没有假装它完美，而是做了盲审计——对每个版本抽取 30 个带标签的 episode 随机样本，人工检查「最后一次代码编辑之后的动作」，用实测精确率对最终估计做双向校正，并给出传播后的置信区间。这一点在同类论文里相当罕见。

三、发现 1：claim–proof 缺口是真实存在的

这是论文最核心的数字。对 893 个改代码的 episode、322 个编辑支撑的 completed to-do 的测量结果（Table 7）：

分类器版本 未验证代码 episode 无证据完成的 to-do 审计精确率
v1376（42.1%）210（65.2%）20/30 = 66.7%
v2 / v3245（27.4%）191（59.3%）22/30 = 73.3%
v4（最终）224（25.1%）186（57.8%）25/30 = 83.3%（verified 96.7%）

经过精确率双向校正后，最终估计是：23.4% 的代码编辑 episode 以未验证告终（95% CI 17.1%–35.7%）。即便取保守下界 17.1%，这个比例也「远高于零」——每 5~6 次改代码，就有一次 agent 在没有任何独立检查的情况下把控制权交回给人。

三个层次的理解：

  1. 「reported complete」≠「observed verified」。一个把 completed to-do 直接渲染成「已交付」的仪表盘，会把 57.8% 的无证据任务显示成「做完了」。这不是渲染 bug，是证据模型本身的缺失。
  2. agent 自称的「证明」很靠不住。在它确实验证的时候，主要手段是「跑一下改过的东西」（exec 40.3%）、「UI 检查」（20.5%）、「冒烟」（15.6%），而正式测试只占 3,697 次验证动作里的 166 次（4.5%）。现实中的验证是行为式的、临时的，不是测试报告式的。
  3. 分类器的进化本身就是证据。v1 把它读成 42.1%，作者在盲审计里发现自己两次误判——把 python -c import 检查、_tmp_test_* 脚本当成「没验证」，把一次 scp 部署当成「执行了改过的脚本」。修到 v4 降到 25.1%。按单元测试惯例构建的分类器会把这个缺口高估近一半。

四、发现 2-3：交接很慢、历史会丢证据

交接（hand-off）识别（PQ2）戳破了一个常见直觉——很多人以为跨会话交接是「紧接着」发生的，用时间窗口就能抓到。实测相反（Table 8）：

量 值
跨会话血缘链接 / 会话对292 / 24
写→读间隔 ≤ 10 分钟的链接占比4.5%
写→读间隔中位数12,742 分钟（≈ 8.8 天）
H0（≤10 min）标记的会话对7
H0 对的精确率6/7 = 85.7%
H0 找回的血缘对（召回率）6/24 = 25.0%

结论很干脆：时间启发式「准而盲」——它触发时通常是对的（85.7%），但只找回 25% 真正相互构建的会话对。真实复用横跨数天（中位 8.8 天，在「几小时」和「几周」两个尺度上呈双峰分布），只有内容血缘（H2）能捕获多会话协作。

历史边界（PQ3）同样反直觉：19/45 会话跨度超过 24 小时（中位 5.5 小时、最大约 43 天），6/45 的转录超过 2 MiB——而这 6 个会话占全部字节的 48.1%。意味着一个 2 MiB 的初始回放窗口，在重启后连不上一半的证据。被有界历史丢掉的，恰恰是那些最长、最值钱的会话。

五、发现 4-5：幻影修改、以及日志里的凭据

确认机制（PQ4）：3,548 次编辑请求里，有 40 次（1.1%）从未被确认成功，散布在 30 个 episode。整体上 20,577 次工具执行里有 193 次失败（0.9%），失败率最高的是 create_file（2.4%）、list_dir（2.7%）和交互式提问（6.0%）。

这引出一个隐蔽的坑：在请求时就记录状态变化的观察者（一些老式 plan 适配器就是这么做的），会把约 1/90 的编辑显示成「已应用」，而它们从未发生。比例不大，但每个错误都是静默的，并且会传播进所有下游推断。两阶段确认（start 记 proposed、complete 记 acknowledged/rejected/timed_out）用几乎零成本消除了它。

隐私（PQ5）是最触目惊心的一项（Table 对比）：

一句话：agent 会在自己的消息里复述 secret，并把它们塞进命令参数。任何显示工具调用细节的工具，都可能把 secret 展示在屏幕上、录进回放里。Soei 的账本因为「隐私网关在持久化之前运行」，同一份 corpus 里 0 个匹配——因为 secret 从未被存进去。

六、Soei 架构：8 条原则、6 层流水线

实证部分量出了「缺口」，架构部分回答「怎么办」。Soei 的 8 条设计原则是理解它的最短路径：

  • P1 只观察，不动手——Soei 从不编辑或批准 agent 状态，从不 prompt agent。
  • P2 一条记录、多种视图——每个视图都是同一条账本的确定性投影。
  • P3 先证据后推理——带溯源标签的证据在解释之前持久化，之后可以用更好的规则重跑、重打分。
  • P4 声明不是证明——agent 报告的状态是声明，只有独立证据才能把「完成」升级。
  • P5 校准的不确定性——推断出的关系带实测置信度，低于阈值就弃权（abstain）。
  • P6 结构上就私有——摄取时一次性执行字段策略，secret 从不进入账本。
  • P7 vendor 中立适配器——provider 格式是不可信的、版本化的输入，靠 conformance corpus 校验。
  • P8 评估优先——录制、标注、回放、打分都是一等公民功能。

六层流水线（L0–L6）把这些原则串起来：

层 职责 关键机制
L0 源接住各 vendor 会话、文件系统、VCS、意图文件、证明源Copilot/Codex/Claude Code/Cursor 日志与 hook
L1 摄取适配器 → 归一化 → 确认追踪 → 隐私网关SES 信封、HLC、start↔complete 配对、字段白名单+secret 清洗+加盐路径哈希

三个最出彩的机制：

  • 确认追踪器：每个状态变更请求在 start 时记为 proposed，由匹配的 complete 决议为 acknowledged / rejected / timed_out；投影默认只渲染 acknowledged 的状态。
  • 隐私网关：在持久化之前运行——逐事件字段白名单（默认踢掉 message/prompt/reasoning/命令体/工具输出）、剩余字符串扫凭据模式替换成类型化占位符、路径加盐哈希（本地保留可逆映射但不在账本内）。因为网关在账本之前，secret 永远不可能被「事后取消显示」。
  • 账本不存内容：制品用加盐路径哈希引用，生产里用内容摘要（BLAKE3/SHA-256 或 VCS blob id）。这就是为什么账本只有原始日志的 20% 却能验证防篡改。

七、形式化模型与自治分级

Soei 不只是工程，还给出了一套形式化定义：

  • 证据格（evidence lattice）：声明携带证据等级 Unknown < Inferred < Observed < Reported < Verified。关于「意图」的声明，Reported 高于 Observed；关于「世界」的声明，Observed 高于 Reported；Verified 只能通过 Proof 节点到达。
  • 任务生命周期状态机：Proposed → Acknowledged → InProgress → ClaimedDone → {Verified, Contested}，外加 Withdrawn 和 Reopened。ClaimedDone → Verified 要求：proof 结果为 pass、proof 时间晚于该任务下最后一次生成、且 proof 覆盖了该任务的制品。
  • 分级交接 H0–H3：H0 时间邻接（Δ=10min）、H1 共享工作集、H2 内容血缘、H3 显式回执。
  • 完成信任 τ(T) = cov(T) · e^(−δ·age(T)) · (1−f(T))：覆盖率 × 时间衰减 × 失败惩罚。

最有现实分量的，是它把这条证据链接到了自治分级和治理上（Table 12）：

级别 agent 可以 授予该级所需的 Soei 证据
L0 Suggest只提代码无（capture 可选）
L1 Assisted edit在工作区编辑文件ack-correct 捕获；交接时向人报告 UHR
L2 Verified edit编辑并交回，无需逐步审批每个声明 Verified 或显式标记；UHR ≤ 目标；SLR = 0
L3 Multi-agent跑会话和相互构建的子 agent每次交接都有摘要血缘；CP ≥ 目标；contested 告警
L4 Unattended delivery在策略内 merge 和 deploy每制品签名溯源证明；oracle 验证的 VCR；可回放账本；回归自动撤销

核心设计思想是：自治是 agent 挣来的、也是可以失去的。一个 agent 在其 golden harness 记分卡满足门槛时被授予某任务类的 Lk，而当重放的回归运行或生产证据把某个指标推过阈值（比如一次模型升级抬高了 UHR），它被自动降级。

「golden harness」是另一个关键概念——一个参考评估与保证环境，满足三点：(i) 每个 agent 动作都被捕获为可验证证据，(ii) 每个完成声明都对照独立证明或任务 oracle 校验，(iii) 每次运行都能跨 agent/模型/prompt 版本逐位重放对比。它同时服务于评估、回归、认证三个目的。论文还给出了一组带真实基线的 harness 指标（Table 11）：

治理层面，论文把 Soei 的证据能力映射到 NIST AI RMF 1.0、ISO/IEC 42001:2023、EU AI Act 第 12 条（记录保存）和第 14 条（人工监督）、以及 SLSA / in-toto 供应链溯源。并点出一句关键的话：治理证据必须在「动作发生的那一刻」就存在——没被捕获的、没被确认的、被边界丢掉的、被 secret 污染的历史，事后无法为审计重建。基座必须在授予自治之前就位，而不是之后补装。

八、边界：这份研究没说、也不能说的事

论文对自身局限的交代相当诚实，值得照单列出：

  1. 内部效度：证明分类器是规则型的。缓解手段是盲审计（4 个样本 × 30）+ 双向精确率校正 + 四版本敏感性分析。但「证明」的其他通道（比如人在 agent 之外手动测试）对观察者是隐形的，这会从「人类视角」高估未验证率——不过作者强调，可观测工具能显示的本来就只有「agent 证据视角」，后者才是他们要测的。
  2. 血缘用路径级身份而非内容摘要：写入和读取之间的覆盖可能制造虚假链接，摘要级血缘是后续工作。
  3. 外部效度：corpus 来自一个开发者、一个 agent 产品（VS Code Copilot agent mode，跑过多个前沿模型）、一个硅后验证与工具化的上下文。作者明确把结果定位成「存在性与量级 pilot」，用于驱动设计，不是总体估计。他们引 AgentLens 在基准轨迹里也发现 10.7% 的缺失/乱序验证，作为「现象不限于此设置」的旁证。
  4. 构念效度：「Verified」意味着「最后一次编辑后有独立检查跑过」，不是「代码是对的」。τ 也绝不表示正确性概率。
  5. 伦理：所有分析在作者自己的会话上本地进行，不持久化任何消息/命令/文件内容，只报聚合计数；credential 值从不打印或存储，并要求受影响凭据轮换。

另外值得指出的一个客观事实：corpus 规模是 45 个会话、单开发者，统计上对「比例」的估计（如 23.4%）置信区间很宽（17.1–35.7），这本身反映了小样本。把它当作「行业普遍水平」读是误用。

九、我的四点判断

1. 「做完了」是 agent 时代最危险的三个字。23.4% 未验证 + 57.8% 无证据完成，这两个数放到「有人盯着」的场景里就已经是这个量级。一旦进入 L3/L4 自治——无人逐步审批、链式子 agent、自动 merge/deploy——未验证的交接就直接变成缺陷逃逸路径。这不是「要不要做可观测性」的问题，而是「在授予自治之前，证据基座必须已经存在」的前提条件。

2. 时间启发式在 agent 协作里基本失灵。「跨会话交接紧接着发生」是个从人脑直觉里带出来的错误假设。真实协作的中位间隔是 8.8 天。谁还在用时间窗口拼会话血缘，谁就只能看到 1/4 的真相。内容血缘（谁写了这个 artifact 的哪个版本、谁读了它）才是唯一可靠的手。

3. 隐私问题不是「小心点」能解决的，必须在存储之前拦截。1,326 条含凭据的记录、agent 主动复述 secret 并塞进命令——这说明 secret 泄漏不是偶发失误，是原始日志的固有属性。事后脱敏永远是补丁，因为 secret 已经落盘了。Soei 的做法（摄取时白名单 + 清洗 + 加盐哈希，账本不存内容）是对的范式：private by construction，而不是 private by policy。

4. 这套东西的护城河其实是「只读」。P1（observe never act）把 Soei 和 2026 年涌现的一批「Proof-or-Stop」「runtime contract」类工作区分开——那些是强制执行，Soei 是被动观察 + 量化缺口 + 提供基座。这让它能对未改动的 vendor agent工作，不用 agent 框架采纳。代价是它自己不执法，治理放在一个独立的 policy plane 里。这个「观察与控制分离」的设计，反而可能是它能被企业接受、又不过度侵入的原因。
