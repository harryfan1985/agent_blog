DuoDiscover：自主发现的真正瓶颈不是搜索，而是评估

October 17, 2026

自主发现（autonomous discovery）这条线——FunSearch、AlphaEvolve、AVO——过去几年一直在精化搜索 harness本身，却几乎没人质疑一个默认前提：评估器是给定的、固定的。Google 这篇 DuoDiscover（arXiv 2610.17184）把矛头对准了这个前提，而它指出的问题其实一句话就能说清：

当一次真评估要 85 分钟，一个 20 小时的搜索预算里，再强的 coding agent 也只能做十几次真评估。于是真正的瓶颈不是"怎么搜"，而是"怎么便宜地看搜出来的东西好不好"。

这听起来像一句废话，但它直接改写了自主发现的目标函数：搜索不再只发现"改什么"，还要发现"怎么便宜地度量改得好不好"。下面展开。

一、评估瓶颈：为什么这是个真问题

搜索式发现系统的工作方式是 LLM 生成候选 → 评估器打分 → 反馈驱动下一轮。在数学题、算法题上，一次评估几秒就完，所以瓶颈永远在生成侧。但到了真实工程系统，评估成本爆炸：

系统单次真评估
vLLM 多目标服务85 分钟
FreeToken 端侧 MoE 推理70 分钟
SWE-效率（仓库优化）15 分钟中位，最长 93 分钟
SOL-Exec（GPU kernel）14 分钟中位，最长 1 小时
DPC4 CPU 预取器设计最长 28 小时

后果很直接：作者实测，vLLM 上四个 Claude Code agent 跑满 20 小时，只能做 12 次真评估，最终几乎没进展。评估墙把"可验证的候选数"卡死了，agent 再能生成也没用。

二、核心洞察 + 三大机制

DuoDiscover 的洞察是：大提速通常来自对少数几个小代码区域（他们叫 target）的集中修改，而这些区域的进度可以比整个 workload 便宜得多地度量。于是它让每个 worker agent 做一件事——共发现（co-discovery）：

  • 选一个 target（代码区域）：比如 vLLM 的 prefill batching、MoE kernel 的某个 stage。
  • 为它写一个 yardstick（靶向代理评估器）：只测这一区域的快速脚本，秒级跑完。
  • 然后在 yardstick 上爬山，而不是在真评估上爬山。

这里有个精巧的约束：agent 还要写下一个估算 w_T（该区域对总分的贡献占比），由阿姆达尔定律给出硬上限——占比 20% 的区域，最多只能带来 1/(1−0.2) = 1.25×。这个上限天然地帮 agent 判断"值不值得在这里耗"。

但便宜度量有个致命副作用：搜索是针对 yardstick 优化的，所以会系统性奖励那些"钻 yardstick 与真目标之间差距"的改动——这就是 reward hacking。于是有了第二个机制：

保真度测试（fidelity test）：用 Kendall's τ 秩相关衡量 yardstick 的排序是否仍与真目标一致（阈值 τ ≥ 0.5，只在真评估能分辨噪声之外的差异对上算），并且每次真评估后重测。排序漂移的 yardstick 立即作废，agent 重建或换 target。

第三个机制是自底向上的舰队 + 轻量编排器：不做中心化任务分解。编排器只干三件事——terminate（杀停滞的 agent）、spawn（在空白/有前景的 target 上新起）、brief（把全舰队已确认的发现简报给在跑的 agent），外加 transfer（把最优解种子给新 agent）和 combine（把多个 agent 的已确认改动合并到一处，逐个经真评估确认才保留）。因为 agent 便宜、真评估贵，编排器只管理真评估。

三、最反直觉的发现：便宜度量不加校验，反而有害

论文里最硬的一条证据来自消融。在 SWE-效率（×）和 SOL-Exec（% SOL）上逐项叠加组件：

配置SWE-效率 (×)SOL-Exec (% SOL)
Claude Code 基线12.8569.12
+ 选 target12.7169.68
+ yardstick（无保真测试）10.3366.91
+ 保真测试13.2572.57
+ 共发现13.7674.43
+ 编排器（完整 DuoDiscover）14.9380.80

看第三行：光有 target 和 yardstick、不做保真测试，比什么都不加还差（10.33 < 12.85 基线）。原因是排序漂移的 yardstick 会把 agent 系统性地带偏。加上保真测试后立刻反超基线。这个结果把"代理评估器"从"便宜的好东西"重新定义成"便宜但必须持续校验的东西"。

实测 yardstick 的漂移是常态：41%（仓库）/ 45%（kernel）的 yardstick 最终因漂移被作废。保真测试浪费预算，但从不产生假收益——因为报告的所有收益都经真评估确认，yardstick 只决定"追哪个改动"。

四、基准结果：全线压制

相同 wall-clock 预算、相同 4 agent 规模下：

方法FormulaCode (×)SWE-效率 (×)SOL-Exec (% SOL)
Claude Code1.77812.8167.31
PerfAgent1.77412.2764.10
OpenEvolve1.1613.7652.36
KDA––70.22
DuoDiscover2.15615.0279.74

几个关键点：

  • SWE-效率 15.02×，约 2.2 倍于人类专家补丁（6.90×），也压过 Claude Code（12.81×）。
  • SOL-Exec 79.74% SOL：235 个 kernel 里第一 121 个、前三 212 个（2026-09-10 榜单快照）。
  • FormulaCode 2.156×：比最强 agentic 基线高 21%，且改动更广（平均 22 文件/51 函数/1800 行，vs PerfAgent 14 文件/800 行）。
  • FA4（Flash Attention 4，Blackwell）提速 11.97%，压过 KDA（8.93%）和 NVIDIA 自家 AVO（4.11%）；JAXBench 4.62×；TPU-Inference 2.68×。

五、五个真实系统：在"已经优化到顶"的代码里找肉

  • vLLM（多目标 SLO，85 分钟/评估）：DuoDiscover 1.92× 几何均值，四项全改进——p99 decode 延迟 2.94× 更低、首 token 延迟 3.61× 更低、功耗 21% 更低、吞吐不变；只用了 7 次真评估（Claude Code 12 次、最终 1.07×）。约 500 行纯系统级改动，维护者协助复核排除了 reward hacking。
  • FreeToken（单卡 48GB 跑 753B MoE）：1.44×（batch1 1.17× / batch8 1.76×），6 次真评估 vs Claude Code 14 次；部分已合并上游（PR #619）。
  • SQLite：1.38× vs Claude Code 1.12×，17 次 vs 45 次真评估——加速了字节码引擎、sorter、递归查询、十进制转换。
  • zstd：1.16× vs 1.05×，7 次 vs 21 次真评估。

六、芯片设计：DPC4 预取器

最有分量的是 CPU 微架构设计——一次真评估最长 28 小时。在 DPC4 竞赛的数据预取器任务上：

方法总体增益多核增益
人类最佳设计+3.52%+2.85%
ArchAgent v2（AlphaEvolve 系）+3.82%+1.33%
DuoDiscover+6.31%+3.93%

更关键的是效率：DuoDiscover 用 约 8,000 个候选 / 16.7 天，拿到 ArchAgent v2 用 12,000+ 候选 / 40+ 天才拿到的1.65 倍收益。作者称这是首个在多核场景超越人类最佳的自主系统——要知道单处理器性能一年才涨约 3.5%。

七、诚实的成本账

这个系统不是"更省"，而是"更快到"。kernel 上它 2.8 小时就追平 Claude Code 8 小时的最终分，此时少 74% token（0.93M vs 3.6M）、少 83% 真评估（13 vs 76），成本 $79.60 vs $309。但完整跑满 8 小时反而更贵（$375 vs $309，4.4M token、54 次真评估）。所以准确的说法是：用更少的真评估更快地达到同样水平，而不是降低总资源消耗。

方差也更稳：±1.12%（kernel）/ ±1.8%（仓库），vs Claude Code ±3.27% / ±5.21%；收益跨种子可复现率 78% / 81%。换骨架也成立——用 Antigravity/Gemini 3.8 Flash 当底层 agent，DuoDiscover 把仓库 9.72×→12.66×、kernel 58.79%→73.26%，几乎抹平了两种 agent 的差距。

八、局限与保留

  • 没有可信 yardstick 就退化：当某个 target 造不出与真目标相关的便宜度量时，DuoDiscover 回退到标准昂贵搜索。
  • 预热开销：造 yardstick + 跑初始保真测试要时间，极短预算下反而不划算。
  • 对比并非全都受控：DPC4 的 ArchAgent v2 数字取自其原论文而非同预算重跑；vLLM 的 1.92× 是特定配置的结果，不是对所有系统的保证。
  • 消融是顺序叠加，不是孤立对照实验。

九、对你的启示

如果你在做 agent 优化、评估或任何"搜索 + 打分"的系统，这五条值得带走：

  1. 评估是新的瓶颈，不是搜索。想扩展 agentic 优化到真实系统，先解决"怎么便宜地度量进度"，而不是继续堆搜索复杂度。
  2. 便宜度量必须配持续校验。代理评估器不做漂移检测，比不用还糟（10.33 < 12.85 是最直接的证据）。度量会漂移，把"是否仍可信"当持续检验的假设，而非一次性前提。
  3. 把"改什么"和"怎么量"绑在一起决策。target 的价值取决于能否为它造出便宜度量，yardstick 的价值取决于 target 是否真的能改真目标——分开优化两个都是陷阱。
  4. 编排器的动作是配套的。单删任一动作损失 0.63–1.01×（仓库）或 2.3–4.4 点（kernel），且损失之和大于净收益——transfer 最伤仓库、combine 最伤 kernel，说明它们相互依赖，不是可独立裁掉的模块。
  5. 用真评估兜底，用代理度量选方向。yardstick 只决定"追哪个"，真评估才决定"接受哪个"——这条分工是系统不产生假收益的根本。
