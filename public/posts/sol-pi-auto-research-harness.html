NVIDIA SoL-Pi：用 auto-research 循环把 agent harness 跑便宜一半

September 12, 2026

一句话：在 scale RSI 之前，先让 AI 把 AI 变便宜

NVIDIA 9 月 7 日开源的 SoL-Pi 表面上是一个工具——Pi coding agent 的效率扩展，装上后 token 降一半、成本降三分之一——但真正值得研究的是它背后的方法论：他们把 harness 改进本身当成一个可以规模化自动搜索的 RSI 问题，152 个自动生成的提案，只有 4 个活了下来，而这 4 个就值每小时 8.75–13.50 美元。

RSI 每次尝试都烧 token，成败都算钱。在 scaling 递归自我改进之前，应该先问 AI 能不能把 AI 系统本身变便宜。这是 SoL-Pi 的出发点，也可能是效率研究的正确位置。

一、问题：长时程 agent 的重复劳动税

跑过几小时以上的 coding agent 都见过这些模式：文件编辑后面总跟着一条可预测的验证命令，却要单独一轮模型往返；大块工具结果在首次使用后仍然每次请求都回放，占上下文也占 cache；已完成的子任务继续赖在活动上下文里；一个 frontier 模型花掉整个请求读日志，而其中只有几行影响下一步决策。

SoL-Pi 的搜索目标被精确定义为受限效率（constrained efficiency）：在预声明的能力保持判据下降低成本、token 和轮次。不允许靠提前停、跳过验证、隐藏证据来省钱——省的钱只有在任务质量保持在容差内时才计入效率改进。

二、流水线：152 个提案如何筛出 4 个机制

整个 auto-research 系统的结构：

152 提案（6 家族：Context 24 / Progress 26 / Tools 26
          / Delegation 15 / Prompt&Policy 15 / Improve&Eval 46）
  → Oracle Analysis 预筛（花 rollout 预算前砍掉弱方向）
  → 扇出为独立 lineage，每条内循环：
     轨迹 Rollout → Map-Reduce 分析 → 提出机制
     → 实现（Ralph Loop）+ 独立 Reviewer 审查行为契约
     → 训练集初筛 → 隔离 held-out 验证
  → 4 个存活（转化率 ~1/40）→ 人工理解后重构 → SoL-Pi

几个关键的实验卫生设计，在 auto-research 领域少见地严谨：

  • Held-out 三隔离：held-out 轨迹永不进入后续分析；循环内任何 agent 看不到 held-out 结果；失败的 held-out 评估直接拒绝候选，不作为修复反馈——杜绝"在测试集上进化"
  • 环境合成有据可查：535 个训练环境 = 495 个 GitHub issue-PR 对挖掘（环境恢复到修复前一个 commit、对 agent 隐藏 PR 和维护者的回归测试、只保留"PR 前测试失败、PR 后通过"的任务）+ 40 个 verifier 驱动的合成任务（Terminal-Bench 风格，先写 verifier 再围绕它构造环境）
  • 评测基准严格隔离：EdgeBench（51 个长时程任务）的数据和 verifier 不作合成源或模板，只做最终 held-out——分数是对未见任务设计的泛化度量
  • Oracle 预筛：在消耗 rollout 预算前，从已有轨迹估算每个方向的机会大小——每个提案必须对 harness 中"可避免的工作"做出具体断言

验收门是双重的：① 全部能力指标在预声明容差内；② 至少一个效率指标改善。过门的候选保留非支配结果。门是逐机制应用的，小损失会在组合时累积——装配后的 harness 保留 Pi 平均分约 94%，这是诚实的代价披露。

三、四个存活机制

层机制改变什么
ToolsAction Fusion编辑/写入 + 后续验证命令合并为一次工具调用：harness 本地先应用编辑再跑命令，返回合并观察，省一次模型往返
ContextOnline Context CompactKV-cache 复用通常让 compaction 越晚越好；它换一个时钟——子任务语义完成作为 compaction 触发点，且只在"预期未来节省 > 重写成本"时动手（经济门控 + 窗口压力检查）；压缩成功后在新 turn 自动继续任务
ObservationsObservationPack大文件/工具结果本地归档，上下文里只留稳定句柄 + 短摘录，需要时精确分页召回——payload 可访问但不再回放
DelegationEvidence-Preserving Reducer长诊断日志委派给便宜 agent 读，产出的 receipt 绑定归档日志、每一条引用核验后才让 frontier agent 看到；核验失败原样返回。委派的正确性不再依赖对流畅摘要的信任

四个机制共享四条规则：不打 Pi 补丁（只用公开扩展 API）、显式 opt-in（缺配置全关）、保留证据（原始观察留在本地）、Pi 的运行时选择不被覆盖。

特别注意 Evidence-Preserving Reducer 的模式价值：它把委派范式从 trust-based（主模型信任子 agent 的摘要）升级为 verify-based（摘要必须带可回指的源句柄，逐条引用对照归档源核验，fail-open）。任何做多 agent 流水线的团队都值得抄这一条。

四、结果：更省，而且（在一个后端上）更强

EdgeBench 51 任务（轨迹 2–12 小时），两个模型后端都开 xhigh（最高推理档）：

  • 分数：保留 Pi 平均分 ~94%；GPT-5.6 Sol 后端上超过原生 Codex harness——更省且分数更高
  • 效率 vs Pi：token −45~49%，成本 −约 1/3
  • 效率 vs 原生 Codex/Claude Code：token −35~64%，list-price API 成本 −50~54%
  • 换算：专业研究员单问题场景，每小时省 $8.75–13.50（vs 原生 harness）

五、方法论发现（比机制本身更值钱的部分）

1. BFS 逃出局部盆地，DFS 陷进去。深度优先策略（单 lineage 反复打磨最新候选）在 5–10 轮迭代后，连 GPT-5.6 Sol @ xhigh 都只做同设计的微调、不换方向。广度优先则大部分想法死在验证上，但偶尔暴露出罕见的异常候选，后来的循环能把它实现并硬化——项目里最有用的 harness 改动，一部分正来自这种跳变。1/40 的转化率不是缺陷而是结构：广度的作用就是让稀有候选可被发现。

2. Token 效率是天然防过拟合的优化目标。在封闭任务集上优化 harness 很容易过拟合——把任务相关信息搬进 harness、给训练集里反复出现的模式加特判。而交互环里的浪费（重复上下文、无决策的相邻动作、大输出的重复传输）是任务无关的，对它们的削减天然更可能迁移到新任务、新模型。选对搜索目标，比防止过拟合的手段更重要。

3. 长时程才能测出 harness 差异。几小时以内的任务上，context 回放、大输出、cache 写、额外往返都来不及积累，每 turn 的节省被启动成本和任务间方差淹没。EdgeBench 是当时唯一支持 2–12 小时连续运行的公开套件（Terminal-Bench 2.1 和 SWE-bench 通常 1 小时内结束）。想测 harness 级效率，先用对时间尺度的 benchmark。

4. 编排系统本身进化了三代。编译式 YAML workflow 死于固定图覆盖不了边角案例（反复停下等人类修复）；lead agent 现场写协调代码的长寿协调器死于分支累积（上线新实验要 10+ 小时改协调器代码）。胜出的是一次性 skill loop：维护一个极简模板，每个实验实例化新副本、跑完即弃——规模化变成重复模板实例化，而不是扩展一个协调器。唯一的共享依赖是模板本身要维护好，这比前两者都容易。

5. 人在环的混合 RSI 分工。人类供给早期先验（harness 原则、机制假设）、砍掉低价值方向（如 base-harness 超参搜索）；想法进入循环后全程无人类干预；候选存活后，人类回来理解机制并重构成干净实现。开源的是被理解了的机制，不是原始搜索工件。完全自主 RSI 是否是正确终态，论文明确定为开放问题——目标、证据、实现的漂移会在人类注意到之前复利。

六、局限

  • 94% 是均值——逐机制允许的小损失组合后的个体任务分布未细披露
  • 51 任务 × 2 后端规模有限；$/小时节省数字依赖 list-price 假设
  • 495 个训练环境来自 GitHub issue-PR 对，分布偏向"有干净 PR 的"开源任务
  • 无逐机制消融披露（哪个机制在哪个后端贡献多少）
  • auto-research 流水线本身未开源（开源的是产物），不接受外部代码贡献

七、对 harness 设计者的四条可迁移结论

  1. 委派要核验，不要信任。子 agent 摘要进主上下文前，绑定源材料 + 逐条引用核验 + fail-open。这一条与 agent 委派任务时的"自报成功不可信"是同一原则的工程化。
  2. 压缩要算经济账。compaction 的触发不该是"上下文太长"，而是"重写成本能否被未来节省偿还"；语义边界（子任务完成）是比 token 数更好的触发器。
  3. 宽假设池 + 严验证门。152 个提案死掉 148 个是健康的；真正危险的是让失败候选回流成修复反馈，和在未隔离的数据上验证。
  4. 编排代码要用完即弃。长寿协调器必然走向分支累积；极简模板 + 每次实例化新副本，规模化才不依赖维护一个不断膨胀的大脑。

最后是 NVIDIA 留下的两个愿景：harness pretraining（harness 也该有类似模型的 scaling law——算力和 rollout 环境多样性涨，harness 变强变省）和 efficiency for efficiency（更高效的 harness 降低下一轮 auto-research 的成本，固定预算覆盖更多想法）。后者被明确标注为长期愿景而非已演示的复利——但方向是清楚的：效率既是 harness 研究的产出，也是扩大下一轮搜索的资源。
