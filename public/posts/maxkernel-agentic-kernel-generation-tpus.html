MaxKernel：Google 的 TPU Agentic Kernel 生成系统

October 4, 2026

Hook：agent 写的 kernel 在 8 个生产级 TPU 任务上 7 次赢过 Google 手调专家，geomean 2.32× vs 2.02×

kernel 工程师是最贵的工程师之一——手写 Pallas/CUDA kernel 要同时驾驭内存层级、DMA 流水线和多维 tiling。Google AI-Hypercomputer 团队 2026 年 9 月开源的 MaxKernel（arXiv 2609.04523）给出了一个系统化答案：把 kernel 优化拆成三种可切换的 agent 编排范式，全部跑在同一个「编译器 + XProf 硬件 trace」反馈闭环上。JaxBench 50 个任务 geomean 1.58×，MLA v1 上对人写的 Pallas kernel 再提升 8.68% latency / 9.50% throughput。

核心发现一：零采样 20% 编译率 → 闭环 agent 100%，实时代码器反馈是生死线

论文最刺眼的基础数据是 Best-of-N 基线（N=100 零采样）在 JaxBench 上只有 10/50 编译成功。Pallas 这类硬件 DSL 的 API 刚性、内存约束和低级编译器报错，让纯 LLM 采样基本不可用。引入「编译验证 → 测试执行 → autotuning → profiling」闭环后，Auto agent 达到 49/50 编译、48/50 正确。

核心发现二：三种编排范式是同一套子 agent 池的三种调度策略

架构上最干净的决策：Planning / Implementation / Test / Autotuning / Profiling(XProf) 五类子 agent 是共享的，「范式」只是 orchestration 层的差异：

  • HITL：「One Agent, Then Wait」交互路由——每个阶段产出（优化计划、代码草稿）停下交人审，人可自选子 agent 调用顺序。适合需要专家直觉的困难 kernel
  • Auto Loop：先合成测试套件并冻结（防 reward hacking），然后循环「Plan → Implement → Validate → Test → Autotune → Profile」，profiling 结论直接注入下一轮 planning。两个防御性设计：失败短路回 planning 保留错误上下文；Best-of-N 状态快照 + 终局回滚到最低延迟有效解，防性能回归
  • Graph Search：把 Auto agent 封装成「节点扩展器」。每个节点 = {代码, 计划, 正确性, speedup}，SearchGraph 持久化（断点可恢复），每个节点扩展跑在独立 agent session——顺手解决了 context overflow。两个算法：Parallel（深预算：每轨迹 5 iter）vs Beam（广探索：每节点仅 2 iter + top-k 剪枝）

核心发现三：Parallel vs Beam——深调试预算比广度剪枝更值钱（至少对 Pallas）

论文 §3.3 的搜索动力学分析是全书最有工程价值的部分。Beam search 前两个 depth 在爬升，depth 3 平台化；Parallel 的性能分布上下界持续抬升，峰值 geomean >1.51×。根因：Beam 每节点只给 2 iter，剪枝机制会惩罚那些「需要多步调试才能编译通过」的大胆优化——Pallas 的 rigid memory constraint 恰恰需要长 horizon。

Beam 的适用域也存在：优化空间里有「多样、易编译的局部最优」（不同 loop ordering 能立刻给出可靠信号）时，广探索更高效。这是一条可操作的选型规则，不是玄学。

知识库设计的一个关键取舍

RAG 语料刻意排除人写 kernel 代码，只保留静态文档（Pallas/Mosaic/XLA 文档、memory layout guide、性能手册）。目的是测 agent 能否不靠记忆人类解法、自己泛化出 TPU 特定优化。开源的 claude-code 实现里对应的是「semantics spine / advisory spine」双链文件治理：参考 kernel 只进 ref/，禁止被测量、禁止被 implementer 读取。这个「隔离参考解」的动机与 frozen test suite 一致——保持测量的诚实性。

工程启示

1. 搜索算法做成可插拔外层，agent 不变

MaxKernel 的谱系贡献是把「搜索算法」从 agent 系统里解耦出来：同一个 Auto agent 可以被 HITL、闭环、parallel、beam（未来还有 evolutionary/greedy）任意调度。对你自己的 kernel agent 系统，值得把「单轨迹迭代」抽象成「节点扩展器」接口，上层搜索策略可替换。

2. 防作弊三件套：冻结测试 + 状态回滚 + 参考隔离

frozen test suite 先于优化生成、Best-of-N 快照终局回滚、参考 kernel 与 implementer 物理隔离（文件路径硬编码 + 权限治理）。这三条组合拳比单靠 prompt 约束可靠得多，可以直接移植到任何 agentic 优化系统。

3. Profiling 反馈要结构化注入 planning，不是贴 log

XProf trace 被提炼成 latency / 带宽利用率 / compute density 等结构化指标进入下一轮 planning，而不是原始 trace 文本。反馈的质量决定闭环的质量。

4. 双 harness 实现是 agent 无关性的样板

同一系统有 adk 版（Google ADK + gemini-3.1-pro-preview）和 claude-code 版（20 个 subagent markdown + state.json 断点续跑）两套实现。claude-code 版证明：编排逻辑可以完全外置为 markdown + 文件系统状态，LLM 框架只是执行器。

局限与诚实标注

  • 单模型背书（论文自认）：所有实验只用 gemini-3.1-pro-preview，其他 LLM 的 ablation 被列为 future work。结论对弱模型是否成立未知
  • 单硬件（论文自认）：全部在 TPU v6e 上测。论文声称 agentic 原则可迁移到其他 accelerator，但没有跨硬件数据
  • Beam 调参敏感性（我的推断）：beam width 3 / depth 3 / 2 iter 这组参数对结论影响多大没有 ablation；「depth 3 平台化」可能是预算配置的人为产物而非范式本质缺陷
  • 并行成本（我的推断）：Parallel 1.58× 是 5 条轨迹 × 5 iter 的总和成本，论文没有报告 token 成本 / 算力成本对比。fast₁ 34/50 的「每任务成本」可能远高于 Auto
  • Ragged Paged Attention 失败模式未深挖（我的推断）：人写 4.65× vs agent 1.42× 的差距根因（动态 shape？ragged layout 复杂度？）论文没有分析

一句话

MaxKernel 证明了 kernel 优化的「搜索算法」可以被抽象成 agent 系统外层的可插拔组件——在 brittle 的硬件 DSL 环境里，给每条轨迹足够的调试预算（深度）比聪明的早期剪枝（广度）更值钱。
