NVIDIA SkillEvaluator：别假设 Agent 技能有用，去测量它

August 22, 2026

问题：Agent 技能"看起来有用"不等于"真的有用"

2026 年 8 月，AI Agent 生态有一个尴尬的事实：往 Agent 里塞"技能"很容易，但没人能证明这些技能真的让它变得更好。 一个技能包可能文档详尽、结构规范、安全合规——但它到底有没有提升 Agent 的任务完成率？有没有减少无效调用？有没有引入不必要的复杂度？

NVIDIA 给出的答案是 SkillEvaluator——一个开源的多层评估框架，专门用来测量 Agent Skills 是否真正改善了 Agent 性能。它不只是检查技能本身的质量，而是直接跑 A/B 对照实验：同一个任务，同一个 Agent，一次装技能，一次不装，看差异。

核心命题：别假设技能有用，去测量它。

一、三层架构：三层独立，各管一件事

SkillEvaluator 的设计是三层结构，每层都是独立入口——可以直接从 Tier 3 开始跑，不需要先过 Tier 1 和 Tier 2。

层级回答的问题代表命令依赖
Tier 1: 验证这个技能安全且格式正确吗？validate, quality-check, security-scan纯离线，无需 API Key
Tier 2: 去重它和已有的技能重叠吗？similarity-check, context-optimization-check需要 embeddings 提供商
Tier 3: 实测它真的让 Agent 变强了吗？tier3 evaluate, compare需要 LLM + Agent CLI + Docker 沙箱

Tier 1：离线质量门禁

Tier 1 是纯静态检查，零 API Key 即可运行。它检查：

  • Schema 验证：SKILL.md 的 frontmatter 是否符合 Agent Skills 规范
  • PII 扫描：是否泄露了个人身份信息
  • License 检查：许可证合规性
  • Quality 质量评分：0–100 分，A–F 评级，及格线 70 分（C）
  • Unicode 安全：是否有隐藏字符注入风险
  • Script lint：附带脚本的安全检查

Tier 1 还集成了 SkillSpector 做专门的 Agent 技能安全扫描，以及外部的 Semgrep 和 Gitleaks。如果某个必需扫描器没有产出可信证据，结果是 INCOMPLETE 而非 PASS——它宁可失败也不会假通过。

Tier 2：语义去重

Tier 2 回答一个被很多人忽略的问题：你的新技能是不是在重复已有技能的内容？

它用 embedding 相似度做两件事：

  • 技能内去重（context-optimization-check）：检查一个技能内部是否有重复的指导内容
  • 跨技能去重（similarity-check）：检查一个集合或目录里多个技能之间是否有重叠

这解决的实际问题是：Agent 环境里每个技能都在竞争 Agent 的注意力，重复的指导不仅浪费 context window，还可能导致 Agent 加载错误技能。

Tier 3：A/B 对照实测——重头戏

Tier 3 是整个框架最有价值的部分。对每个技能，它在沙箱里跑同一个任务两次：

实验臂配置
With-skill（技能臂）Agent 装上这个技能
Without-skill（基线臂）同样 Agent，同样任务，不装技能

唯一的实验变量就是技能本身。 Prompt、模型、任务输入、评分标准、执行环境全部相同。使用的是开源框架 Harbor 做沙箱隔离执行。

支持的 Agent harness 包括：

  • Claude Code
  • OpenAI Codex
  • OpenCode

NVIDIA 还为 Cursor 发布了插件，同样的技能也通过 Skills.sh、ClawHub 和 Hermes Hub 分发。这种对照实验设计比传统的"装上技能后看 Agent 能不能完成任务"严谨得多——后者缺少反事实基线。

二、五维度评分：不只看"答案对不对"

Tier 3 测量五个维度，每个维度回答一个独立的问题：

维度测什么映射的 Harbor 指标权重
Security安全吗？无不安全操作、无密钥泄露security1.0
Correctness最终答案正确吗？accuracy1.0
Discoverability该加载时加载，不该加载时不加载？skill_execution1.0
Effectiveness是否达成用户目标，遵循预期工作流？goal_accuracy + behavior_check0.5 + 0.5
Efficiency有没有浪费工具调用和 Token？skill_efficiency1.0

其中 Discoverability 和 Efficiency 是针对技能本身的评分——它们衡量的是 Agent 是否在正确时机激活并使用了相关技能，而不是 Agent 本身的行为能力。这个区分很重要：一个技能可能让最终答案已经正确的流程通过减少死胡同来提升效率。

核心指标：Skill Lift

Skill Lift = 技能臂得分 − 基线臂得分。它直接测量你的技能贡献了多少。判定区间：

Skill Lift判定含义
≥ +0.05Pass技能有可测量的帮助——可发布信号
−0.10 ~ +0.05Neutral在运行噪声范围内——增加 --n-attempts 再下结论
≤ −0.10Fail技能让 Agent 变差——发布前调查

此外还有 pass@k 作为可靠性信号：每个用例跑 k 次，只要有一次通过即算 pass，它衡量的是技能是否让成功更可重复，而不只是平均分是否提升。

三、基准测试结果：300+ 技能，30+ 产品

NVIDIA 在 2026 年 8 月 12 日的基准快照中，公布了对其 NVIDIA/skills 目录中 300+ 个验证技能的评估结果。这些技能覆盖 30+ 个 NVIDIA 产品，在 Claude Code 和 Codex 两个 harness 上分别测试。

无技能基线 vs 有技能得分

维度无技能基线有技能得分Skill Lift
Correctness4687+41
Discoverability4282+40
Effectiveness3978+39
Efficiency4378+35
Security9798+1
全部维度平均——+31
排除 Security 平均——+39

注意 Security 的基线已经 97 分——它的主要目标是验证装技能不引入安全回退，所以 Lift 只有 +1 是预期的。

两个 harness 都展示了持续且显著的提升。差异约 5 分，符合预期——它们有不同的默认 system prompt、context 处理和 tool-calling 实现。

四、三个关键实务发现

发现 1：产品领域比 harness 选择更重要

Claude Code 和 Codex 平均只差约 5 分。但不同产品领域的 Skill Lift 从 +2 到 +46 不等。领域、任务和评估设计的影响远大于选哪个 Agent harness。这意味着优化技能内容比换 Agent 更有效。

发现 2：Token 节省因技能而异，不能取平均

SkillEvaluator 单独跟踪 Token 使用量。两个例子：

  • jetson-optimize-memory：Token 从 617,306 降到 142,540（−76.9%），执行时间从 474.9s 降到 220.0s（−53.7%）
  • cuopt-install：Token 从 25,227 增到 55,582（+120.3%），执行时间从 34.0s 增到 41.1s（+20.8%）

目录级平均值无法预测单个技能在特定工作流中的价值。 有的技能省 77% Token，有的反而多花 120%。这恰恰说明需要逐技能评估。

发现 3：85% 的技能只用 1 次尝试测试

85% 的已发布技能结果用 1 次尝试测试，15% 用 2 次。由于 Agent 运行有固有噪声，小 Lift（−0.10 到 +0.05）被刻意判定为 Neutral。NVIDIA 自己的建议是：在小 Lift 区间不要下结论，增加 --n-attempts 再跑。

五、局限：厂商自报，无置信区间

必须说清楚这个基准测试的局限：

  • 全部基于 NVIDIA 自己的仓库、技能和评分框架 → 这是厂商自报数据，不是独立第三方证据
  • 没有置信区间 → +31 分是宏平均，不能当作"技能普遍能涨 31 分"的精确估计
  • 85% 只用 1 次尝试 → 单个技能的分数可能有波动
  • 尚无独立第三方复现 → 下一个关键信号是外部开发者能否用不同模型、harness 和任务集复现类似结果
正确读法：把 +31 分当作方法论有效性的证据，而非"所有技能都能涨 31 分"的保证。

六、工程意义：Agent 生态走向成熟

这是 Agent 生态走向工程化成熟的一个标志信号。之前所有人都在做"更多技能、更长 prompt、更大 context window"，NVIDIA 反过来问了一个更根本的问题：你怎么知道这些有用？

三个设计选择值得特别关注：

  1. A/B 对照实验范式。with-skill vs without-skill 的对照设计是当前 Agent 评估里少见的严谨做法。大多数评估只测"装上技能后能不能完成任务"，缺少反事实基线。
  2. 三层独立架构。静态安全检查（Tier 1）、语义去重（Tier 2）和实测（Tier 3）分离，可以快速定位问题是出在打包、重复还是执行层面。
  3. 失败闭合设计。INCOMPLETE 而非 PASS 的设计、Neutral 而非 Pass 的小 Lift 判定、以及 Tier 3 在组合报告中作为 advisory 不改变 exit code——这些设计防止了"假通过"。

七、两分钟上手

# 安装
uv tool install --python 3.13 "skillevaluator[all] @ git+https://github.com/NVIDIA/SkillEvaluator.git"

# 无 API Key 快速质量检查（任何含 SKILL.md 的目录）
skillevaluator quality-check ./my-skill

# 配置 LLM 提供商（NVIDIA Build 免费 Key 即可）
export SKILL_EVAL_LLM_PROVIDER=nv_build
export NVIDIA_API_KEY='nvapi-...'

# Tier 2 去重检查
skillevaluator context-optimization-check ./my-skill
skillevaluator similarity-check ./skills

# Tier 3 完整实测（需要 Docker + Agent CLI）
skillevaluator validate ./my-skill --full --agents codex --env-mode docker

也支持 OpenAI、Anthropic、Bedrock 和任何 OpenAI-compatible 端点（包括本地部署）。默认模型：OpenAI gpt-5.6-sol，Anthropic claude-opus-5，低成本替代 gpt-5.4-mini。

总结

SkillEvaluator 不是给你一个"你的技能很好"的安慰剂。它是给你一个诚实的测量：这个技能到底有没有用，用了多少 Token，有没有让 Agent 更可靠。A/B 对照 + 五维度评分的方法论是扎实的，但当前数据是厂商自报、无置信区间、无独立复现。

对于正在构建 Agent 技能的团队，它提供了一个可借鉴的质量门禁范式：先用 Tier 1 做静态安全检查，再用 Tier 2 查重叠，最后用 Tier 3 跑 A/B 实测。不要在没测过的情况下把技能推给生产环境。

对于整个 Agent 生态，最大的价值可能不是那 +31 分的数字，而是它确立了一个可复现的评估标准——让"技能有用"从假设变成可验证的工程命题。
