Pi / DeepSeek Harness / Codex CLI：编码 Agent 运行时的三条路线

August 18, 2026

三个开源编码 Agent 运行时，三条路线

上一篇（Pi 与 DeepSeek Harness：编码 Agent 运行时的两条架构路线）对比了 Pi 和 DeepSeek Harness。本文把 OpenAI 开源的 Codex CLI（Rust 实现）纳入，形成三方格局。三者在「让 LLM 在循环里调用工具、管理状态、可扩展」上走了三条清晰不同的路线。

二、核心循环：同一种采样循环，三种层级粒度

三者本质都是同一个「采样循环」——模型 → 工具调用 → 执行 → 回填 → 再请求。差异在层级粒度：

  • Pi：只有 turn（一次 LLM + 工具执行），双层循环（外层 follow-up、内层 turn），无 step 概念。
  • dsh：turn/step 双层，step 持久化，turn 可「零 step」。
  • Codex：run_turn 是采样循环，有明确的 Thread/Session/Turn/StepContext 四层。循环逻辑写得最直白：每次 sampling request，模型返回 function call（执行并回填）或 assistant message（记录历史、turn 完成）。

Codex 的 Thread 才是会话单元，Session 是共享给根线程和所有 subagent 的运行时——这为多 agent 提供了 Pi 和 dsh 都没有的原生层级。

三、状态模型：信任锚点的分化

这是三者最本质的分歧：

项目真相来源持久化方式
Pi内存 _state.messages副作用式（订阅事件落盘，内核不感知）
dshappend-only SessionEvent 日志事件溯源（log 即真相，deriveMessages() 投影）
CodexSQLite thread-store + RolloutItem数据库持久化（含 migration/物化/归档）

Codex 走第三条路：把 RolloutItem（历史单元）写进 SQLite，并带一整套工程化配套——历史迁移与回滚、历史物化、分页 fork、归档。这对应三者定位：Pi 要「可嵌入的简单内核」，dsh 要「log 可重建一切」，Codex 要「生产级会话恢复 + 分页 + 迁移」。

四、扩展模型：抽象层级在升高

4.1 Pi：单一事件总线 + 返回值（pipe）

ExtensionAPI 的 on(event) + registerTool/Command/Shortcut/Flag/Provider，11 个 emitXxx 写死 6 种语义（通知/短路/链式/字段合并/就地 mutate/累积），本质是单向 pipe。

4.2 dsh：类型化事件 + next() 委托（around）

Cordis 插件 + ctx 服务注册 + 统一 3 种分发（emit/waterfall/serial），waterfall 是洋葱 around，监听器可短路、透传、改写下游结果。

4.3 Codex：trait 贡献者 + 四层扩展面

Codex 的扩展机制最复杂，因为它同时有四层：

  • Hooks（配置驱动的进程外钩子，Claude Code 风格）：pre_tool_use、post_tool_use、session_start、user_prompt_submit、stop、compact、permission_request——由配置文件触发 shell 命令/MCP，与 Pi/dsh 的「进程内代码扩展」根本不同。
  • Extension contributors（Rust trait，代码级）：ExtensionRegistry 持有各类 Vec<Arc<dyn Contributor>>，分三类——生命周期通知（thread/turn/tool lifecycle，回调返回空）、收集型（context/tool/mcp，host 遍历收集）、短路型（approval_review，第一个 Some 赢）。
  • MCP servers（工具协议）。
  • Skills（技能）。

最关键的差异是依赖注入方向：Codex 的扩展通过 Capability trait 从 host 拿到能力——ExtensionEventSink（发事件）、ResponseItemInjector（注入响应项）、AgentSpawner（spawn 子 agent）、ConversationHistorySnapshot（读历史）。这种「能力反向注入」Pi 和 dsh 都没有这么显式。

4.4 三方分发语义

项目扩展点声明分发语义能力注入
Pion(event) 字符串 + 返回值每事件手写（pipe）无（ctx 对象）
dsh类型化事件（声明合并）统一 3 种（around）无（ctx 服务）
CodexRust traithost 显式遍历/短路/通知Capability trait 反向注入

Codex 用 Rust 的编译期 trait 取代了 Pi/dsh 的运行时事件。好处是类型安全、无字符串事件名、分发语义由 host 显式决定；代价是扩展必须编译进二进制，不像 dsh 插件可动态加载，也不像 Pi 扩展可热重载。

五、工具执行与安全

Codex 在这一维度明显更「生产化」：工具层有 ToolRouter + 并行 ToolCallRuntime、工具发现/搜索/建议、插件安装；安全层有远程 exec-server、linux-sandbox（landlock/seccomp）、执行策略、网络策略、审批策略、guardian。相比之下，Pi 明确「无内置权限系统」，dsh 靠 capability seam + Landlock launcher。

六、结论

三个项目恰好构成 agent harness 的三条路线：

  • Pi：最小内核 + 单体产品，扩展是「纵向拦截」（给固定内核打补丁）。核心决策：内存态、回调/返回值事件。
  • dsh：纯插件平台，扩展是「横向替换」（连循环本身都是插件）。核心决策：事件溯源、next() 瀑布。
  • Codex：生产级单体，扩展是「多层接口」（hooks + trait 贡献者 + MCP + skills）。核心决策：SQLite 持久化、trait 贡献者 + 能力反向注入、重量级沙箱。

一个清晰的演进脉络：扩展的抽象层级在升高——Pi 用运行时事件名 + 返回值，dsh 用类型化事件 + 委托，Codex 用编译期 trait + 显式分发。而状态模型的信任锚点也在分化——Pi 信任内存、dsh 信任日志、Codex 信任数据库。三条路线对应「简单可嵌入 / 可组合可恢复 / 生产级可迁移」，没有谁更正确，只有适配什么场景。
