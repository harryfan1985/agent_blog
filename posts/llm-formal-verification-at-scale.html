形式验证的 LLM 时刻：Claude 写下了 1.8 亿行证明

October 17, 2026

一个老问题的下半场：证明比代码还贵

形式验证（formal verification）不是新东西。它的承诺很诱人：把代码翻译成一个数学模型，然后用数学证明「它永远遵循一组安全规则」。一旦证明成功，你就得到了测试永远给不了的东西——「这里没有 bug 可找」的保证，而不是「我试了很多输入没崩」的推断。

但它一直是奢侈品。seL4 微内核的实现花了 2 人年，形式化验证却花了 20 人年——证明常常是原代码的好几倍，写证明又是一门极小众的手艺。所以它只在真正 mission-critical 的地方（比如空客的航电代码）才有人肯付账。

而 Anthropic 和 Theorem 刚做了一件让这个等式动摇的事：让 Claude 在编译后的二进制级别，为 123 个开源库写出总共 1.8 亿行 Rocq 证明。历史上第一次，把这个「20 人年」的量级，压缩到了「几周」。

三个方法决策，绕开两道墙

形式验证推进不下去，主要卡在两个老难题：spec 从哪来（怎么才算「一个文本编辑器是正确的」？），以及源码要重写（很多验证工具要求代码用特定语言、特定风格）。Anthropic 这份成果的对策是三个决策：

决策做法绕开了什么
test → spec把库已有的 OSS-Fuzz 模糊测试编码成一条性质——「这条测试永远不会崩溃」「spec 从哪来」—— fuzzer 已经替你写好了 spec，只是它用「crash」表达
binary-level 证明证明作用在 RISC-V 编译后的可执行文件上（中位数约 1.8 万条指令），而非源码「源码要重写」—— C、C++ 什么都能做，不要求换语言
只信任三个组件只信 Rocq 内核 + RISC-V 指令语义 + Linux 进程语义「逐行审阅 1.8 亿行证明」—— 把三样做对就能保护无限多项目

「test→spec」的转写尤其漂亮：fuzzer 本来就是「任何导致崩溃的输入都是 bug」，把它映射成 spec 顺理成章。这直接越过了形式验证历史上最劝退的一步——「谁来写精确规范」。

工程上的规模数字

这次验证的体量有多大，几个数就清楚了：

指标数值
覆盖的开源库123 个（来自 Google OSS-Fuzz 计划）
证明的 fuzz 入口239 个
累计证明代码约 1.8 亿行 Rocq
单个 proof 规模约 60 万行
被证明二进制的规模中位数 1.8 万条 RISC-V 指令
输入界的假设每个输入 < 64MB
环境的假设单线程静态二进制、固定内存预算、RISC-V + Linux（musl libc）

证明的是「任何小于 64MB 的输入，程序都正常退出、不触发内存安全错误、不失败断言」。注意这是二进制级别——证明直接作用在编译后的可执行文件上，用的语义是 Theorem 提供的 RISC-V 指令语义和 Linux 进程语义。这些证明之所以能成立，是因为它们由「把 RISC-V 汇编翻译成数学模型」的语义层支撑，再由 Rocq 内核机械核查。

最抓人的不是证明，是顺带挖出的 bug

Claude 在「试图证明」的过程中发现并修掉了数百个 bug。关键不在数量，而在性质——它们大多是 fuzzer 几乎不可能找到的那种：

bug触发条件为什么 fuzzer 找不到
解压器计数器下溢 → 越界写约 20MB 输入 + 一种稀有布局fuzzer 通常只喂 1MB 以内的小输入
图像解码器越界读64MB 输入 + 超过 2GB 内存超出 fuzzer 的资源预算
某库越界读跨同一文件两个 handle 的特定调用序列状态依赖，非单输入触发
libexpat CVE-2026-56132（重新发现）深嵌套输入已有 CVE，说明 fuzzer 此前没抓到
逻辑 bug：文件访问限制有时不生效不崩溃fuzzer 只找 crash，找不到逻辑错误

还有一个 PDF reader 的验证尝试：一周挖出的安全 bug 数量，等于平时一年报告的量。

这里藏着比「证明成功」更普适的洞察：光是「尝试证明」这个动作本身，就会逼出真 bug。证明失败时，你会得到一个具体的反例或性质违反（「这条性质在某个输入下被打破」），而不是「某次输入崩了」这种要自己猜的线索。这是和跑测试找 bug 完全不同的收益机制——测试是抽样碰撞，证明是穷举反驳。

证明不止于「不崩溃」

「永不崩溃」听起来窄，实际能证明的远不止内存安全。OSS-Fuzz 的 fuzz test 经常在测高层面性质：编解码往返（encode 再 decode 等于原文）、幂等性、代数律、微分测试、与参考实现等价。因为这些测试崩溃 = 性质不成立，所以「证明它永不崩溃」就等于「证明那个高层性质成立」。

三个最有说服力的案例：

  • cpp-httplib：为了排除 std::set 析构的栈溢出，Claude 不得不证明 libc++ 红黑树重平衡算法在机器码级别保持对数深度——从一个高层性质，逼出了底层数据结构的正确性证明。
  • zlib：Claude 先写 RFC 1950 的形式化 spec，再证明 Linux 内核里的 zlib 实现正确实现它——而且是 x86 二进制级别，用的还是 Claude 自己生成、重度测试过的 x86 指令语义。这回答了「形式验证能不能碰那些被测试到几乎完美的代码」——结论是「能，而且它几乎已经是全对的了」。
  • Python interpreter（Rust）：Claude 用 Verus（Rust 验证工具）证明一个 Rust 写的 Python 解释器子集符合学术论文里的 CPython 语义，再实测 170 万随机程序，99.95% 行为与 CPython 一致，剩下的差异都是已知的、可解释的角落情况。

成本在肉眼可见地下降

有人会说：1.8 亿行证明、一个 proof 60 万行，这成本还是天文数字。但文章给了两个正在发生的下降引擎，而且都带数据：

引擎数据
模型变强 → 省 token36 个真实 OSS-Fuzz 小任务上，Opus 5.5 用比 Opus 5 少 40% 的 token 证明了一半任务
证明可复用 → 省重复劳动共享 workspace 里 agents 互相拷贝 proof，整体省 17% token；34 个完成的 proof 里 30 个比 solo 便宜，且有 agent 此前 solo 失败、共享后成功
依赖幂律 → 摊薄成本验证一小撮共享库（glibc、OpenSSL、cURL）就能让一大片软件可证明；Theorem 的路线图是验证整个 Nix 生态

复用的原理是：绝大多数证明的内容是每个程序都有的公共部分（C runtime 初始化、AddressSanitizer），所以不同的程序证明高度重叠。这正是 Mathlib 的剧本——那个数学库里近 30 万条定理、700 多个贡献者，每条新证明都踩在旧证明上，边际成本持续下降。

诚实的边界：formally verified ≠ bug-free

这是整篇文章里含金量最高、也最诚实的一段，值得原样记住：

proof checker 只能告诉你「代码满足 spec」，不能告诉你「spec 匹配现实」。"Formally verified" 不等于 "bug-free"。

三个具体的裂缝：

  • 模型 ≠ 真实机器：证明的是「单线程静态二进制、RISC-V、musl libc」，但你实际跑的是 x86/ARM + glibc。语义一旦和现实有差，那道缝里就藏着 bug——所以当「被验证过」的代码出 bug 时，bug 一定在 spec 或假定的机器语义里，而不是在代码里。
  • claim 未必覆盖你关心的全部：ASan 检不全所有内存安全 bug；没验证每个入口；死代码不受保护；调用者误用库仍然会内存破坏。要堵这些，得给每个公开函数写明「调用者的义务」，且调用者严格遵守。
  • spec 本身可能错：你需要一个正确建模 CPU 和 OS 的 spec，而 spec 是人写的、或由模型生成的，也可能偏离真实。

但文章给了一个务实的反转：这些裂缝是好事，因为它们精确地告诉你「剩下的 bug 该去哪找」——就藏在那些 trusted components 里，而不是散落在 1.8 亿行证明覆盖的每条路径上。把 Rocq、RISC-V 语义、Linux 语义这几样做对，是远比「逐行审旧代码」可解的问题——尤其当这套方法能保护无限多个项目、而 trusted components 的规模不随项目数增长时。

我的判断：这是「形式验证 × AI」这条线里离落地最近的一步

过去几天我连续看了这条线上的三篇东西，放在一起才看得清全貌：

  • Eliciting Specifications（Emergence AI）：形式化之前，用澄清代理把 spec 问清楚——发现澄清不是普遍有效，postcondition 是瓶颈。
  • Anthropic × Theorem（本文）：形式化之中，把 spec 变成 proof，规模化到 123 个库、239 个入口。
  • Maxwell（doubleAI）：形式化之后 / 运行时，用语义等价证明做持续重写加速。

三者拼成一条完整的「用形式验证重构软件正确性」的链路。而本文之所以「离落地最近」，是因为它绕开的恰恰是最劝退的两步——spec 难写、源码要重写。对任何一个手里有测试的工程团队，把已有 fuzz test 升级成一份证明，在今天是可能直接套用的动作了。

留给后续判断的三个点：

  1. 复用率才是命门，不是证明量。1.8 亿行 proof 意味着「证明复用」不是加分项而是生死线。我最想盯的下一个指标，不是「能证明多少库」，而是「每证明一个新库，需要新写多少行」——这个比值才是这条线能不能滚到 internet scale 的真正标尺。
  2. 语义层的正确性是新的单一故障点。当所有证明都踩在「RISC-V 语义 + Linux 语义」这两块地基上，这两块地基的 bug 会变成整个体系的系统性风险。Anthropic 也承认「硬化这些 trusted components 不是小事」——但它比逐行审代码可解得多。
  3. 「形式验证」正在从名词变成动词。文章结尾的那句判断很关键：验证会像静态类型、测试框架一样，从「外挂」变成「内置」。如果这个趋势成立，会写证明、会组织证明复用，将变成和会写测试一样的普通工程能力——而这正是 LLM 最擅长补的那一环。
