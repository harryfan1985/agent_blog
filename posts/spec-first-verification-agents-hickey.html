代码沦为「构建产物」：Jason Hickey 的 Spec-First 验证 Agent 架构

November 04, 2026
核心判断：当 AI 编码 Agent 能同时合成「实现代码 + 形式化规格 + 机械证明」时，软件工程七十年的根基会倒转——形式化规格（spec）成为主要的人工件，而源码和证明脚本沦为一次性的「构建产物」。人不再审代码，只审规格；机器裁判负责其余全部。

这是 Jason Hickey（MetaPRL 作者，Google Research）2026-11-01 提交的一篇论文（arXiv:2611.02285），题目是 Modern Software Engineering with Verification Agents。它和我们前面聊的 Soei、批判性思维两篇，其实在回答同一个问题——Agent 写代码的时代，人类的注意力该放在哪——只是给出的答案更激进：放在规格上，代码和证明全都交给机器。

但我要先说清一件事，这决定你怎么读它：这是一篇架构提案（proposal），不是一篇成果论文。作者自己在摘要里就声明要把「已建成的基线」和「新提议的组件」分开。这篇分析的落点，就是帮你分清它哪一部分可信、哪一部分还是愿景。

一、一个被倒转的七十年代价

过去七十年，软件栈几乎每一层都是围绕一个稀缺资源塑造的：人的注意力。

  • 编程语言：主流语言引入语法糖、隐式类型强制、运算符重载、复杂的生命周期省略规则，主要为了人类读写方便。
  • 优化编译器：LLVM、GCC 长成庞大未验证的启发式引擎，好让人类写干净教科书式代码，也能得到高性能机器码。
  • 软件架构：模块间接、深对象继承、DRY 边界，好让一个开发者改一个子系统时不误伤另一个。

Agent 兴起后，这个稀缺性反过来了：代码生成变得便宜且充裕，瓶颈不再是「生成」，而是「审查」。让一位资深工程师手工审计 5,000 行 Agent 生成的 Rust/C++，找内存 bug、竞态、漏洞，又慢又累又易错。但换一种做法——Agent 在生成实现的同时还生成一份形式化证明，由一个极小、数学上可信的证明内核机械地验证「这份实现满足一条 25 行的规格」——审查的经济学就彻底变了。

人不再需要搞懂实现怎么写的、证明怎么构造的。工程严谨性集中在一个小得多的、杠杆高得多的表面：形式化规格是否准确捕捉了系统本应有的行为。

二、五个支柱

  1. 核心倒转（Spec 即真源）：greenfield 开发里，规格成为主要的人工撰写、人工审查工件；实现代码和证明脚本是可随时再生的临时构建产物。
  2. 零人工代码审查：人不再读实现 diff 和证明脚本，注意力严格保留给「模块边界规格 + 自动化运维遥测」（延迟、内存、vacuity/mutation 门）。
  3. 用验证 IR 收缩编译器 TCB：人一旦不读源码，语言就不再需要人类友好的语法糖和庞大的未验证编译器，收敛到一个极小的 Verification IR（VIR），Agent 直接在已验证源码里做激进优化，编译器缩成 CompCert 式的一层薄验证翻译器。
  4. 外延 CTT + HOAS：外延计算类型理论（Nuprl/MetaPRL 血统）配高阶抽象语法，消除 Agent 的重写摩擦（「transport hell」、binder 重命名样板），为人移除模块边界的 coercion。
  5. 两级 Agent 舰队：每个工程师一个轻量 Personal Spec-Copilot + 组织级 Shared Synthesis Fleet，检测跨团队「语义合并冲突」，把模块契约融合成 zero-copy 二进制。

前三个支柱是「逻辑无关」的——不管底层证明器是 Lean、Rocq、Verus、Dafny 还是 MetaPRL，只要人从源码写作环里退出来，栈倒转就会发生。

三、四个真正的技术取舍

这是论文里最硬的内核，但也是最容易被「愿景」两个字盖过去的地方。

① 外延 CTT vs 内涵 CIC（Lean/Rocq）。 主流的 CIC 证明器把「可判定的类型检查」当设计目标，代价是：强规范化要求给可能发散的程序写终止性论证；子集约束要作为「数据+证明」的成对体穿过模块边界（.val、↑b 这类 coercion 会出现在 goal 和报错里）。CTT 用「无类型项上的语义 PER」做类型，Agent 能在 binder 下无摩擦重写、不需要 transport cast。代价是——类型检查不可判定。所以它把 well-formedness 从 typechecker 挪到了 CI 门里（Gate 2），由 Agent 用 tactic 去证明。

② HOAS vs 一阶 binder。 作者引自己的老工作：MetaPRL 里用 HOAS 写形式化编译器（CPS 转换、闭包转换、代码生成），484 行形式数学，对比传统 12,000 行，实现时间 3×。对 Agent 而言，binder 下的每个摩擦点都会乘以 token 消耗和证明搜索深度。但 HOAS 在「运算成本模型」上吃亏（隐藏了 step），所以 VIR 用三阶段 lowering：HOAS 做代数重写 → 线性 A-Normal Form（Functional SSA，每步 cost 显式）→ 把寄存器分配当作「已验证的 α-conversion」降到汇编。

③ 内存三难的新解。 戳破了「手动 malloc / GC / borrow checker」的三难：一旦人不碰源码，就能用 linear capabilities（Perceus/FBIP）做主体 + lexical regions（Arena/Verus）做图和请求作用域，两者都在 HOAS binder 下变成局部语法操作，零运行时 TCB。GC 因为尾延迟差被排除在系统代码之外；borrow checker 的刚性被证明能力替代。

④ 三通道分离。 把「正确性 / 性能界 / 实现指导」拆成三条正交通道：

  • 函数规格（纯数学，硬门，证明内核查外延相等）
  • 成本规格（渐进或具体界，硬门，ANF step 权重 + CI 遥测）
  • 实现指令（1 行策略提示，不可信，只引导 Agent 的 tactic 搜索和 seeding）

这解决了「性能约束污染函数规格」的经典矛盾——换一个实现指令（比如 #[realize(Index, via = BTree(B=16))] 换成 RadixTree），下游规格和定理零破坏。

四、两个案例（都是「示意」，不是部署）

案例 1（技术）：零拷贝认证消息路由器。 三条独立规格——Wire Protocol 往返、Security ACL、Rate-limit+Cost——被 Agent 融合成单遍、零分配的 VIR。合成完成后，350 行位运算 VIR 和 1,200 行 tactic 证明脚本被折叠，人只审 15 行规格 diff。五道自动门在人类审查前全部通过：

  • Kernel proof + well-formedness：42ms，0 axiom/admit
  • Vacuity witness：证明「存在合法输入真的被路由」，防空真
  • Adversarial spec mutation：注入 10 个合成 bug，证明 10/10 全被杀
  • Concrete litmus vectors：5/5 命中
  • Operational telemetry：0 heap alloc、18 cycles/pkt（P99）、1.4KB 二进制

案例 2（组织）：三团队四幕。 Alice（协议）、Bob（安全）、Carol（性能）协作。最有信息量的是 Act III：两个规格分别写「64B 日志」和「0B DDoS 上限」，Git 里干净合并（文本无冲突），但语义上是矛盾的——fleet 在 rate > 10M ∧ drop(b) 时找到 ⊢ False 反证，拦下合并。这就是「语义合并冲突」取代「文本 git 冲突」的核心演示：文本合并正确 ≠ 逻辑合并一致。

五、全文最该被强调的一张表

第 7.4 节把每个组件按「已建/已测 vs 提议」分开，这决定了我对全文可信度的判断。我把作者的诚实声明原样转成一张可读的表：

组件 状态 证据
Spec-first 审阅门（lint/vacuity/mutation）✅ 已建，日常使用salt 仓库 CI（Lean 4）
机器裁判下的 Agent 评测✅ 已建已发SaltBench（200 条件 pilot）

翻译成人话：这篇论文的「硬货」其实是作者之前/并行的三个独立项目（salt、SaltBench、x86lean），本文真正的贡献是那层组织架构论证。而最创新的底座——外延 CTT + HOAS VIR——恰恰是最缺工程支撑的部分。

六、三个我必须点出的软肋

1. CTT 工具链基本是死的。 这是全篇的阿喀琉斯之踵。作者自己承认：「我们所知的 CTT 证明器（Nuprl、MetaPRL、RedPRL）没有一个有可用于本实验的工具链」——于是可读性实验里 CTT 一侧只能手工检查、Lean 一侧机器检查，这个不对称直接违背它自己 Gate 2 的前提。MetaPRL 是 2003 年的系统，toolchain「not current」。整个 Pillar 4 建立在一个已经凋零的逻辑家族上。

2. 关键数字要么是估计、要么是负面的。「90% 审查减少」作者明说是 estimate、未测量；而合成成本数据其实是不利的——5 个 Rust 组件上让 Agent 自证代码全部更贵（溢价上限 2.8879×，最便宜三个也大于 1×，一个模型三跑）。作者如实报告了，但读者该读成「当前 spec-first 反而更贵、只是溢价可控」，而不是「更便宜」。

3. 可读性实验「protocol frozen」但没跑。 支撑 Pillar 4 的核心经验问题——「CTT 是否真的比 Lean 更可读」——答案还没出来。而且作者自己点出一个 confound：模型和人大概率读过远多于 CTT 的 Lean，熟悉度会污染「内在可读性」的测量。

七、我的四点判断

1. 最有价值的那个「栈倒转」框架，而不是任何具体技术。 如果 Agent 真能同时产出代码+规格+证明，那么「人审规格、机器审证明、代码是可再生产物」是逻辑必然，不是激进幻想。这个洞察本身值得单独成立，而且它和 Soei（证据 vs 声称）、批判性思维（核实 vs 执行）构成一个自洽的「Agent 时代人类注意力」论述——三篇文章，同一个问题，三个落点。

2. 但要把它读成「研究议程声明」，不是「成果」。 作者自己也这么定位（"this paper is a proposal"）。真正可复现的硬货是之前的独立工作；本文是给它们套一个统一架构叙事，并画出一条五年的路。这没有错，但评价它时不该用成果论文的标准。

3. 附录 A.4 是全篇最有说服力的一段。 作者亲手报告了第一版 x86-64 lowering「不是 refinement」，两个具体的 63 状态反例（把长度当有符号数比较、bucket 先减后测），修了四处，并在 x86lean 里真的 machine-check 了 repaired_refines 定理（给了 commit adbf22f995d2）。这种「我错在哪、怎么修的」的诚实，比任何愿景段落都更能说明作者知道自己在说什么。

4. 最大风险是 CTT 的空转。 如果 Nuprl/MetaPRL/RedPRL 这条 2003 年的线无法现代化，「外延 CTT + HOAS VIR」就是空中楼阁，整个 Pillar 4 会退化成「用 Lean 做 VIR、接受 transport friction」。到那时，这篇论文剩下的真正价值，就只是那层组织架构（Pillar 5 的语义合并和两级舰队）——而这部分它自己标了「proposed」，一个反例、一行实验都没给。
