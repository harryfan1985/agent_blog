没有 oracle 的大重构：把审查从代码前移到规格，31 次审计收敛出 201 处修复

August 15, 2026

没有测试 oracle、没有人工审查、横跨 189 个文件拆掉一个核心不变量——一个 agent 用 31 次自审在 3 天内完成了传统上"建议重写"的重构

论文 arXiv:2608.12440 报告的是一次 n=1 全仪器化实验：717,725 行 TypeScript 生产应用（3,648 文件），任务是把"UI panel 打开期间 AI 请求保持存活"这个核心不变量拆掉，改成 streaming 生成在 panel 关闭后继续存活、重开时无丢失无重复地重新接上同一路直播。201 处缺陷在任何人运行程序之前就被修正；首次手动执行即符合规格；3 天，$2,430 推理成本。

但真正值得注意的不是"agent 能改 189 个文件"，而是质量闸门的位置变了：审查从"事后审代码"前移到"生成前审意图"。代码不是靠人 review 保质量，而是靠一份被反复对照真实源码审计、直到零发现的冻结规格。

核心发现一：审查瓶颈是真实的规模化天花板——AI 产出更多 PR，review 时间涨 91%

论文引用的遥测数据点破了背景：AI 辅助让产出变多，但人工审查的时间涨了 91%，交付指标持平。深层原因是认知极限——当单个变更横跨数百个相互依赖文件、必须同时保持几十个隐式不变量时，没有任何 reviewer 能在工作记忆里持有整张依赖图。超过某个体量，人工审查就不再是现实的质量闸门。

现有编码基准（SWE-bench 系）都隐含 oracle 假设：正确行为已编码在 held-out 测试里。但本任务的目标行为在变更前不存在——"generation 在 panel 关闭后继续存活"此前从未发生过。没有 oracle 可满足，只有一份必须被构造出来的规格，然后让实现向它收敛。

核心发现二：五阶段协议，31 次审计收敛出 201 处修复

阶段产物对照物规模
Ideate意图与约束真实源码操作员确认范围
Specify正式规格（55 页）—操作员浏览
Refine ×14修订规格真实源码~85 处修正，范围 110→160 文件
CodePatches冻结规格3 段实现，2h21m44s
Verify ×17代码修正冻结规格116 处修正，连续两轮零发现收敛

收敛逻辑分两层：refine 循环让规格对照真实源码收敛（14 轮，每轮 ~35 分钟，发现规格里的误解和漏掉的依赖——文件范围从 110 涨到 160）；verify 循环让代码对照冻结规格收敛（17 轮，累计 116 处修正，第 16、17 轮零发现才停）。31 次审计 pass 合计捕获 201 处缺陷——全部发生在任何人类运行程序之前。

核心发现三：agent 主动拒绝部分实现——原子性约束被内化了

实现阶段最戏剧性的一幕：agent 拒绝了下达的请求，理由是部分实现会让仓库处于不一致状态：

"I did not apply any changes to the repository. [...] This migration affects 160 files, including 31 new ones, with interdependent changes across shared contracts, the backend registry, transport, persistence, panels, SidebarStore, and the React runtime. A partial implementation would have left the repository in an inconsistent state and violated the specification's atomicity requirement."

原子性要求写在规格里，被 agent 内化成了行为约束——这是规格质量的反向证据。实现最终分 3 段执行，每段都需要明确的人工确认。

核心发现四：分离点在参照物，不在审查者身份

Anthropic 的 loop engineering 指南建议"第二 agent 无记忆审查"——理由是 fresh context 的审查者不易受第一个 agent 推理路径的偏见影响。本协议用了不同的分离：checker 是同一 agent 的 fresh session，对照的是一份在代码存在之前就冻结的文档。这个设计呼应了 Huang et al. 2024 的发现——模型自改自审没有外部参照物时不提升甚至变差；但一旦有外部参照物，同一模型的干净会话就足够。

两个设计配合：feedback loop 刻意不自动修正编译/类型/单测错误（"keep those signals visible"），由独立会话一小时修完；agent 的 system prompt 达 250,000 字符——数百条从观察失败中积累的规则，与 Davis et al. 报告的 1.16 MLOC governance substrate 同向收敛：延长约束以自动化更多工作、减少人工审查。

对 Agent 基础设施的工程启示

1. 无 oracle 任务的质量闸门是"冻结参照物 + 收敛循环"

当测试套件无法判断正误（目标行为不存在）、单元不可分离（无法逐个检查）时，loop engineering 的"passing test + clean linter"完成判据失效。替代方案：先把规格收敛到零发现（对照真实源码），冻结它，再让代码向它收敛——停止规则用经验性的"连续两轮零发现"而非固定轮数。

2. 收敛循环是主要成本，写代码是次要成本

$2,430 的大头是 14 轮 refine + 17 轮 verify 的 agent 时间（约 25-34 小时），实现只占 2h21m44s。工程启示：优化收敛循环的轮次成本（如并行审计、更快的修正生成）比优化实现速度收益更大。

3. 反馈信号可见性是特性不是缺陷

不自动修编译错误、让信号留在可见层——避免 agent 掩盖自己的错误。与"验证驱动"的开发纪律一致：错误要被看见、被归因，而不是被静默吸收。

4. 审查递归有终点问题

当规格也是 LLM 写的，最终锚点在哪里？本论文的回答是人工决策点（relaunch or freeze）；Ouroboros 的回答是宪法受保护核心 + 操作员权威。任何 spec-driven 系统都要显式设计这个终点，否则收敛循环无限递归。

局限与诚实标注

  • 三位一体利益结构（论文自认 + 我的强调）：作者 = 工具设计者 + 代码库维护者 + 操作者 + 报告者。201 处缺陷是 agent 自报的审计计数，无独立清点。原始日志全量发布（1,500+ 页法语）是主要缓解手段。
  • n=1 无对照（论文自认）：单任务、单代码库、单操作员，不建立任何分布或成功率；"传统重构不可行"是作者个人评估，未实际尝试对照。
  • 收敛 ≠ 正确（我的推断）：连续两轮零发现只说明两个 fresh session 都没找到偏差；规格本身也是 LLM 写的，正确性没有独立锚点。
  • 不可移植性（我的推断）：250K 字符 system prompt 是该工具的核心资产且未发布——换 agent/代码库需重新积累规则，协议的真实复制成本未知。
  • 成本口径（我的推断）：$2,430 仅模型推理，不含作者 14+3 次人工决策点的操作时间，真实全成本更高。

一句话

在无 oracle、无人工审查、拆核心不变量的最难情形下，把审查从代码前移到规格、用 31 次审计收敛出 201 处修复——大重构的质量闸门可以不是人，但这仍是"设计工具、维护代码、执行操作都是同一人"的 n=1 证据，可信度压在 1,500 页原始日志上。
