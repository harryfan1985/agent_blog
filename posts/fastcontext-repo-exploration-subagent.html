FastContext：把仓库探索从编码 agent 里拆出来，token 省 60% 还能多解 5.5% 的题

August 8, 2026

56.2% 的回合在找代码，46.5% 的 token 在买"噪音"——微软把仓库探索从求解主流程里拆了出来

编码 agent 的钱都花在哪了？微软 CoreAI + 上海交大对 300 条 GPT-5.4 完整轨迹的审计给出一个反直觉的答案：读文件和搜代码占了全部 tool-use 回合的 56.2%（9.96/17.72 回合），消耗主模型 46.5% 的 token——而真正决定成败的编辑只占一小部分。更糟的是，探索是编辑前的一段"漫长的顺序前奏"：中位数实例要 6 个顺序探索回合、15.5 次探索工具调用，才等到第一次源码编辑。

FastContext（arXiv 2606.14066）把这段探索从主 agent 的轨迹里整体剥离：一个按需调用的专用探索 subagent，用 4B–30B 的小模型，返回紧凑的 file:line-range 证据块，而不是一整条探索历史。端到端效果：SWE-bench Pro 上 GPT-5.4 从 46.0 提到 51.5（+5.5），token 最多降 60.3%。

⚠️ 注：该论文 v4（2026-06-30）已被撤回，arXiv 备注"涉及产品 IP 问题，需撤回重新审批"，官方代码仓库 github.com/microsoft/fastcontext 不存在。本文基于 v1 全文分析。

先量化病，再动刀：探索到底贵在哪

论文的初步分析（Figure 2）把 300 条 GPT-5.4 轨迹的每次工具调用按 read/search/edit/test 分类，得到三个硬数字：

  • 56.2% 的 tool-use 回合是读和搜（9.96/17.72）——不是编辑，不是测试
  • 46.5% 的主模型 token消耗在探索上——直接对应推理成本，且这些上下文会被 agent 一路扛到底
  • 未解决实例探索更久：首个编辑前的探索回合 8.34 vs 6.67（解决实例）——难题需要更多搜索，但这份搜索量也正在拖垮 solver

结论很工程化：探索既贵到影响成本，又结构化到可以外包——这就是 FastContext 的存在理由。

Delegation contract：三个只读工具，一个紧凑答案块

FastContext 刻意保持接口最小化，只暴露三个语言无关的只读工具：

  • Read：带行号的文件内容读取
  • Glob：路径发现
  • Grep：基于 ripgrep 的正则全文搜索

每回合 explorer 可以并行发多个工具调用（覆盖互补假设），最后输出一个 <final_answer> 块，例如：

<final_answer>
/src/router.py:42-58 (Router definition)
/tests/test_router.py:101-119
</final_answer>

主 agent 消费这份 file-line 证据直接进入编辑阶段，探索的完整历史留在 subagent 的轨迹里，不进 solver 的上下文。

训练配方：SFT 学行为，RL 锚定任务

小模型不会天生会探索，训练分两段：

① SFT 初始化（2,954 例，来自 Sonnet 4.6 轨迹）——关键设计是把监督按运行时行为拆成三个来源：

  • parallel_toolcalls：训练"第一回合广撒网"——给查询+目录列表，要求发出覆盖路径模式/符号/入口点的非冗余并行调用
  • multiturn_traj：训练多回合证据收集——保留完整参考轨迹（含工具观测）
  • linerange：训练精确引用——给已取回的文件内容，只输出窄 <final_answer> 块

② RL 精调（400 prompts, GRPO）——reward 完全锚定输出契约：

R = F1(file) + F1(line) + r_parallel − r_format

目标文件/行集合从参考 patch 解析而来；r_parallel 奖励有界的多调用探索；r_format 惩罚空/过长/畸形/过度 fan-out 的输出。跑在 4B 模型上的 RL 版本（4B-RL）在多个设置里超过了 30B-SFT——任务锚定的优化比单纯的规模更值钱。

规律清晰：主 agent 越啰嗦（GLM-5.1 基线 2.5M token），FastContext 省得越多；主 agent 越强越短（Kimi-K2.6），节省越小但精度仍涨。SWE-QA 是纯问答任务，探索占比最大，所以 token 节省最夸张（−60.3%）。

Standalone 定位质量：不只是省钱，找得更准

用 SWE-bench Verified 的 patch 推导出参考位置，单独评测探索器：训练后的 FastContext 4B-RL 达到 file-level F1 71.48、module-level 56.26；30B-SFT 到 73.71/60.35，超过最佳非 FastContext 基线（CodeScout-14B 的 68.57/50.88）。差距在 module/function 粒度最明显——证据被收窄到真正相关的代码区域。

成本审计更直白：GPT-5.4 主模型整轮 Multilingual 从 $282.47 降到 $208.92，4B-RL 探索器全程只花 $4.52（按 serverless $0.20/1M token 估算；本地部署则这笔都不花）。

对 Agent 基础设施的工程启示

  • 探索是独立可训练组件，不是 solver 的隐性成本——把探索从求解轨迹剥离，同时降本和提准，说明 context boundary 本身就是一种架构决策
  • 最小 delegation contract 有效：3 个只读工具 + 结构化输出块，比给 subagent 完整 shell 更可控，输出直接可被主 agent 消费
  • 任务锚定 reward 是性价比路径：4B + GRPO + patch-derived F1 就能超过 30B 纯 SFT——对小模型本地部署是强信号
  • 与 SWE-Pruner Pro 互补：Pruner 裁剪主轨迹里"已读但没用"的内容，FastContext 让探索内容根本不进主轨迹——一个事后清理，一个事前隔离

局限

  • 只集成 Mini-SWE-Agent 一种框架；只测强主模型（GPT-5.4/GLM-5.1/Kimi-K2.6），未验证 30B 级主 agent
  • 撤回状态（IP 问题）意味着方法可能已产品化，benchmark 数字需谨慎解读；作者也自述存在 benchmark overlap 风险
  • 主 agent 编辑阶段仍需自己读文件——FastContext 只砍探索阶段
  • 官方代码未发布，复刻需从附录 recipe 自行实现（SFT 数据构造 + GRPO 训练管线）
