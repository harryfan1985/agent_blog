端侧小模型 Harness-Aware 后训练技术路线

August 27, 2026

当前业界正在形成一个非常明确的方向：

端侧小模型的后训练，不再是"先把模型训好，再找个 Agent Harness 去套"；而是把 Harness 直接变成后训练系统的一部分。

如果结合 2025–2026 年公开方案，主流技术路线已经从 Model-Centric Post-training 演进到 Harness-Centric / Harnessed Agentic RL。

一、核心架构：Harness 从推理外壳变成训练环境

传统链路是：

Base Model
   ↓
SFT / DPO / RL
   ↓
Deploy Model
   ↓
Agent Harness
   ↓
Tools / OS / App / Device

现在越来越多方案是：

                  ┌─────────────────────────┐
                  │      Agent Harness      │
                  │ Context / Tools / State │
                  │ Retry / Recovery / Plan │
                  └───────────┬─────────────┘
                              │
                        Agent Execution
                              │
                      Token / Action Trace
                              ↓
┌────────────────────────────────────────────────┐
│                Post-training Loop              │
│                                                │
│   SFT → Distillation → On-policy RL → Eval    │
│    ↑                          │                │
│    └──── Failure / Reward ────┘                │
└────────────────────────────────────────────────┘

核心变化：

Harness 不再只是：

  • Prompt 组装器
  • Tool Router
  • Runtime Controller

而变成：

  • Trajectory Generator
  • State Environment
  • Reward Context
  • Failure Signal Producer
  • Training Distribution Controller

这类范式已经被明确称为 Harnessed Agentic RL。近期的 Agent Lightning v1.0 将它定义为：部署期 Harness 直接参与模型后训练，从而缩小"训练环境"和"真实运行环境"之间的鸿沟。(Hugging Face)

二、当前最主流的 5 类联动机制

1. Harness 作为轨迹生成器：Harness → Post-training Data

这是目前最成熟、工程门槛最低的方案。

真实 Harness
    ↓
Teacher / Large Model 执行
    ↓
Harness 记录完整 Trajectory
    ↓
成功/失败评估
    ↓
Filter / Repair / Relabel
    ↓
SFT / Distillation
    ↓
Small Edge Model

训练数据不再只是：

Instruction → Answer

而是：

System Prompt
+ Context State
+ Tool Definition
+ Action
+ Tool Result
+ Action
+ Error
+ Recovery
+ Final Result

对于端侧模型，这是非常重要的。

因为端侧模型真正要学习的通常不是：

"如何完成任务"

而是：

如何在受限工具、有限上下文和有限算力下推进任务。

Apple 最新的 PROOF-Gen 就体现了这个方向：不仅保留 Teacher 成功轨迹，还针对失败执行轨迹进行反思和修复，把原本会被丢弃的 near-miss failure 转化成高质量训练数据，并报告了向实际部署的 on-device model 的正向迁移。(Apple Machine Learning Research)

对端侧模型的典型做法

Cloud Frontier Model
        │
        │ Generate Trajectory
        ↓
┌────────────────────┐
│  Real Edge Harness │
│                    │
│ Tool A             │
│ Tool B             │
│ Context Window     │
│ Memory Budget      │
│ Retry Policy       │
└────────────────────┘
        ↓
Teacher Trajectory
        ↓
Trajectory Compression
        ↓
Small Model SFT

关键不是让 Teacher 在一个理想环境中生成答案。

而是：

让 Teacher 在端侧 Small Model 将来真正使用的 Harness 中运行。

2. Distillation → Agentic RL：当前端侧小模型最主流的后训练配方

目前小模型直接做 RL 的问题非常明显：

Small Model
   ↓
Exploration
   ↓
大量失败
   ↓
Sparse Reward
   ↓
训练不稳定

尤其是 0.5B–4B 模型：

  • Initial policy 太弱
  • Tool call 容易错
  • 多步任务 reward 极稀疏
  • 很难自己探索到成功轨迹

所以当前越来越主流的是：

Teacher Demonstration
        ↓
Cold Start SFT
        ↓
On-policy Distillation
        ↓
Agentic RL
        ↓
Edge Model

例如 DGPO 针对 compact model agentic RAG，使用 cold-start teacher demonstration + policy optimization 中持续的 teacher guidance 来解决小模型稀疏奖励和探索困难。(ACL Anthology)

Microsoft 近期提出的 reward-density 思路也很有代表性：

Sparse Reward
    │
    ├── 更适合强模型 Exploration
    ↓
Strong Teacher Policy
    │
    ↓
Dense Teacher Signal
    │
    ↓
Small Deployment Model

也就是说：

稀疏奖励给大模型做探索，密集监督给小模型做压缩。

这可能比"直接对端侧模型 GRPO"更符合当前小模型能力边界。(微软)

3. 真实 Harness-in-the-loop RL：目前最值得关注的方向

这是未来 1–2 年最关键的演进方向。

核心结构：

┌──────────────┐
│ Small Model  │
└──────┬───────┘
       │
       ▼
┌──────────────────┐
│ Production Harness│
│                  │
│ Context          │
│ Tool Calling     │
│ Memory           │
│ Recovery         │
│ Routing          │
└───────┬──────────┘
        │
        ▼
   Environment
        │
        ▼
 Reward / Failure
        │
        ▼
 RL Trainer

这里的核心难题是：

Harness 本身通常不是 RL Environment。

Agent Harness 往往：

  • 是 Python/TypeScript 工程
  • 有自己的 Event Loop
  • 有异步调用
  • 有 Tool Middleware
  • 有 Context Management
  • 有多个 LLM Call
  • 有状态机

所以新的方案不是重写 Harness，而是使用 LLM Proxy / Harness Proxy。

Polar 的方案很典型：

Agent Harness
     │
     │ LLM API Call
     ▼
┌──────────────────┐
│   Proxy Layer    │
│                  │
│ Capture Tokens   │
│ Capture Context  │
│ Capture Action   │
└────────┬─────────┘
         │
         ▼
Trajectory Reconstruction
         │
         ▼
RL Trainer

Polar 可以把 Agent Harness 当成 Black Box，通过代理模型调用捕获 token-level interaction，并重建训练轨迹。论文报告在多种 coding harness 上训练 Qwen3.5-4B。(arXiv)

这意味着未来的核心接口可能是：

Harness
   ↕
LLM Proxy
   ↕
Rollout / Trajectory
   ↕
Post-training Framework

而不是：

Harness
   ↕
某个特定 RL Framework

4. Small Model–Optimized Harness Co-design

这是目前端侧 Agent 和传统 Agent 最大的区别之一。

大模型 Harness

可以假设：

Model 很强
  ↓
Harness 主要做组织

但端侧模型是：

Model 较弱
  ↓
Harness 必须补偿能力

所以变成：

Model + Harness = Agent Capability

而不是：

Model = Agent Capability

微软近期的 MagenticLite/MagenticBrain/Fara1.5 就明确在探索：

small model + codesigned tools + optimized execution harness

MagenticLite 的 Harness 是专门围绕小模型能力设计的，而不是把 Frontier Agent 的复杂 Harness 直接缩小。(微软)

对于端侧 Harness，通常需要优化：

A. Context Compression

Raw Context
   ↓
State Extraction
   ↓
Structured State
   ↓
Small Model

例如：

{
  "task": "Book flight",
  "current_step": 3,
  "completed": [
    "search_flight"
  ],
  "next_options": [
    "select_flight",
    "change_date"
  ]
}

替代：

10000 tokens raw history

B. Tool Surface Reduction

大模型可能看到：

50 Tools

小模型最好看到：

3～8 Relevant Tools

所以：

Global Tool Set
       ↓
Tool Router / Retriever
       ↓
Task-specific Tool Subset
       ↓
Small Model

这个 Router 本身也可能由：

  • Rule
  • Small Classifier
  • Embedding Retrieval
  • Tiny Model

实现。

C. Deterministic Harness Control

小模型不应该承担：

Retry
Timeout
Schema Repair
State Validation
Tool Recovery

Harness 应该接管。

Small Model
    │
    ├── Plan
    ├── Decide
    └── Select Action
             │
             ▼
Harness
    ├── Validate
    ├── Retry
    ├── Repair
    ├── Recover
    └── Execute

所以一个重要趋势是：

把确定性能力从 Model Weight 外化到 Harness。

这与之前关注的 Parametric vs Externalized 框架高度一致。

三、Harness 会反过来决定后训练什么

这是更重要的一层。

传统：

Training Objective
        ↓
Train Model
        ↓
Adapt to Runtime

未来：

Harness Capability Boundary
        ↓
Define Model Responsibility
        ↓
Define Training Distribution
        ↓
Post-train Model

例如：

Harness A：强 Tool Recovery

模型只需要：

Intent
→ Tool Selection

训练：

Policy Accuracy

Harness B：模型自己 Recovery

模型需要：

Intent
→ Tool Call
→ Read Error
→ Diagnose
→ Retry

训练：

Long-horizon Recovery Policy

Harness C：Context Compressor

模型训练：

Structured State → Action

而不是：

Long Context → Answer

所以：

Harness 设计实际上决定了 Small Model 的后训练 Problem Formulation。

近期研究也开始明确把 Harness Design 作为 post-training 的可控变量，而不是固定的工程细节；结果显示 harness-aware post-training 能提升分布内表现，也有助于适应任务和工具环境变化。(Emergent Mind)

四、端侧特有的一种新架构：Cloud Teacher + Edge Student + Runtime Harness

这是当前最实用的生产级结构。

                  ┌─────────────────┐
                  │ Cloud Teacher   │
                  │ Frontier LLM    │
                  └────────┬────────┘
                           │
                           │ Exploration
                           ▼
               ┌────────────────────────┐
               │   Edge Runtime Harness │
               │                        │
               │ Device APIs            │
               │ Local Tools            │
               │ Memory                 │
               │ Context Compressor     │
               │ Error Recovery         │
               └────────────┬───────────┘
                            │
                            ▼
                    Agent Trajectory
                            │
                   ┌────────┴─────────┐
                   │                  │
                 Success             Failure
                   │                  │
                   │          Reflection / Repair
                   │                  │
                   └────────┬─────────┘
                            │
                            ▼
                   Distillation Data
                            │
                            ▼
                   Small Model SFT
                            │
                            ▼
                     On-policy RL
                            │
                            ▼
                    Edge Deployment

Liquid AI 最新的 LFM2.5-2.6B 是非常典型的公开案例：

SFT
 ↓
Domain Specialist Teachers
 ↓
Multi-domain On-policy Distillation
 ↓
Agentic RL in Real Harnesses
 ↓
On-device Agent

其公开描述明确提到，Agentic RL 在真实 agentic harness 中运行，并通过 Harness Proxy 将 Harness 作为黑盒接入训练系统。(Liquid AI)

五、最新趋势：不只训练 Model，开始训练 Harness 本身

这是 2026 年刚出现、但非常重要的方向。

传统优化：

Failure
  ↓
Update Model Weights

新方向：

Failure
   ↓
Analyze
   ├── Model Problem?
   │       ↓
   │   Post-training
   │
   └── Harness Problem?
           ↓
      Patch Harness

例如：

Failure:
Model keeps selecting wrong tool

可能不需要重新训练模型，而是：

Tool Description Rewrite
Tool Schema Simplification
Tool Filtering
Context Reordering
Validator Addition
Retry Policy Update

近期 Harness-R1 更进一步，直接探索通过 agent failure trajectories 学习修改 executable runtime harness，而不是只更新模型权重。(Hugging Face)

这意味着未来可能形成：

              Failure Trajectory
                     │
          ┌──────────┴──────────┐
          ▼                     ▼
    Model Optimizer       Harness Optimizer
          │                     │
     Update Weight        Update Runtime
          │                     │
          └──────────┬──────────┘
                     ▼
              Better Agent System

六、当前的技术路线已经可以分成 3 代

第一代：Harness-agnostic Post-training

Model Training
      │
      ▼
   Model
      │
      ▼
  Harness

特点：

  • SFT
  • DPO
  • GRPO
  • Static benchmark

问题：Training ≠ Deployment

第二代：Harness-aware Post-training

Harness Design
      │
      ▼
Training Data
      │
      ▼
Small Model
      │
      ▼
Same Harness

特点：

  • Harness-generated trajectories
  • Tool-aware SFT
  • Context-aware distillation
  • Environment-specific RL

这是当前主流。

第三代：Harness-Model Co-evolution

       ┌───────────────┐
       │ Runtime Agent │
       └───────┬───────┘
               │
       Failure Trajectory
               │
      ┌────────┴────────┐
      ▼                 ▼
Update Model       Update Harness
      │                 │
      └────────┬────────┘
               ▼
        Runtime Evolution

这才是真正的：

Self-improving Edge Agent

目前还偏早期研究，但 Harness-R1 等工作已经开始探索这个方向。(Hugging Face)

七、针对端侧小模型，建议的主流技术架构

建议采用：

                    ┌─────────────────┐
                    │ Cloud Teacher   │
                    │ 30B / 70B+      │
                    └────────┬────────┘
                             │
                       Exploration
                             ▼
┌───────────────────────────────────────────┐
│             Target Edge Harness           │
│                                           │
│  Context Manager                          │
│  Tool Retriever                           │
│  State Machine                            │
│  Validator                                │
│  Retry / Recovery                         │
│  Memory                                   │
└────────────────────┬──────────────────────┘
                     │
              Trajectory Store
                     │
       ┌─────────────┼─────────────┐
       ▼             ▼             ▼
    Success       Near Miss       Failure
       │             │             │
       ▼             ▼             ▼
      SFT        Repair + SFT   Diagnosis
                     │             │
                     └──────┬──────┘
                            ▼
                   On-policy Distillation
                            │
                            ▼
                     Small Model
                            │
                    Harness-in-loop RL
                            │
                            ▼
                       Edge Model

后训练的优先级

对于 0.5B–4B 端侧 Agent Model，建议：

第一优先级

Harness trajectory SFT

学习：

  • Tool format
  • State transition
  • Action pattern
  • Recovery behavior

第二优先级

Teacher-guided on-policy distillation

解决：

  • 小模型探索能力不足
  • Sparse reward
  • 长轨迹失败

第三优先级

Harness-in-loop RL

只强化少量真正需要 Policy Learning 的部分：

  • Tool Selection
  • Retry Decision
  • Plan Revision
  • Long-horizon Recovery

而不是端到端训练所有行为。

最核心的判断

端侧小模型未来最重要的技术竞争，不是：

谁把 3B 模型训得更聪明

而是：

谁能把：
Small Model
+ Context Harness
+ Tool Harness
+ Recovery Harness
+ Memory
+ Post-training

设计成一个闭环系统。

换句话说：

对于端侧 Agent，后训练的对象不应该只是一组模型权重，而应该是 Model × Harness 的联合行为。

甚至可以把它抽象成一个优化目标：

Maximize Agent Capability
Subject to:

Model Compute
+ Harness Complexity
+ Context Budget
+ Memory Cost
+ Tool Latency
+ Power Consumption
≤ Edge Budget

因此未来端侧 Agent 的最优解，大概率不是"更强的小模型"，而是：

弱一点的模型 + 极强的 Harness + Harness-in-the-loop 后训练。

如果继续往下拆，可以进一步形成一套完整的 "端侧小模型 Harness-Aware Post-training 技术架构"，包括 训练数据层、Trajectory Store、Harness Proxy、Rollout Engine、Distillation、RL、Failure Mining、线上持续学习 八个模块。
