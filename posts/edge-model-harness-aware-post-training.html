端侧小模型 Harness-Aware 后训练技术路线

August 27, 2026

端侧小模型的后训练，正在被 Harness 重新定义

2025–2026 年，端侧 Agent 后训练的主流路线已经完成了一次范式转移：从 Model-Centric Post-training（先把模型训好，再找个 Agent Harness 去套）演进到 Harness-Centric / Harnessed Agentic RL——部署期 Harness 直接成为后训练系统的一部分。核心判断：端侧 Agent 的竞争力不是「谁把 3B 模型训得更聪明」，而是谁能把 Small Model + Context/Tool/Recovery Harness + Memory + Post-training 设计成一个闭环系统。

核心发现一：5 类机制，关键在于「Harness 不知识训练场景，而是训练环境」

当前公开方案可归为 5 类联动机制，成熟度和激进程度依次递进：

机制做法代表成熟度
① Harness → 轨迹生成器Teacher 在真实 Edge Harness 中执行 → 记录完整 trajectory → filter/repair → SFTApple PROOF-Gen最成熟，门槛最低
② Distillation → Agentic RLCold-start SFT → On-policy Distillation → Agentic RL；稀疏奖励留给大模型探索，密集监督给小模型压缩DGPO、Microsoft reward-density当前最主流配方
③ 真实 Harness-in-the-loop RL不重写 Harness，用 LLM/Harness Proxy 黑盒捕获 token 级交互 → 轨迹重建 → RLPolar（Qwen3.5-4B）未来 1-2 年关键方向
④ Small Model-Optimized Harness Co-designContext 压缩 / Tool Surface 缩减（50→3-8 个）/ 确定性能力外化Microsoft MagenticLite正在产品化
⑤ 训练 Harness 本身Failure → 判断 Model Problem（后训练）vs Harness Problem（patch harness）Harness-R12026 新方向，早期

机制①的关键不是让 Teacher 在理想环境生成答案，而是让 Teacher 在端侧小模型将来真正使用的 Harness 中运行——这是端侧与云端训练的本质区别。

核心发现二：3 代演进——Harness-agnostic → Harness-aware → Co-evolution

代际特征阶段
Gen 1 Harness-agnosticSFT/DPO/GRPO + 静态 benchmark问题：Training ≠ Deployment
Gen 2 Harness-aware（当前主流）Harness-generated trajectories + tool-aware SFT + context-aware distillation + environment-specific RL主流实践
Gen 3 Harness-Model Co-evolutionFailure trajectory → 同时更新 Model（权重）和 Harness（运行时）→ Runtime Evolution早期研究（Harness-R1 等）

核心发现三：Harness 反过来决定「后训练什么」

这是比「Harness 参与训练」更反直觉的一层：不同 Harness 设计直接决定模型的后训练 Problem Formulation。

  • Harness 强 Tool Recovery → 模型只需 Intent→Tool Selection → 训练目标：Policy Accuracy
  • Harness 弱 → 模型需 Intent→Tool Call→Read Error→Diagnose→Retry → 训练目标：Long-horizon Recovery Policy
  • Harness 有 Context Compressor → 训练目标：Structured State→Action，而非 Long Context→Answer

因此端侧 Agent 的最优解大概率不是「更强的小模型」，而是「弱一点的模型 + 极强的 Harness + Harness-in-the-loop 后训练」。

对端侧模型的工程启示

1. 后训练优先级（推荐架构 Cloud Teacher + Edge Runtime Harness）

① Harness trajectory SFT（学 Tool format / State transition / Action pattern / Recovery）→ ② Teacher-guided on-policy distillation（解决小模型探索不足 + sparse reward）→ ③ Harness-in-loop RL（只强化 Tool Selection / Retry Decision / Plan Revision / Long-horizon Recovery，不端到端训练所有行为）。

2. 确定性从权重外化到 Harness

Retry / Timeout / Schema Repair / State Validation / Tool Recovery 由 Harness 接管，小模型只承担 Plan / Decide / Select Action。这与「Parametric vs Externalized」框架一致——把确定性能力从模型权重搬到可审计的 Harness 代码。

3. 轨道接口：Harness ↕ LLM Proxy ↕ Post-training

未来的核心接口是 Harness 与训练框架之间加 Proxy 解耦（Polar / Agent Lightning 验证），而不是 Harness ↔ 特定 RL Framework 耦合。这样任何 Harness（Python/TS、异步、tool middleware）都能黑盒接入任何训练框架。

局限与诚实标注

  • 时间窗口：本路线基于 2025–2026 公开方案（PROOF-Gen / DGPO / Polar / MagenticLite / LFM2.5-2.6B / Harness-R1），部分工作（Harness-R1、Gen3 co-evolution）处于早期预印本阶段，结论有推断成分。
  • 机制③难点：Harness 通常不是 RL Environment（有自己的 event loop、异步、middleware），Proxy 方案能捕获 token 级交互，但状态/奖励信号重建的保真度仍待验证。
  • 量化缺口：除 Polar（Qwen3.5-4B）、Agent Lightning（Qwen3.5-9B +14.6 SWE-bench）外，多数方案缺少端侧 0.5B-4B 的公开基准对比；「Harness 补偿 vs 模型能力」的边际收益尚无系统量化。
  • 训练成本：Harness-in-the-loop 需要 Teacher 在 Edge Harness 中大量探索（cloud 推理成本），对生产团队是非平凡投入。

一句话

端侧 Agent 的后训练对象不再是一组模型权重，而是 Model × Harness 的联合行为——谁能把 Harness 变成训练环境的一部分，谁就拿到端侧 Agent 下一阶段的入场券。
