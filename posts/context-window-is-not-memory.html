context window 是 RAM 不是记忆：一张办公桌讲清 agent 认知栈五层

August 19, 2026

停止买那张 1000 万 token 的办公桌：context window 是 RAM，不是记忆——一篇用办公室隐喻讲清 agent 认知栈五层的文章

当 AI 厂商发布 200 万 token 上下文窗口的模型，开发者的第一反应往往是"把整个代码库塞进 prompt，记忆问题解决了！"。MachineLearningMastery 的这篇文章（Iván Palomares Carrascosa，2026-06-24）用一组办公室隐喻戳破了这个幻觉：把超大 context window 当"记忆"，等于买一张 25 英尺宽的办公桌，因为你懒得买个文件柜——所有文件摊在桌面上，但工作会话一结束，桌面就被保洁清空了。

文章没有新技术，但把 agent 认知栈里最常被误用的五层——context window、retrieval、compression、summarization、memory——讲得干净利落，每个概念配一个可落地的代码模式。

核心框架：认知栈五层，各管各的事

层隐喻本质关键陷阱/模式
Context Window桌面 / 无状态草稿每次调用从 step zero 开始的 RAM三个陷阱：lazy student / snowballing / brain freeze
Retrieval (RAG)办公室书架JIT 拉取 top-K 相关块vector similarity ≠ 语义真值，需 reconciliation
CompressionZIP 压缩无损带宽优化保留数据、缩 footprint（15K→5K token）
Summarization摘要不可逆抽象（单程票）必须 forked storage：raw 存冷库 + summary 进 prompt
Memory文件柜状态机（跨会话持久）query-then-commit，agent 做 DBA 而非数据库

核心发现一：context window 的三个致命陷阱

模型本质是完全无状态的——每次 API 调用都从"step zero"开始。给它 200K token 历史，它不是"记住"了之前发生什么，而是在毫秒级重新读取它的整个宇宙。长期依赖这个策略，会掉进三个陷阱：

  • Lazy student（懒惰学生）：对巨长 prompt 的开头和结尾认真，对埋在中间的要点完全略过——这就是 lost-in-the-middle。
  • Snowballing（雪球效应）：对话每增长一步，agent 每一步都要重新发送并重读全部历史，包括最早那些早已无关的轮次。
  • Brain freeze（大脑冻结）：面对一面巨大的文本墙，模型要等好一会儿才开始吐第一个 token——延迟随上下文长度累积。

文章给了一个扎心的具体化：你在 Step 47 问"我们 Step 1 里约定变量叫什么？"，仅仅为回答这个问题，前面 46 轮对话必须全部重发一遍。

核心发现二：RAG 的向量相似 ≠ 语义真值

RAG 像书架——JIT 拉取当前步骤相关的 top-K 文档块。但当 agent 进入循环，问题就来了：向量相似度不等于语义真相。例子：用户先说"把会议挪到周五"，后来说"取消周四，Alice 病了"——向量搜索会把这两句互相矛盾的陈述都检索出来，留模型去猜哪句还生效。

可靠的模式是在生成之前就消解冲突——按时间戳取最新：

retrieved_chunks = [
  {"text": "Move meeting to Friday", "timestamp": "2025-01-10T09:00:00"},
  {"text": "Cancel Thursday, Alice is sick", "timestamp": "2025-01-12T14:30:00"}
]
latest_relevant = max(retrieved_chunks, key=lambda c: c["timestamp"])

这一行 reconciliation 逻辑，就是"自信地重复一条过期指令"和"正确知道会议已取消"之间的差别。

核心发现三：compression 和 summarization 是两种不同的操作

这是文章最有价值的区分——两者常被混为一谈：

  • Compression（压缩）：无损带宽优化。保留底层数据，只缩它在 prompt 里的 footprint。例如把 15K token 的 JSON payload 用 LLMLingua 压到 5K。数据没丢，只是"占桌面积"变小了。
  • Summarization（总结）：不可逆的抽象——删掉原始数据，换成摘要。它是单程票。所以正确做法是 forked storage：原始 transcript 写进 S3 冷存储，只有摘要进 prompt。以后需要细节，从 S3 取回。

一句话区分：compression 的数据还能从 prompt 内部重建，summarization 的永远不能。

核心发现四：真正的记忆是状态机，agent 做 DBA 而不是数据库

文章的落点是架构判断：给 agent 真正的记忆，它必须做数据库管理员（DBA），而不是数据库本身。用户说"我狗叫 Goofy，但可能改名 Pluto"，agent 应该显式触发一个工具调用：

{"tool": "update_entity_graph", "params": {
  "subject": "User_Dog", "attribute": "Name",
  "value": "Goofy", "notes": "Considering Pluto"}}

背后是 SQL 表、知识图谱还是 Redis 都无所谓——关键是 discipline：每一轮开始时查询状态机，结束时提交更新（query-then-commit 循环）。

对 agent 基础设施的工程启示

1. 记忆是模型旁边的系统，不是模型的能力

无论用什么模型、多大窗口、什么框架，"agent 在某一轮看似知道什么，只是你的代码在调用前装进窗口的东西"。把加载步骤拿走，agent 每一轮都回到白板。架构上必须把记忆做成显式的、可查询的外部状态。

2. 给检索加 reconciliation 层，别让模型猜

朴素 RAG 只是把检索结果拼接，留模型去猜哪条指令还生效。可靠的模式在生成前就消解矛盾——时间戳取最新、按优先级覆盖。这一层是"stateful agent"和"stateless RAG"的分水岭。

3. 压缩和总结要分开设计

需要无损带宽优化（大 payload 进 prompt）用压缩；需要长期抽象用总结——但总结必须配 forked storage（raw 落冷库），否则不可逆丢失。总结是单程票，不能当压缩用。

4. 把 query-then-commit 变成硬纪律

每一轮开头查状态、结尾提交，像数据库事务一样。这是"agent 记得住"的唯一可靠形态——无论记忆后端是 entity graph、SQL 还是 vector store。

局限与诚实标注

  • 概念澄清，非新技术（我的判断）：全文无实验、无 benchmark，是认知栈的重新命名和组织。价值在"讲清楚"，不在"发现什么"。
  • 三个陷阱有更早的学术出处（我的推断）：lost-in-the-middle 是 Liu et al. 2024 的正式发现，snowballing/brain freeze 是工程常识的复述。文章用"lazy student"等隐喻做了通俗化。
  • entity graph 例子过于简化（我的推断）：真实记忆系统要处理 schema drift、冲突解决的优先级、检索质量、TTL/过期、隐私边界——文章只讲了 query-then-commit 的骨架。
  • 与"RAG is not Agent Memory"同源（我的关联）：Letta 的区分（RAG = 无状态文档检索，memory = 有状态、可更新、用户范围）和 Redis/Mem0 的"window 是 RAM 不是 storage"是同一条线，文章是这条线的通俗化表达。

一句话

context window 是每次调用从零开始的无状态 RAM，不是记忆；真正的记忆是模型旁边一个"每轮开始查询、每轮结束提交"的状态机——停止买那张 1000 万 token 的桌子，买个普通桌子，给 agent 一支锋利的铅笔，教它开文件柜。
