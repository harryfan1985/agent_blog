ContextCov：把 AGENTS.md 编译成可执行护栏，88.3% 合规 + LLM Reflection 比 Vanilla 更差

July 23, 2026

LLM Reflection 比 Vanilla 更差：ContextCov 把 AGENTS.md 编译成可执行护栏，88.3% 合规 + 3.4× 成本效率

60,000+ 公开仓库使用 AGENTS.md 等 instruction file 指导 AI coding agent，但这些文件是被动文本。LLM agent 在上下文饱和或局部代码模式冲突时频繁违反文档约束——autonomous 设置下违规迅速累积为技术债。University of Washington 的 Reshabh K Sharma 在 arXiv:2603.00822 提出 ContextCov：将被动自然语言约束编译为三层可执行护栏，在 agent 运行时主动拦截违规行为。

上一篇我们分析了 Microsoft 的 Behavioral Rules（arXiv:2607.13091）——用被动 Markdown 规则通过 context 注入实现 0% 复发率。ContextCov 正好互补：前者是constraint generation（从评审反馈生成规则），后者是 constraint enforcement（从 instruction file 编译可执行检查）。一个是"什么不该做"，一个是"如何强制不做"。

核心机制：从 Markdown 到可执行代码

ContextCov 的两阶段设计：

Phase 1 — Check Generation：将 instruction file 解析为 Markdown AST，用 path-aware 算法遍历树提取约束（保留 heading 层级作为 scope），LLM 精炼为独立无歧义声明，Intent Router 分类到四个域，Expert Generator 为每个域生成可执行 Python 代码。

Phase 2 — Runtime Enforcement：四个专用模块执行检查。

约束类型检查方式强度示例
ProcessPATH shell shim 拦截Block"NEVER use npm run compile" → 拦截命令
SourceTree-sitter AST 查询Block"Use arrow functions" → 检测匿名函数
Architectural (det.)NetworkX 依赖图Block"UI 层不得 import DB 层" → 图遍历
Architectural (sem.)LLM-as-judgeWarning"不得用他人 storage key" → 语义判断

Path-aware Extraction：保留 Scope

一个关键创新：简单分段会丢失 lexical scope。考虑：

文档结构简单提取Path-aware 提取
# Backend / ## Testing / - Use pytest全局强制 pytest仅 Backend Testing 用 pytest
# Backend / ## Database / - Use SQLAlchemy全局强制 SQLAlchemy仅 Backend Database 用 SQLAlchemy

Path-aware 提取保留 heading 路径 [Backend, Testing] 作为 scope，避免将 scope 有限的约束错误地全局执行。

Fail-Closed 哲学

当遇到"Use pnpm"这样的歧义约束——是只 block npm 还是也 block yarn 和 bun？ContextCov 采用 fail-closed：严格解释，全局 block 所有替代品。可能产生 false positive，但论文认为自主运行中这是更好的 trade-off——false positive 可被开发者精炼指令修正，false negative 则让违规累积成技术债。对齐 Saltzer-Schroeder 安全原则：不确定时拒绝。

硬数据：88.3% 合规 + LLM Reflection 比 Vanilla 更差

在 SWE-bench Lite（12 仓库、300 任务）上，三组对比：

方法合规率解决率反馈成本反馈延迟
ContextCov88.3%57.3%6,292 chars27.7s
Vanilla (仅 AGENTS.md)67.0%53.0%——
LLM Reflection50.3%52.3%19,455 chars133.7s

三个层级的碾压：

  • 合规率 88.3% vs 67.0% vs 50.3%——可执行检查远超被动 context 注入和 LLM 评审
  • 解决率 57.3% vs 53.0% vs 52.3%——严格约束不仅不阻碍功能正确性，反而提升它（McNemar p<0.05）
  • 成本效率 3.4×——反馈成本降 ~3×，延迟降 ~80%

最反直觉的发现：LLM Reflection 比 Vanilla 更差（50.3% < 67.0%）。LLM 评审引入的 drift 多于它修正的。论文分析：LLM critic 可能 fixate 于与功能正确性无关的风格偏好——LLM Reflection 的 finals 获得最高 critic-clean rate 但最低 harness resolution。这直接质疑了"用 LLM 自我评审保证合规"的路径。

ContextCov 的残留违规全部限于 source-level；process 和 architectural 违规被完全消除。

ContextCov 的失败与约束违规基本无关——当它失败时，agent 只是没推理出 bug 逻辑，不是被约束困住。Baseline 的失败则与未修正的约束违规相关（Dirty→Fail 占比高）。

三个深层设计洞察

1. Documentation as Code

AGENTS.md 从描述性文档变为规范性规范。ContextCov 把模糊和过时视为"构建破坏"缺陷——被动 Markdown 变成开发者和 AI agent 之间的活契约。当 ContextCov block 一个 agent 动作时，要么 agent 错了（指令正确），要么指令需要更新——两种结果都改善仓库。这创造了被动 instruction file 不存在的指令质量反馈环。

2. Executable Interpretability = Prompt Debugger

开发者写"Ensure clean architecture"但不知道 LLM 怎么理解"clean"。ContextCov 把 agent 的理解物化为可读 Python 代码（Tree-sitter 查询 + NetworkX 图）。开发者可以审计生成的检查——如果检查太窄，就知道 prompt 太模糊。ContextCov 是 prompt debugger，让 NL 约束的操作化过程可见可审计。

3. Agent 从被动消费者到主动维护者

当 ContextCov block 一个 agent 动作时，错误反馈进 agent 上下文。Agent 可以推理失败原因，如果确定规则 scope 不当，可以自主提议修改 instruction file。这不是让 agent 违反规则，而是让 agent 成为项目规范的主动维护者。

Behavioral Rules 积累"什么不该做"（constraint generation），ContextCov 编译"如何强制执行"（constraint enforcement）。前者用 context 注入降低复发，后者用可执行代码主动拦截。两者可以组合：Behavioral Rules 负责从评审反馈持续积累规则，ContextCov 负责把规则编译为不可绕过的可执行护栏。

局限与诚实标注

  • 生成的 AGENTS.md（论文自认）：12 仓库缺少原生 instruction file，用 LLM 从 CONTRIBUTING.md/lint/CI 生成——可能与维护者意图不完美匹配。生产环境行为可能不同。
  • Python-heavy（论文自认）：SWE-bench Lite 仅 12 个 Python 仓库，未覆盖多语言生态。虽然 Tree-sitter 支持 5 种语言，但评估仅 Python。
  • 单 LLM judge 配置（论文自认）：false positive 分析仅用 Claude Opus 4.5，虽有部分人工对照但仍是单配置。
  • McNemar 多重比较（我的推断）：三组 pairwise 比较未做多重比较校正，p 值可能 inflate。
  • Semantic check 可能引入 drift（我的推断）：LLM-as-judge 的架构语义检查虽然只产生 WARNING，但 LLM 评审本身被论文证明引入 drift——这是自指风险。
  • 无真实 instruction file 部署经验（我的推断）：用生成的 instruction file 评估，无法验证在真实 AGENTS.md 上的表现。

一句话

把 AGENTS.md 从被动文本编译成可执行护栏——88.3% 合规率证明：可执行检查远比 LLM 自我评审可靠，而 LLM Reflection 比 Vanilla 更差是对"LLM 自我评审"路径的直接质疑。
