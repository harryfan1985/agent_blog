三、Effort 到底值不值：Thariq 的自测结论是「别一直拉满」

Anthropic 的 Thariq 抛出一个很多人默认跳过的问题：effort（推理努力度）究竟是什么？什么时候该调它，为什么不干脆所有任务都用 max？他说自己为此深挖了评测、也做了自己的测试，结果「相当意外」（原文，3.5k 赞）。他给出的实际用法更具体（原文，321 赞）：

  • effort low 用得更多——当你想保持在环里、想参与过程的时候用 low；
  • effort max 基本只留给两类场景：完全不想插手、要零输入的任务，以及找安全漏洞。

他还把自建的交互式 benchmark 与 demo 解释页放上了新的 dev site（原文，140 赞）。对每天和 agent 打交道的人来说这条比新模型更实用：effort 不是「越高越好的旋钮」，而是「你想介入多少」的开关——想盯着过程就调低，想彻底撒手才拉满。

四、Agent 在团队里的真实分工：Tag 每天写掉 50% 以上的 PR

Boris Cherny 给了一份很具体的工作量账单：Tag 每天写掉他 50% 以上的 PR，做了他 约 100% 的数据分析，还修掉了大部分产品反馈与 bug。他强调这不是普通 Slack bot——「它是主动的、可编程的、有记忆的、能接你各种 connector 的」（原文）。他列出的 prompt 是今天最实用的一段：

  • 「@Claude 这个频道里已解决的线程用 ✅ 回应」——把巡检变成常驻任务；
  • 「@Claude 从现在起，这个频道里每个 bug 都要端到端复现：跑起完整应用，复现后直接提 PR，并 @ 对应团队来 review」；
  • 「@Claude 就这份奇怪的数据 brainstorm 100 个假设，用 workflow 逐个验证，花个 1000 万 token 深挖，最后画张图」；
  • 「@Claude 做个交互式小游戏解释这段代码怎么工作，再生成一份给团队其他人看的 slide」。

这段的价值不在工具，而在任务定义方式：把触发条件、验收标准、产出形态一次性写清，agent 才能从「回答问题的 bot」变成「承担流程的同事」。第 09-19 期讨论的「让同事劫持 session 做 deslop」是同一条线——团队开始围绕 agent 重新划分职责。

五、575 个 PR 的自动化重构：大重构不再可怕

Peter Steinberger 复盘了自己最大的设计失误：把 OpenClaw（OC）迁到 sqlite 时用了同步 DB 访问。当时它只是个在 Slack / iMessage 里汇报的 agent，这没问题；现在一个 agent 可能并行跑 50 个 session、整个团队都在上面干活，同步访问就成了硬瓶颈。

他的解法不是排期半年，而是给 Astra 挂了一个 /goal：至今已经落了 575 个 PR，把系统逐步迁到 async worker，边做边发。他的结论很直接——「以前那种让人害怕的大重构，现在不吓人了」（原文，1.0k 赞）。工程里最贵的资源从来是「耐心」和「不被打断的连续时间」，agent 正在把它变成可并行、可累积的东西。

六、企业侧的两道门槛：先能测，再能被 agent 调用

Box CEO Aaron Levie 把 evals 提到了企业 AI 扩散的闸门位置：「你无法自动化你无法度量的东西。」企业的确定性流程还能用软件测，但大多数企业今天根本没有办法理解自己的非确定性流程——也就是 agent 到底干得怎么样。没有好 eval，就不知道什么在生效、什么坏了、什么变了、什么变好了；所有变更、升级、部署都在好 eval 的下游，而各行业会涌现大量领域专用的 eval，每家企业在自己环境里也需要一套（原文，195 赞）。

Vercel CEO Guillermo Rauch 从另一侧给出同构结论。他介绍了给 Klaviyo 这类公司搭的 agentic 部署平台（① 接入所有 agent：claude、codex、cursor…… ② 通过 IDP 配 SSO ③ 全员安全地用），并抛出一个判断：新的「采购门槛」将是你的产品对 agent 有多顺手，而不是对人有多顺手。这正是大型 SaaS 突然抢着发 CLI 和 MCP、把冷落多年的 API 翻出来的原因；他还预测长尾 SaaS 里会有一批「再也不会被采购，而是被生成」——更安全、更快、更贴合每个公司的流程（原文，183 赞）。顺带一句他关于 npx skills 的感慨：「我们过去写代码，现在我们写英文。」（原文，331 赞）
