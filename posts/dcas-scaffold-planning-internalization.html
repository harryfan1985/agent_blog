换掉脚手架，模型就崩了？DCAS 把规划从脚手架惯例变成模型能力

August 13, 2026

同一个模型，从 OpenHands 换到 OpenCode，SWE-bench Verified 从 52.6% 跌到 8.4%——44 个百分点的崩塌，模型参数一个没动。换到 mini-swe-agent，另一款模型从 49.7% 跌到 20.4%。而它们的未训练底座（base model）在四个脚手架之间波动不到 10 个点。

这就是华为加拿大 + Queen's University 团队在 ASE '26 发表的 DCAS（Decoupling CLI Agent Scaffolding）论文揭示的现象：跨脚手架部署鸿沟（cross-scaffold deployment gap）是微调安装的，不是模型固有的。开源生态已经收敛到单一训练环境——SWE-Gym、Nebius、SWE-Lego、CoderForge 的轨迹几乎全部在 OpenHands 下采集——于是几乎所有强开源模型都带着 OpenHands 的"行为惯例"出厂，换个脚手架就露馅。

责任机制：规划结构（Planning Structure）

论文把嫌疑锁定在 planning structure，并拆成两个可分离的维度：

  • 显式规划（explicit planning）：执行前模型产出一份 plan 作为一等工件——Claude Code 的 Plan Mode、OpenCode 的 Plan agent 是典型代表；
  • 隐式规划（implicit planning）：每个脚手架对 agent loop 逐轮强加的结构惯例——子步骤粒度、探索何时让位给行动、工具调用如何排序、失败如何触发重规划。

所有主流脚手架底层共享 ReAct 式 act/observe loop，所以模型不缺能力，缺的是对目标脚手架规划惯例的熟悉度。旁证来自 Liu et al. 对 16,991 条 CLI agent 轨迹的分析：plan quality 与 plan adherence 是 resolution rate 的首要驱动。

关键实验 1：只换计划来源，+15 个百分点

RQ1 做了最干净的隔离：executor 固定 Qwen3-Coder-30B-A3B、脚手架固定 Claude Code 2.0.76、turn 上限全条件一致，唯一变量是 plan 来自哪里：

Plan 来源Pass@1Δ
无计划（基线）42.8—
自生成计划48.2+5.4
Qwen3-480B（开源大模型）49.2+6.4
Claude Opus 4.554.2–56.0+11.4~13.2
Claude Sonnet 4.557.8+15.0

三个信号：① 计划质量随 planner 能力单调上升；② +15% 的杠杆超过观察到的任何跨脚手架跌幅，规划值得投入训练；③ 反直觉——更弱的 Sonnet 4.5 胜过更强的 Opus 4.5，说明 规划器-执行器校准比规划器原始能力更重要（Opus 的 plan 可能隐含 30B executor 做不到的推理假设，Sonnet 的 plan 更显式、更 stepwise）。

关键实验 2：576 条轨迹把规划内化成模型能力

RQ2 用 GLM-4.7 在 Claude Code 下采集 planning-aware 轨迹（SWE-Lego Real Data 实例，对 SWE-bench Verified 显式去污染），拒绝采样留 576 条，构造两个 SFT 变体：

  • PlanOnly（14,162 样本，只含规划阶段）：no-plan 涨到 53.8 (+11.0)，但 self-plan 无额外收益（53.2）——只装下了隐式惯例，没学会"执行时怎么用计划"；
  • Plan+Exec（36,259 样本，规划+执行全轨迹）：no-plan 52.8 (+10.0)，self-plan 再加 +3.0 到 55.8——两个维度都装下了。

Plan+Exec 的 self-plan 成绩（55.8%）≈ RQ1 里 Claude Opus 4.5 注入 plan 的成绩（56.0%），距 Sonnet 注入只差 2 分——推理时不再需要外部 planner。显式/隐式规划在训练数据里干净地分离开，这是论文最漂亮的实证。

关键实验 3：学到的规划是结构技能，不是脚手架记忆

RQ3 把 Plan+Exec 部署到三个训练时没见过的环境：

部署环境SFT no-planSFT self-planvs base no-plan
CC 2.0.76（训练版）52.855.8+13.0
CC 2.1.73（新版）54.657.2+14.4
OpenCode v0.0.5547.649.4+3.4
mini-swe-agent v2.2.839.242.4+7.0

版本迁移成立：CC 2.1.73 换了工具 schema 和 turn 管理，模型零额外微调反而更高（57.2% 是全论文无外部 planner 的最高分）。跨脚手架迁移成立：收益幅度与目标脚手架惯例对齐度正相关——如果是表面记忆，在未见脚手架上应该退化而不是增益。

工程启示

单脚手架评估是方法论混淆

论文的 Table 1 说明 leaderboard 上的单点分数系统性虚高能力：每个微调模型至少在一个非训练脚手架上退化，而行业没在测量这个失败模式。"模型 X 达到 Y%" 不标注脚手架就是方法论不完整。最低标准是至少报一个训练分布外的脚手架；理想是多脚手架向量报告——Qwen3-Coder-Next 已经开始这么做。

采集脚手架的选择 ≥ 采集规模

行业共识是"轨迹越多越好"（SWE-Gym、Nebius、CoderForge 都是数千到数万条）。DCAS 用 576 条就拿到跨脚手架一致增益——因为脚手架可迁移的信号藏在轨迹的规划结构里，不在体量里。预算有限的团队，选一个规划结构丰富的采集脚手架，比堆量更划算。

Planner 校准是设计变量

Sonnet 4.5 > Opus 4.5 的 planner 反转意味着：选外部 planner 要对着 (executor, scaffold) 对校准，而不是选最强的模型。数据生成同理——teacher 太强会产出 student 消化不了的轨迹（这也是论文刻意用 GLM-4.7 而非 frontier 采集的原因：隔离"惯例信号"与"能力蒸馏"）。

局限

  • 跨脚手架归因不纯：planning 与工具 schema、turn 管理、上下文处理共变，没有 execution-only / token-matched / 劣化 plan 对照组；
  • 单一 benchmark（SWE-bench Verified）、单一 executor（Qwen3-Coder-30B-A3B）、单一训练脚手架（Claude Code）；Codex / Gemini CLI 未覆盖（Codex 尝试过：Responses API SSE 流式格式让代理在 10-18 次往返后永久无响应）；
  • 拒绝采样偏向易实例；Pass@1 不测效率；self-plan 增益可能部分来自执行行为改善；
  • 论文引用的 HF 权重链接（kishanthan/models）404，但复现包（Zenodo）与轨迹数据集（kishanthan/dcas_glm4.7_distill，270MB 全量 + 187MB 规划分离）均可下载。

对 agent 基础设施的启发

DCAS 本身是一个 backend-substitution 拦截层：在脚手架与后端模型之间双向翻译 API 流量，脚手架零修改。这意味着：

  • 专有后端（Claude Code + Anthropic）也可以被任意开源模型替换，做受控对比；
  • 规划阶段与执行阶段可以分离采集，轨迹带结构化 plan 字段（instance_id / patch / plan / main_agent / sub_agents）；
  • 版本迁移测试成为常规操作——同一模型在脚手架新旧版本上跑一遍就知道学到的是惯例还是记忆。

它把"scaffold 惯例"从隐性的、不可测量的东西，变成了可采集、可训练、可评估的显式变量——这正是 harness 工程从经验纪律走向实验科学的路径。
