WikiSkill：技能进化缺的不是更好的优化器，而是一层永不回滚的知识

September 01, 2026

技能进化（skill evolution）研究了一整年，从 EvoSkill 到 SkillOpt，大家默认的瓶颈是"技能质量不够好"——生成的技能不够精确，需要更强的优化器、更细的反馈信号。但 Google Research 的新论文 WikiSkill（arXiv:2608.27454）指出了一个被忽视的根因：指导技能开发的洞见，散落在优化历史里。EvoSkill 维护 proposal 历史、Trace2Skill 提取轨迹教训、SkillOpt 用 rejected-edit 反馈——但没有一家把"学到了什么"维护成一个独立的、持续演化的知识表示。结果就是每一轮进化都在部分地重新发明轮子。

WikiSkill 的答案很直接：在原始轨迹与可执行技能之间，插入一层永不复利清零的 wiki。五个 benchmark × 五个模型全面超基线，且揭示了一个对端侧模型极有意义的规律——技能进化与模型规模互补：小模型 + 好技能可以打平并超过无技能的大模型（Qwen-3.5-9B + WikiSkill 47.4% > Qwen-3.6-27B 无技能 39.4%）。

三层知识架构：把"学到什么"变成一等公民

WikiSkill 把 agent 工作区分成三个生命周期完全不同的层：

  • Raw Layer（raw/）：不可变的完整执行轨迹（推理、工具调用、输出、最终答案）。只写不删。
  • Wiki Layer（wiki/）：持久知识——patterns/ 存放失败模式与成功策略的可行动 workaround，logs.md 演化日志，skill-impact.md 记录每次技能提案的 diff + 验证分数 + 接受结果。这一层跨迭代积累、永不回滚。
  • Skills Layer（skills/）：可执行技能（SKILL.md + PURPOSE.md 回链到催生它的 wiki pattern）。唯一可被验证门控回滚的层。

关键不是分层本身，而是三个设计决策：

1. 审计轨迹防重复提案。 skill-impact.md 由外层 harness 程序化追加（提案 diff + 验证分 + accepted/rejected），Proposer 的 system prompt 明确要求"先读 wiki，不要提案已被拒的方案"。ALFWorld 案例：Iteration 0 的 goal-directed-action 被拒后，其 diff 永久留在审计轨迹里，Iteration 1 的 break-repetition-loop 正是基于这次拒绝记录成功合成，Iteration 4 又根据新的循环变体 pattern 继续精修。

2. 访问分离（最反直觉的消融）。 执行 agent（Inference Agent）在训练 rollout 时禁读 wiki——如果执行时能直接从 wiki 拿答案，产出的轨迹就对技能开发失去信息量（-2.8 pp）；只有提案 agent（Skill Proposer）能读 wiki（+15.0 pp）。知识是给"老师"看的，不是给"考生"看的。

3. 按需探查替代全量注入。 Proposer 的上下文不再是预采样的轨迹包，而是 wiki 索引 + pass/fail 汇总 + skill-impact 历史，然后以 ReAct 方式用 read_file 自行决定读哪条轨迹、哪个 pattern。长执行历史不再直接塞进上下文（上限 ~15K chars），而是变成一个可导航的知识库。

对端侧模型与 Harness 工程的启示

这篇论文与端侧小模型路线（本博客的 Harness-Aware 后训练系列）形成强互补：

  • 技能是参数外的能力补偿器。 Qwen-3.5-9B + 技能 47.4% > Qwen-3.6-27B 39.4%——8 pp 的差距用一行技能注入补回，而 9B→27B 的模型参数量差距是 3 倍。对算力受限的端侧部署，这意味着"编译经验"可能比"扩大模型"更划算。
  • 技能发现 ≠ 技能执行。 迁移实验显示 4B 模型演化的技能能把 Gemma-4-31B 的 LiveMath 从 33.9% 提到 73.1%，而强模型的自进化技能未必更好——技能质量取决于经验覆盖与提炼能力，不是源模型大小。这也解释了为什么"云端大模型编译技能 → 端侧小模型执行技能"是可行的生产架构（与 Cloud Teacher + Edge Runtime 路线一致）。
  • 负迁移警告。 4B 技能让 Gemini-3.5-Flash 的 SpreadSheet 从 50.5% 跌到 18.1%——低层 workaround（单行 Python、字符串转换）会约束强模型用端到端脚本。技能需要区分"通用程序"与"模型特定 workaround"，迁移前要按目标模型能力筛选。
  • 全批次 O(1) 优化器成本。 B=N_train 时每轮只需 1+T_ReAct（约 11-21）次 LLM 调用，与训练集规模解耦——技能进化的边际成本可控，适合持续运行的 agent 系统。

工程落地：与 Hermes/Obsidian 管线的同构

WikiSkill 的三层结构在 Hermes 生态里几乎逐项可映射：

最大可移植洞察是三条闭环纪律：① 知识永不回滚（技能可以被拒，学到的东西必须留下）；② 提案前先查审计轨迹（不重复失败方案）；③ 执行与提案访问分离（知识服务进化，不服务执行）。这三条可以原样写进任何 skill 维护工作流。

批判性阅读

  • 选模型略偏心：5 个模型含 3 个 Qwen + 自家 Gemini；Gemini-3.5-Flash 的 ALFWorld 全方法同分 85.9% 是因为验证集提前满分——"无技能上限"对自家模型有点讨巧。
  • 全量注入隔离检索：技能直接注入 system prompt，回避了技能库变大后的检索成本（与 Skills System 的渐进披露互补，但真实性存疑）。
  • 严格门控排除中性提案：只接受严格优于 R_best 的提案，可能阻断"本轮持平、下轮才见效"的中间提案。
  • wiki 无自动剪枝：长演化运行会膨胀，论文自认这是未来工作。
  • 未覆盖超长地平线：数百动作/数小时的任务不在实验范围。
