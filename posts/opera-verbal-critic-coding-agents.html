Opera：把批评家反馈做成「持久化笔记」，长程编码 Agent 才听得进去

October 13, 2026

长程编码 Agent 的问题，不在「不会写代码」，而在「没人盯着它改完没有」

让一个 agent 在几十上百轮里探索仓库、改代码、跑测试，它会反复犯同一个错、做冗余探索，甚至没验证完就谎报「完成」。自然的解法是加一个批评家（critic）。但批评家本身也是 LLM——它看的是「进行中的工作」，中间证据不全，一个看似合理的诊断可能误读局部证据，把本可成功的轨迹带偏。

批评家反馈不该是一条评论，而是一次「干预」——其价值只有事后才能看清。Opera 的核心主张：把每次纠错当一条持久化笔记，审核后才投递，追踪到问题真正解决才关闭，并把「照做了」和「解决了」分开记。

这就是 Opera（arXiv 2609.33987，Kai Mei 等 10 人）做的事。它是「口头批评家框架」，不碰 agent 的权重，只通过执行轨迹和自然语言与 agent 交互，因此能即插即用到任何 harness 上。

一、为什么现有批评家不够用

此前的批评家工作——Self-Refine、Reflexion、CRITIC，以及编码专用 SWE-PRM、SWE-Search、Agentic Rubrics——都集中在「评估轨迹、生成反馈」上，几乎没人追踪反馈送达之后发生了什么。Opera 把问题拆成三个：

  • ① 何时介入？定期反馈来得太慢（agent 可能连发几次失败命令才等到下一次回顾）；但不是每个事件都需要纠偏。
  • ② 反馈靠不靠谱？一个 plausible 的诊断可能错读证据、带偏工作；LLM 裁判即使在核对明确标准时也有噪声（RuVerBench 的发现）。
  • ③ 干预生效没？agent 可能照做了建议，但底层故障纹丝没动。

对应地，Opera 给出三块拼图：混合调度（①）、算子化诊断（②）、审计式笔记管理（③）。

二、核心抽象：持久化笔记

Opera 把每次纠错建模为一条 open note：一个被诊断的问题 + 当前建议 + 固定不变的解决判据。持久化让它能跨轮次追踪自己的口头反馈；固定判据保证「解决」是对照最初的问题来判断，而不是对照最新的建议。任一时刻至多一条 open note，把 agent 的注意力锁在单一修正上，也让结果可归因。

混合调度（何时看）

每 k 轮定期回顾，加上五类事件即时触发：Idle（无进展）、Repeat（重复动作）、Error（失败动作/工具调用）、Claim（声称完成）、Submission（提交补丁）。事件触发会重置定时器，多信号合并成一次回顾。关键点：「回顾」不等于「干预」——批评家可以返回 continue，让 agent 继续跑而不打扰，因为不必要的干预会打断本可成功的轨迹（Vasudev et al. 2026 的恢复-干扰权衡）。

算子化诊断（怎么干预）

自由文本批评常是空话（「再考虑考虑边界情况」）或一锅炖。Opera 要求每次诊断必须落在一个带类型的算子上，共 9 个、横跨修复的 5 个阶段，每个算子都按 Design by Contract 规定「何时适用 / 需什么证据 / 可请求什么修正 / 何时算解决 / 明确排除什么」：

阶段算子作用

每次输出：点名算子 + 引证据 + 给位置/当前行为/需改什么/怎么验证。一次只报一个问题，避免互相打架的指令。

审计式笔记管理（发不发 / 关不关）

因为批评家本身是 LLM、诊断可能 plausible 但错，Opera 用两道审计把关：

  • 准入审计（admission）：投递前核对「证据是否真支持诊断、修正是否必要、提议的检查能否证成解决」，拒绝无关清理和无新证据的重复提醒。
  • 释放审计（release）：关闭笔记前要求执行结果（行为性需求）或可见编辑（静态需求）作证据，通过后归档并把引导从上下文移除。

两道审计都只 accept/reject、不改写——是 verifier，不是 co-author。

三、实验：数字说话

在三个基准上评测：Terminal-Bench 2.1（89 题，Terminus-2）、SWE-Bench Pro（100 题子集，OpenHands）、DeepSWE v1.1（113 题，mini-swe-agent）。策略模型 Qwen3.8-27B，默认批评家 GPT-5.6-Sol：

三个基准均值均第一。但请注意一个诚实的细节：SWE-Pro 上对最强基线只领先 0.6 pp——因为非批评家 agent 在 SWE-Pro 上已经很强，所有批评家的收益都小。跨 4 个策略模型（Qwen3.5-9B / Muse-Glimmer-30B / Qwen3.8-27B / DeepSeek-V4-Flash），最高 +12.4 / +15.0 / +8.9 pp 都来自最弱的 Qwen3.5-9B。唯一例外：Qwen3.5-9B 在 DeepSWE 上有无批评家都是 0——批评家替代不了能力缺失。

四、最反直觉的发现

「照做」≠「解决」

Opera 刻意把 adherence（是否照做） 和 resolution（是否解决） 分开追踪。实证：弱模型 Qwen3.5-9B 收到反馈后编辑的频率和强模型 Muse-Glimmer-30B 一样高，却只解决掉约一半的 requirement-contract / state-transition 笔记；而 Muse 很少立刻编辑，最终却解决了大多数问题。立即照做是解决与否的糟糕代理。

审计是净收益的大头

把两道审计全去掉，增益大幅缩水：TB 从 +7.9 掉到 +2.6（丢约 2/3）、DeepSWE +8.9 → +4.5（丢约 1/2）。审计在「过滤有害干预」——在中间证据易误读、纠错代价高的基准上尤其值钱。

自反批评有效，但只在模型够强时

让策略模型批评自己（Self）在 DeepSWE 上给 Qwen3.8-27B、DeepSeek-V4-Flash 各带来 +6.2 pp，追平甚至超过 Claude 当批评家的收益。因为自反批评没有额外知识，这暗示收益大半来自框架本身——及时回顾 + 类型化诊断 + 追踪，逼模型把它本有却未用的知识用出来。但低能力策略（Qwen3.5-9B）自反最多 +2.7 pp，配强批评家 GPT 则至少 +12.4 pp。

恢复-回归权衡

强模型把反馈转成更多「救回」（原本解不出的题），但也更多「拖累」本该做对的题——因为它们更快照做，放大了正确干预和不必要干预两边的影响。弱模型几乎不回归，被救回的也少。还有一个细节：failure_triage（纠正「怎么读一个错误」）对多数模型带来轻微负收益——告诉它该怎么读错误，不等于告诉它该改什么。

五、训练配方：批评家当老师

Opera 的第二个用途是产出训练数据。把 SWE-Bench Pro 按仓库切分成 270 训练 / 108 留出，选了 67 题（基座很少成功、但两种来源都至少有一条成功轨迹），对 Qwen3.5-9B 做 SFT：

训练数据SWE-Pro（留出）TB-2.1
无（基座）28.723.6
老师 Qwen3.8-27B rollout（蒸馏）39.57.9 ⚠️
Opera 引导38.925.8

两种来源在留出仓库上打平（都约 +10 pp），但蒸馏把 TB-2.1 从 23.6% 砸到 7.9%，Opera 引导反而保住 25.8%。原因：蒸馏数据是 off-policy 的——拟合老师的完整轨迹会把学生拉向老师的分布，分布偏移越大遗忘越重；而 Opera 引导的 rollout 里每个动作都是学生自己的，批评家的影响只通过笔记进入上下文，近似 on-policy。这正是 DAgger 和 on-policy distillation 的原则：在学生实际到达的状态上给专家纠错，而不是喂它专家的完整轨迹。

六、局限

  • SWE-Pro 上对非批评家只 +4.0 pp、对最强基线只 +0.6 pp——批评家在「已很强的 agent」上边际收益有限。
  • 批评家补不了能力缺口（Qwen3.5-9B 在 DeepSWE 上 0→0）。
  • 强模型的回归副作用不可忽略——净收益为正，但代价落在「本该做对的题」上。
  • 训练只做了单一模型 SFT + 单一 OOD 基准；规模扩展、用训练后的模型当新策略迭代、或结合 RL，都留作 future work。
  • 自反批评增加了推理算力，但对比中未对齐这部分计算量。

七、对你自己 agent 工作流的启示

  1. 把每条纠偏当「带判据的开放事项」：反馈必须带上「何时算解决」的可验证判据，而不是只给一句建议。这是「做完要 verify、而非声称做完」的机制化。
  2. 投递前要有审计闸门：LLM 的诊断本身可能是错的。Opera 用第二个廉价判断「这条反馈该不该发」，消融证明这一层值 2/3 的收益。
  3. 「照做了」不等于「解决了」：追踪要分两栏——是否采纳了建议、是否真正解决了原问题。
  4. 自反批评的启示：够强的模型，把「什么时候回头检查自己」做成结构化流程，就能逼出它本有的知识。
  5. 数据侧：想喂弱模型，喂「它自己犯错 + 强模型在那个状态上的纠错」比喂「强模型的完整轨迹」更抗遗忘、跨 harness 更稳。
