LLMs Get Lost in Evolving User Intent：GPT 5.5 从 99% 降到 80.5% 的意图追踪失败

July 23, 2026

GPT 5.5 从 99% 降到 80.5%：Microsoft 证明 LLM 在用户意图演变时系统性失败

LLM coding agent 越来越多地作为协作 agent 部署——vibe coding、深度研究、迭代文档编辑。但真实交互本质上是动态的：用户很少预先完整指定意图，而是在对话中披露、修订、重塑。Microsoft Research 的 Jihoon Tack、Philippe Laban 和 Jennifer Neville 在 arXiv:2607.20734 提出一个框架，将静态单轮基准转化为意图演变的动态多轮对话，揭示了当前 LLM 的一个根本性缺口。

结论很直接：GPT 5.5 在 GSM8K 上从 99.0% 降到 80.5%——仅 6 次意图转换后。更极端的是，多个模型在 SWE-Bench Verified 上直接降到 0%。今天最强模型在单轮基准上接近饱和，但静态性能不预测动态性能。

框架：锚定式回溯构造

论文的框架设计很精巧：不从零构建多轮基准，而是将现有单轮基准"提升"为意图演变的动态对话，同时保留原数据集的验证器——无需新标注或 LLM-as-judge。

核心思路：锚定式回溯。从单轮数据提取意图作为最终轮锚点，然后回溯构造导致此锚点的合理前序情境。因为最终轮与源意图一致，原数据集的验证器直接可用。

用户意图形式化为可控状态 I_t = (f_t, C_t, C_t^rev, y_t)，三种转换类型驱动演变：

转换类型定义agent 挑战示例
Argument Reveal披露新参数积累信息"找餐厅" → "我是 vegan"
Argument Revision修改已披露值更新信念不锚定旧值New York → Brooklyn
Function Switch任务切换，共享参数携带检测切换+复用意图找餐厅 → 订餐厅

三个关键发现：

  • SWE-Bench 极端退化：GPT 5.1、Gemini 3.1、Grok、Kimi K2.5 直接降到 0%。agent 耗尽 100 次工具调用预算——把大部分预算花在探索（grep/find/ls）而非执行（pytest/apply_edits），在 extended thinking 中超时
  • 少数反常正向：DeepSeek V3.2 在 SWE-Bench 上 +40%，GPT 5.2 在 BrowseComp+ 上 +17%——但大部分模型在大部分数据集上显著退化
  • 退化是跨模型/跨域的普遍现象，不是某个模型的个别问题

消融：Function Switch 最具破坏性

论文对转换类型做了系统消融。结论明确：

场景GSM8K (5.1/5.5)BIRD (5.1/5.5)Browse (5.1/5.5)
Single-turn98.0/99.072.0/80.049.0/65.0
Reveal only97.0/96.072.0/76.045.0/46.0
Revise only96.5/97.072.0/77.047.0/61.0
Switch only87.0/87.559.0/65.045.0/62.0
All combined82.0/80.566.0/71.034.0/57.0

Function switch > argument revision > argument reveal（破坏性排序）。原因：switch 要求最大的信念状态更新——agent 必须丢弃更多已积累上下文，而非仅积累或修正。

更深层的发现（Figure 5）：对比"switch 后立即评估" vs "switch 后还有其他转换再评估"——后者显著更差。Agent 能在 switch 后立即恢复切换后的意图，但难以将 switch 前的上下文与 switch 后的更新联合整合。

Reasoning 模式无帮助，Oracle Recap 仍未关闭 Gap

两个关键消融直接质疑了常见的缓解策略：

1. 更强推理 ≠ 更好意图追踪

GPT 5.1 instant vs reasoning 模式：GSM8K 从 83.0→82.0（略降），BIRD-SQL 从 64.0→66.0（微升）。瓶颈不是局部推理能力，而是跨轮信念维护——这正好说明 harness 层（而非模型层）是正确的干预点。

2. Oracle Recap 仍不够

两种记忆机制测试：

  • Prompt Recap：每轮追加"先列出所有适用条件再回答" → 有改善
  • Oracle Recap：每轮重述完整已披露意图（oracle 信息） → 大幅改善（function switch 65%→75%）

但即使 Oracle Recap 也未达单轮 80%——这拆解出两类错误：Prompt Recap 测的是"能否从历史追踪意图"，Oracle Recap 测的是"给出正确意图后能否在冲突上下文中执行"。Oracle 仍未关闭 gap 说明问题不只是信息检索，还有冲突上下文中的执行困难。

3. 源数据难度放大效应

BIRD-SQL 控制难度（easy 有 hint vs hard 无 hint）：单轮 easy→hard 降 3.6%，演变设置下 easy→hard 降 9.0%。更难的源数据在多轮动态下退化更严重——用户委派更难任务时 agent 退化更厉害。

Turn-wise 意图追踪：Switch 是追踪瓶颈

论文隔离了意图追踪能力（Table 3）：在每轮结束时让 agent 预测用户当前意图，独立 judge 打分：

转换类型1 次出现2 次出现
Argument Reveal99.0%98.0%
Argument Revision98.0%96.0%
Function Switch89.0%82.0%

Reveal 和 revision 的追踪近乎完美，但 function switch 显著退化——跨任务的上下文整合是当前 LLM 的结构性弱点。

对 Harness Engineering 的工程启示

1. Intent tracking 是 harness 的核心能力，不是模型能力

Reasoning 模式无帮助 → 瓶颈不是模型推理 → harness 层必须维护用户意图的结构化状态，而非依赖 LLM 隐式记忆。Hermes 的 session memory 和 fact_store 正是这个方向的实践。

2. Oracle recap 不足 → harness 需要主动信念更新和上下文修剪

即使给 agent 完整意图也无法达到单轮水平——问题不只是检索，还有冲突上下文中的执行。Harness 需要：(a) 显式意图状态追踪 (b) 旧约束的主动失效标记 (c) 上下文修剪减少干扰。

3. Function switch 最难 → 多任务 harness 需要显式任务切换检测

Harness 需要检测用户何时切换任务，隔离前任务上下文，保留共享参数——这对应 Hermes 的 session/topic 管理。

4. SWE agent 耗尽预算 → harness 需要工具调用预算管理

Agent 在 evolving intent 下把 100 次工具调用预算花在探索而非执行——harness 需要预算分配策略和探索 vs 执行的平衡控制。

5. RL 可训练 → 框架可生成训练数据

Qwen3-4B 在演变意图示例上 GRPO 50 步训练后 +12%。框架可将任何单轮基准转化为 evolving intent 训练数据——为 intent tracker 模型提供数据基础。

局限与诚实标注

  • SWE-Bench 0% 的归因（论文自认 + 我的推断）：多个模型在 SWE-Bench 演变后降到 0%，论文归因于工具调用预算耗尽。但 0% 意味着完全失败——per-turn 100 工具调用 + 6 次转换的设置是否过于极端？真实用户在 SWE 任务中是否真的会 6 次切换意图？
  • 模拟用户 vs 真实用户（我的推断）：虽然有 rule-based 和 LLM-based renderer，但仍是模拟。真实用户的行为可能更不可预测——修订可能不清晰，switch 可能没有明确的共享参数。
  • 最终轮验证假设（论文自认）：验证仅在最终轮精确，中间轨迹的评估依赖调度规则。中间步骤的失败可能被最终轮成功掩盖。
  • 反常正向结果未充分讨论（我的推断）：DeepSeek V3.2 在 SWE-Bench 上 +40%，GPT 5.2 在 BrowseComp+ 上 +17%——少数模型在少数数据集上不降反升，论文未充分分析原因。
  • Function switch 在代码任务中可能不自然（我的推断）：真实用户在 SWE 任务中很少切换功能（"修这个 bug" → "现在订餐厅"）。这可能导致 SWE-Bench 的 0% 结果不完全代表真实场景。
  • RL 结果初步（论文自认）：仅 50 步训练 Qwen3-4B，单一起点，未做多模型/多数据集验证。

一句话

GPT 5.5 从 99% 降到 80.5%——仅 6 次意图转换后。Reasoning 无帮助，Oracle recap 不够：问题不在模型推理能力，而在跨轮信念维护——这是 harness 层而非模型层的职责。
